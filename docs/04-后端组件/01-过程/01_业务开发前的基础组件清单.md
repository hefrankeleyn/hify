### 1.2 需要补的组件

#### （1）首个模块的 Flyway 脚本 + Entity + Mapper 样板

**解决什么问题**：`CLAUDE.md` 5.2～5.4 的规范（五个必备字段、`deleted` 存毫秒时间戳、唯一索引带 `deleted`、复合索引定序、命名规则）目前只是文字，没有一份「跑得通」的实例。第一次踩坑（比如 `deleted` 声明成 `String`、忘记 `COLLATE`、索引漏了 `deleted`）如果发生在第一个真正的业务表上，会当场发现；如果没有样板，八个模块可能各写各的、风格不一致，且要等到跑测试或建索引失效才发现。

**建议怎么做**：从 `provider`（模型提供商）或 `agent` 里选一张最简单的表（比如 `model_provider`）先走一遍完整链路：
```
Flyway 脚本(V20260812_01__create_model_provider.sql)
  → Entity(ModelProviderEntity implements 五字段 + deleted:Long)
  → Mapper(extends BaseMapper<ModelProviderEntity>)
  → 一个単测(Spring Boot Test 起内嵌/本地 MySQL,验证插入 → 软删 → 按 name 重建同名不冲突)
```
这一趟走完之后，其余 15 张表照抄结构即可，不需要再单独设计一次。

**落点**：`hify-provider` 或 `hify-agent`（哪个先开工哪个先建），脚本命名与目录规则见 `10_数据库性能规范.md` 6.2。

#### （2）pgvector 第二数据源

**解决什么问题**：`document_chunk` 表要落在 PostgreSQL + pgvector，与主库 MySQL 是两个连接池、两套事务，需要单独的 `DataSource` / `SqlSessionFactory` 装配。

**建议怎么做**：**现在不做**。`hify-knowledge` 模块本身还没开工，提前装配一个没有表可查的数据源纯属过度准备，且装配方式（用 MyBatis-Plus 还是 JdbcTemplate 直连、多数据源怎么和 Flyway 配合）最好等 `document_chunk` 的具体访问模式明确后再定。列在这里只是标记「这是一个已知的、会出现的组件」，触发条件：`hify-knowledge` 的 `pipeline`/`vector` 包开工时。

**落点**：`hify-knowledge` 的 `config` 包（届时新建）。

### 2.2 需要补的组件

#### （1）TraceId 生成与绑定的 Filter ⚠️ 优先级最高

**解决什么问题**：`CLAUDE.md` 3.4 要求每条日志能按请求串联排查，日志 pattern 已经预留了 `[%X{traceId:-}]` 占位。但目前没有任何代码生成或写入这个值，意味着**现在跑起来的每一条日志，`traceId` 位置永远是空的**——这是当前唯一一处「规范已经承诺、代码没兑现」的缺口，会直接影响所有后续 Controller 写日志时的可排查性，越晚补越难补（补的时候要把已经写的 Controller 日志重新验证一遍）。

**建议怎么做**：一个 `OncePerRequestFilter`：
```
1. 从请求头取 X-Request-Id(前端/网关如果传了就用,没传就生成一个)
2. MDC.put("traceId", requestId)
3. 放行
4. finally 里 MDC.clear()   —— CLAUDE.md 3.8 第 6 条,ThreadLocal 用完必须 remove
```
🔴 **这个 Filter 只覆盖 Tomcat 工作线程本身这一段**。一旦进入 `llm-chat-` / `kb-index-` 线程池的异步任务，`MDC` 会是空的（`CLAUDE.md` 3.8 第 7 条）——`SseEmitter` 的编排代码里必须在提交任务前把 `traceId` 当作显式参数取出来，再在任务体内 `MDC.put` 回去。这一条在 `CLAUDE.md` 7.1 的示例代码里已经点出来了（`String traceId = MDC.get("traceId");` 那一行），Filter 只是把「从哪来」这一步补上。

**落点**：建议放在 `hify-common` 的 `config` 包（一个全局关注点，不属于任何业务模块），命名如 `TraceIdFilter`。

#### （2）补齐 `GlobalExceptionHandler` 的剩余 Web 层异常

**解决什么问题**：类头注释里已经自己列出了缺口——`BindException`（查询参数绑定失败）、`ConstraintViolationException`（方法级校验，如 `@RequestParam` 上直接标 `@Min`）、`HttpMessageNotReadableException`（JSON 格式错）、`HttpRequestMethodNotSupportedException`、`NoResourceFoundException` 目前全部落到兜底 handler，被报成「系统内部错误」并打 `error` 全栈——这些其实是客户端的问题，误报成系统故障会在生产日志里制造大量假警报，且 `ErrorCode` 里已经备好了对应的 `PARAM_INVALID` / `METHOD_NOT_ALLOWED` / `NOT_FOUND`，没有理由不用。

**建议怎么做**：不必现在一次性补全——**跟着第一个真正暴露分页查询接口（会触发 `ConstraintViolationException`）或第一次前端联调（会触发 JSON 格式错）时顺手补**，比提前臆测更准。放进这份清单是为了不要在这些报错第一次出现时被当成系统 bug 去排查半天。

**落点**：`hify-common` 的 `GlobalExceptionHandler`，追加 handler 方法即可。

#### （3）请求日志：不需要统一组件，按 Controller 自己打

`CLAUDE.md` 3.4 的规则是「Controller 入口 info：`[API] 动作, 关键标识`，不打全量 body」——这本身要求日志内容按业务语义裁剪（哪个字段是「关键标识」因接口而异），做成统一 `Filter`/AOP 反而会退化成打全量 `body` 或啥都不打两个极端。**结论：不需要新组件，每个 Controller 方法里手写这一行日志即可**，属于写业务代码时的编码习惯，不属于基础设施。

## 三、外部调用（LLM）

这一整节在 `04_LLM调用的线程超时重试与容错.md` 里已有完整的设计推导（约 30KB，含配置值的推理过程），这里不重复推导，只回答「现在要写哪些类、放哪」。**这是五个角度里当前实现程度最低的一块**——目前只有 `hify-provider/pom.xml` 里一行 `resilience4j-circuitbreaker` 依赖，和 `config`/`client` 包下 `package-info.java` 里写好的设计意图，没有一行可运行代码。

### 3.1 需要补的组件

#### （1）两个隔离线程池

**解决什么问题**：一条 SSE 对话从进入业务线程池开始，会独占一个线程整轮（1～5 分钟），Tomcat 工作线程早已在建连后释放。如果对话线程池和知识库索引线程池共用同一个池，长任务和短任务互相排队，会出现「索引一个大文档时，所有对话都在排队」这种互相拖累。

**建议怎么做**：两个 `ThreadPoolTaskExecutor`（显式构造，禁止 `Executors` 工厂方法）：

| 池 | 用途 | 配置 |
|---|---|---|
| `llm-chat-` | SSE 对话编排 | core 32 / max 64 / **queue 16**（🔴 队列必须小，见 `04_...` 1.2 的反直觉推导） |
| `kb-index-` | 文档解析、分块、向量化 | core 2 / max 4 / queue 64 |

拒绝策略 `AbortPolicy`，捕获后转 `BizException(ErrorCode.TOO_MANY_REQUESTS)`。

**落点**：`llm-chat-` 归 `hify-chat` 的 `config` 包（`hify-chat` 是编排层，池的生命周期该由它管）；`kb-index-` 归 `hify-knowledge` 的 `config` 包。**两者现在都可以先搭一个空池**（不接业务逻辑），因为线程池配置本身独立于业务代码，越早跑起来越早能在真实并发下观察队列行为。

#### （2）HTTP 客户端 + 四道超时闸

**解决什么问题**：标准 HTTP 客户端的 read timeout 只覆盖「等第一个字节」，流开始之后上游卡住十分钟也不会超时——这是 LLM 流式调用最容易被忽视的一个坑，必须自己在读流循环里算「距上一个 chunk 多久」。

**建议怎么做**：基于 JDK 21 自带 `java.net.http.HttpClient`（不引第三方 HTTP 库，`pom.xml` 注释里已经写明理由），封装连接 3s / 首字节 30s（Ollama 90s）/ 流间隔 30s（Ollama 60s，手写）/ 整体 300s（Ollama 600s）四道闸。具体实现见 `04_...` 二、2.2。

**落点**：`hify-provider` 的 `client` 包。这是四个 provider（OpenAI/Claude/Gemini/Ollama）客户端共用的基础设施，建议先把「四道闸 + SSE 逐行解析」这个通用骨架搭出来，再接具体 provider 的请求/响应格式。

#### （3）熔断器注册表

**解决什么问题**：超时只产生失败信号，熔断器负责在失败率超阈值时快速失败、不再把请求打到已经挂了的 provider 上。必须**按 `providerId` 分实例**——OpenAI 挂了不能连带把 Ollama 也熔断。

**建议怎么做**：一个 `CircuitBreakerRegistry` + 按 `providerId` 缓存 `CircuitBreaker` 实例的工厂类，配置见 `04_...` 四、4.2（时间窗、`ignoreExceptions(BizException.class)`）。

**落点**：`hify-provider` 的 `client` 或 `config` 包。

#### （4）per-provider 舱壁（信号量）

**解决什么问题**：本地 Ollama 推理超过显存并发能力后是**集体劣化**（所有请求一起变慢甚至超时），不是排队变慢——必须用信号量硬性挡住超额并发，而不是指望线程池或熔断器兜住。

**建议怎么做**：`Semaphore`，Ollama 上限 3，云 API 上限 20，按 providerId 持有各自实例。

**落点**：`hify-provider` 的 `client` 包，与熔断器注册表相邻。

#### （5）重试封装

**解决什么问题**：LLM 调用的失败形态复杂（连接失败/429/5xx 可重试，401/400/404 不可重试，**首字节到达之后一律不可重试**），如果不封装，容易在具体业务代码里写出「重试了已经吐了一半的回复」这种把两段不连贯文本拼接的 bug。

**建议怎么做**：手写一个装饰器（不引 Spring Retry，理由见 `04_...` 三、3.4），退避 500ms→1500ms（±30% 抖动），最多 2 次，总预算 60s；工具调用之后那一轮请求重试上限降为 0。

**落点**：`hify-provider` 的 `client` 包。

### 3.2 建议顺序

这五项不需要五个人一起做（本来也是一个人），但有依赖关系：**线程池 → HTTP 客户端 + 超时闸 → 重试封装 → 熔断器 → 舱壁**，后三者都是在「调用已经能跑通」之后叠加的容错层，不要在还没打通一次真实 LLM 调用之前就先搭熔断器——那样熔断器的失败率统计永远是 0，等于白装（`04_...` 四、4.2 已指出这一点）。

### 4.2 需要补的组件

#### （1）缓存 key 命名规范

**解决什么问题**：`CLAUDE.md` 九节定了哪些对象要缓存（Provider/Agent 配置 TTL 30min，对话上下文 TTL 2h，MCP 工具清单）以及 TTL，但没定 key 该怎么拼。八个模块各自往同一个 Redis 实例写 key，如果没有前缀规范，`agent:1` 这种 key 迟早会在两个模块间撞车，或者排查时靠 `SCAN *` 猜哪个 key 是哪个模块写的。

**建议怎么做**：约定 `hify:{module}:{对象}:{id}` 的前缀规则，比如 `hify:agent:config:1001`、`hify:chat:context:{conversationId}`。这不需要写代码，是一条约定，落在本文档或直接补进 `CLAUDE.md` 九节即可；如果想要类型安全，可以在各模块的 `constant` 包里加一个 `XxxCacheKey`（`@UtilityClass` + 静态方法拼 key），但不是必须现在做——第一个用到缓存的模块（大概率是 `hify-provider` 或 `hify-agent`）落地时顺手定即可。

**落点**：约定写文档；如果要落代码，各模块自己的 `constant` 包。

#### （2）Spring Cache 注解要不要引入 —— 需要用户拍板

**解决什么问题**：`RedisUtil` 是手动 `get`→查库→`set` 的裸操作，每个需要缓存的 Service 方法都要重复写这段样板。Spring 提供 `@Cacheable`/`@CacheEvict` 注解可以省掉这段样板，但 `spring-boot-starter-cache` **不在 `CLAUDE.md` 1.3 的技术栈表里**。

**建议怎么做**：按 `CLAUDE.md` 12.5「需要新依赖时先问」，这里不擅自决定，先列出两个选项，见文末「需要拍板的问题」。

#### （3）MCP 工具清单的缓存 + 数据库二级兜底

**解决什么问题**：`CLAUDE.md` 六、6.5 明确「MCP Server 不可用时，工具清单走缓存兜底」，这要求缓存不是简单的 TTL 过期就读空，而是「缓存过期后如果查上游失败，仍然返回旧值」的模式。

**建议怎么做**：**现在不做**，`hify-mcp` 模块还没开工。这是一个会在该模块落地时才需要的、比通用 Cache-Aside 更特殊的模式，提前抽象没有意义，列在这里只是标记会出现。

**落点**：`hify-mcp` 的 `service.impl`（届时新建）。

### 5.2 需要补的组件

#### （1）`SensitiveUtil` 脱敏工具

**解决什么问题**：`CLAUDE.md` 3.4 硬性规定「API Key / Token / MCP 鉴权信息一律不进日志，必须打时用 `SensitiveUtil.mask()`（保留首尾各 4 位）」，但这个类目前不存在——一旦 `hify-provider` 开始写 Provider 的连通性测试、`hify-mcp` 开始写鉴权配置，第一次需要在日志里打印这些字段时就会卡住。

**建议怎么做**：`@UtilityClass`，一个 `mask(String raw)` 方法，保留首尾各 4 位、中间替换成固定长度的 `*`，对长度不足 8 位的输入整体打码（避免短字符串脱敏后反而暴露全部内容）。

**落点**：`hify-common` 的 `util` 包。

#### （2）异步场景的 `traceId` 透传工具

**解决什么问题**：`CLAUDE.md` 3.8 第 7 条——异步线程里 `ThreadLocal`（`MDC`/`UserContext`/`RequestContextHolder`）都是空的，必须在提交任务前显式取出再传入。如果每个提交到 `llm-chat-`/`kb-index-` 的地方都手写「取 `MDC.get` → 传参 → 任务体内 `MDC.put` → `finally MDC.clear`」，容易漏写 `clear`（线程池复用线程，漏 `clear` 会导致下一个任务读到上一个请求的 `traceId`）。

**建议怎么做**：一个轻量包装，比如 `TraceableRunnable`（或直接给 `ThreadPoolTaskExecutor` 配 `TaskDecorator`，Spring 原生支持），在 `execute` 时自动完成「取值→包装→清理」，业务代码不用每次手写这四步。

**落点**：`hify-common` 的 `util` 包（工具本身与业务无关）；接入点在 `hify-chat`/`hify-knowledge` 的线程池配置里（三、3.1 的两个线程池）。

#### （3）Actuator / Micrometer 要不要引入 —— 需要用户拍板

**解决什么问题**：目前的「健康检查」只是一个手写 Controller，返回是否存活，不检查 MySQL/Redis 连通性，也没有任何运行时指标（JVM 内存、线程池队列深度、Hikari 连接池使用率）。`ThreadPoolTaskExecutor` 的队列深度尤其值得关注——`CLAUDE.md` 反复强调队列必须小、满了要能观察到，没有指标就只能等用户反馈「卡住了」才知道。

**建议怎么做**：不擅自引入（不在技术栈表里），列入文末待拍板问题。

## 六、补充：ArchUnit 架构测试（不属于以上五类，但强相关）

**现状**：`pom.xml` 已声明 `archunit-junit5` 依赖（`CLAUDE.md` 12.3 要求「改完确保已有测试通过，包括架构测试」），但 `hify-app/src/test` 下目前只有 `HealthControllerTest`，**没有任何 `@AnalyzeClasses` 测试类**。

**解决什么问题**：`CLAUDE.md` 第十一节的 20 条红线里，至少 6 条是可以用 `ArchUnit` 自动化守住的静态规则：跨模块只能引用对方 `service`/`dto`/`constant`/`exception`（红线 1）、Controller 不注入 `Mapper`/`service.impl`（红线 2）、`@Transactional` 只在 `service.impl`（红线 4）、不字段注入（红线 7）、不显式 `new Thread()`/`Executors`（红线 6）等。如果不写这些测试，这些规则只能靠人肉 review 守住——项目只有一个人开发，短期内不容易犯错，但一旦写代码的节奏快起来（尤其是后续如果有 AI 辅助大量生成代码），最容易先被突破的就是这类「编译能过、但违反分层约定」的错误，而这类错误恰恰是肉眼在 diff 里最不容易看出来的。

**建议怎么做**：现在就补，不用等业务代码写多了再补——规则数量固定、和业务逻辑无关，早写晚写工作量一样，但早写能在第一次违反红线时就被 CI/本地测试拦住，而不是等到某天 code review 才发现。

**落点**：`hify-app/src/test/java/com/hify/architecture/`（新建包），一个 `LayerRuleTest` 类起步，覆盖依赖方向和分层规则，后续可以按红线条目逐条加。

## 八、需要拍板的问题

按 `CLAUDE.md` 12.5「规范没覆盖时先问，不要自己编」，以下三项本文没有替用户决定：

1. **Spring Cache 注解**（`@Cacheable`/`@CacheEvict`，`spring-boot-starter-cache`）要不要作为白名单外依赖引入，还是继续手写 `RedisUtil` 调用？
   - 引入：Service 方法少写重复的「查缓存→查库→回写缓存」样板。
   - 不引入：维持现有技术栈边界，`RedisUtil` 的写法更直白、行为完全可控（尤其是 `CLAUDE.md` 九节要求「对话消息、知识库文档、LLM 响应不缓存」这类例外情况，手写调用比注解排除更直观）。

2. **Actuator / Micrometer** 要不要引入？
   - 引入：健康检查能检测 MySQL/Redis 连通性，`ThreadPoolTaskExecutor` 队列深度等运行时指标可观测。
   - 不引入：技术栈表未列出，20-50 人内部工具场景下，出问题时人工看日志基本够用；真要引入也应先问清楚要不要顺带接 Prometheus/Grafana，还是只要一个更完整的 `/actuator/health`。

3. **`ErrorCode` 的模块号段**（`2000-2999` Provider、`3000-3999` Agent……）现在要不要预埋一批通用错误码（如 `XXX_NOT_FOUND`、`XXX_NAME_DUPLICATE`），还是等写到对应模块 CRUD 时再按需添加？
   - 预埋：多模块共性错误码（找不到、名称重复）复用，减少后续重复添加。
   - 按需添加：`CLAUDE.md` 8.5 本身的取舍就是「一屏看完，不会撞号」，过早预埋可能埋出用不上的号，且不同模块的「找不到」文案可能需要更具体（比如「Provider 不存在」比「资源不存在」更明确）。
