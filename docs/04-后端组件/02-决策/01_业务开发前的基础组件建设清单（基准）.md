## 二、第一档：必须先做

### 2.1 数据库初始化脚本

**现状核实**：`application.yml` 已启用 Flyway，指向 `classpath:db/migration`；六个业务模块（`provider`/`agent`/`chat`/`mcp`/`workflow`/`knowledge`）的 `db/migration` 目录已建好，**里面一个脚本都没有**，16 张表一张没建。

> ⚠️ 一个需要澄清的细节：严格说，Spring Boot / MyBatis-Plus 在**启动阶段**不会校验表是否存在——`Mapper` 是懒代理，SQL 只在真正被调用时才执行，所以空表不会让应用启动失败。会失败的是**第一次真正调用 `Mapper` 方法**（写第一个 CRUD、跑第一个单测）的那一刻。结论不变——这仍然是「业务代码写不出来」的第一档问题，只是触发时机比「启动」更晚一点点，不影响这条决策本身。

**决策：用 Flyway 版本化脚本落地，不用 Spring Boot 原生的 `schema.sql`/`data.sql` 自动建表机制。** 项目已经把 Flyway 定为唯一的库版本管理机制（`CLAUDE.md` 5.8：脚本一旦发布永不修改），`schema.sql` 不做版本追踪、每次启动都可能重新执行，两条机制同时对同一批表生效会冲突，且和「已发布脚本不可改」的规范直接矛盾。所以「建表 DDL」在本项目里就是「写 Flyway 脚本」，不是新增一条初始化路径。

**范围**：16 张表里的 **15 张 MySQL 表**（不含 `document_chunk`——它落在 pgvector，第二数据源还没接线，建了也用不上，沿用过程稿已定的延后处理，不在这次范围内）。

**版本号分配（避免多模块脚本撞版本号）**：Flyway 把所有 `locations` 下的脚本合并成同一条时间线排序执行，`V<版本>__<描述>.sql` 的版本号必须**全局唯一**——如果两个模块各自从 `V20260812_01` 开始编号，会冲突。`CLAUDE.md` 5.8 已经点出这一点（「时间戳式版本号，多目录下递增序号必冲突」），本项目是一个人开发，处理方式是：**把这一批初始建表脚本当作同一条全局序列编号**，不按模块各起一套：

| `V20260812_03` | `knowledge_base` | `hify-knowledge` | `V20260812_03__create_knowledge_base.sql` |

| `V20260812_05` | `tool` | `hify-mcp` | `V20260812_05__create_tool.sql` |
| `V20260812_06` | `agent` | `hify-agent` | `V20260812_06__create_agent.sql` |
| `V20260812_07` | `agent_knowledge_base` | `hify-agent` | `V20260812_07__create_agent_knowledge_base.sql` |

**不在本文档范围内的事**：每张表的具体列设计（除五个必备字段外，业务列该叫什么、加哪些索引）不在这里展开——写脚本时参照 `09_核心数据表与关系.md`（各表职责与字段线索）+ `10_数据库性能规范.md`（6.1 建表模板、6.3 建表检查清单）+ `CLAUDE.md` 5.2～5.4。本文档只锁定「现在要建哪些表、每张表落在哪个模块的哪个文件、版本号怎么分配」这三件事。

**验收标准**：应用启动日志里 Flyway 报告成功执行 15 个迁移脚本；抽 1～2 张表（建议 `model_provider`，最简单）跑一次插入 → 软删除 → 按唯一键重建同名，验证 `CLAUDE.md` 5.3 的唯一索引方案生效。

**落点**：对应模块的 `hify-{module}/src/main/resources/db/migration/`。

### 2.2 `@MapperScan` 扫描路径 —— 核实结论：已具备，无需改动

**核实**：`HifyApplication.java` 目前放在 `com.hify` 包（不是 `com.hify.app`），且已经写了 `@MapperScan("com.hify.*.mapper")`。类头 Javadoc 已经说明「放在这一层是为了让 `@SpringBootApplication` 的组件扫描一次覆盖全部八个模块」。

```java
@Slf4j
@SpringBootApplication
@MapperScan("com.hify.*.mapper")
public class HifyApplication { ... }
```

`com.hify.*.mapper` 能同时匹配 `com.hify.provider.mapper`、`com.hify.agent.mapper` 等全部模块的 `mapper` 包，新增模块也是零配置命中。**这一条不需要任何改动**，写进本文档是为了把它从「待办」正式划掉，避免后续被重复提出。

### 2.3 `llmChatExecutor` / `kbIndexExecutor` 线程池

**现状核实**：`hify-provider/pom.xml` 已引入 `resilience4j-circuitbreaker`（这与线程池无关，是熔断器的依赖，顺带确认过）；各模块 `config` 包目前只有设计意图性质的 `package-info.java`，没有任何线程池 Bean。`hify-chat` 的 `runtime` 包、`hify-knowledge` 的 `pipeline` 包的 `package-info.java` 里都已经写死了要跑在 `llm-chat-`/`kb-index-` 线程池上，但代码侧还没有这两个池可用——`ChatRuntime` 之类的类现在无法用 `@Qualifier` 注入，因为 Bean 还不存在。

**决策：Bean 名统一为 `llmChatExecutor`（对应线程名前缀 `llm-chat-`）与 `kbIndexExecutor`（对应线程名前缀 `kb-index-`）**，不用 `llmExecutor`/`asyncExecutor`——`CLAUDE.md` 7.1 的 SSE 示例代码里已经直接写了 `llmChatExecutor.execute(...)`，`04_LLM调用...` 过程稿里的代码示例也是这两个名字，沿用它们能让后续所有引用这两个池的代码（示例、文档、实现）用同一套名字，不用来回换算。

**配置**（`CLAUDE.md` 6.2 / `04_LLM调用...` 已经拍板的值，这里不重新推导，只落位置）：

| Bean 名 | 线程名前缀 | 配置 | 拒绝策略 | 落点 |
|---|---|---|---|---|
| `llmChatExecutor` | `llm-chat-` | core 32 / max 64 / **queue 16** | `AbortPolicy` | `hify-chat` 的 `config` 包 |
| `kbIndexExecutor` | `kb-index-` | core 2 / max 4 / queue 64 | `AbortPolicy` | `hify-knowledge` 的 `config` 包 |

拒绝时捕获 `RejectedExecutionException`，转 `BizException(ErrorCode.TOO_MANY_REQUESTS)`，不用 `CallerRunsPolicy`（会让 Tomcat 线程去跑分钟级任务，`CLAUDE.md` 6.2 已经排除）。两个池必须显式 `ThreadPoolTaskExecutor` 构造，禁止 `Executors` 工厂方法（红线速查第 6 条）。

**验收标准**：应用启动后两个 Bean 正常创建；可以先不接业务逻辑，提交一个空 `Runnable` 验证线程名前缀符合预期；参照 `MybatisPlusConfig` 的写法，装配完成后打一条 `[CONFIG]` 级别的 `info` 日志。

## 三、第二档：做业务时同步补

### 3.1 `BaseEntity`

**决策（已与你确认）：`hify-common` 新增第七个包 `com.hify.common.entity`，只放 `BaseEntity` 这一个抽象类**。原有六包固定列表里没有 `entity`，`CLAUDE.md` 2.3 需要同步补一行说明——这条不是我擅自改的，见文末「需要你确认的后续动作」。

**解决什么问题**：`CLAUDE.md` 5.2 要求每张表都有 `id`/`created_at`/`updated_at`/`deleted`/`creator_id` 五个字段，如果每个模块的每个 Entity 都手写一遍，16 张表就是 16 份重复代码，且容易出现 `deleted` 类型写成 `String`（5.3 明确警告过的坑）这类细节不一致。

**字段设计**：

```java
package com.hify.common.entity;

import com.baomidou.mybatisplus.annotation.FieldFill;
import com.baomidou.mybatisplus.annotation.TableField;
import com.baomidou.mybatisplus.annotation.TableId;
import lombok.Data;

import java.time.LocalDateTime;

/**
 * 公共 Entity 基类，五个必备字段（CLAUDE.md 5.2）。
 * <p>本类不对应任何具体表，只被各模块的 Entity 继承。
 */
@Data
public abstract class BaseEntity {

    /** 主键 id，数据库自增（id-type=auto 已在 application.yml 全局配置，此处无需再指定类型） */
    @TableId
    private Long id;

    /** 创建时间，插入时由 AutoFillMetaObjectHandler 自动填充 */
    @TableField(fill = FieldFill.INSERT)
    private LocalDateTime createdAt;

    /** 更新时间，插入/更新时由 AutoFillMetaObjectHandler 自动填充 */
    @TableField(fill = FieldFill.INSERT_UPDATE)
    private LocalDateTime updatedAt;

    /** 逻辑删除:0 未删,已删存删除时刻毫秒时间戳。属性名必须叫 deleted,由 MybatisPlusConfig 全局识别,不需要 @TableLogic */
    private Long deleted;

    /** 创建人 id。登录体系未落地前始终为 0（数据库 DEFAULT 兜底），不在 Java 侧设默认值（CLAUDE.md 3.5 第 4 条） */
    private Long creatorId;
}
```

🔴 `deleted` 不加 `@TableLogic`——这是刻意的，和 `MybatisPlusConfig` 里已经落地的全局逻辑删除配置保持一致（5.3 已经解释过原因：16 张表各自标注容易漏标）；只要属性名叫 `deleted` 就会被全局配置自动识别。

**落点**：`hify-common/entity/BaseEntity.java`；各模块的 Entity 改为 `extends BaseEntity`，只需再写自己的业务列。

**验收标准**：任意一个模块的第一个 Entity 继承它后，插入一条记录，`createdAt`/`updatedAt` 自动填充，`deleted` 默认为 `0`。

### 3.2 统一分页参数封装

**现状核实**：`hify-common/dto` 包目前物理上不存在任何文件（连 `PageQuery` 都还没建），`CLAUDE.md` 8.3 已经给出了它的样例代码，只是还没真正落地。

**决策**：

1. `hify-common/dto/PageQuery.java`：按 `CLAUDE.md` 8.3 的样例（`page` 默认 1，`pageSize` 默认 20、`@Max(100)`）直接实现，供 Controller 层的查询 Request 继承或组合使用。
2. `hify-common/util` 包新增一个转换方法，把 `PageQuery` 转成 MyBatis-Plus 的 `Page<T>`。**这个转换不能放在 `dto` 包里返回 `Page` 类型**——`CLAUDE.md` 4.1 规定 `service` 接口层不能出现 `Page`/`Wrapper`，如果 `dto` 包直接暴露 `Page` 类型，等于把 MyBatis-Plus 概念泄露进 L0，且会被 Controller、`service` 接口一路带着走。放进 `util` 包是因为它只在 `service.impl` 内部被调用（`service.impl` 本来就允许看到 MyBatis-Plus 的 `Page`/`Wrapper`），不会污染更上层。

```java
// hify-common/util/PageConverter.java
@UtilityClass
public class PageConverter {
    public static <T> Page<T> toPage(PageQuery query) {
        return new Page<>(query.getPage(), query.getPageSize());
    }
}
```

**落点**：`hify-common/dto/PageQuery.java` + `hify-common/util/PageConverter.java`。

**验收标准**：`PageConverter.toPage(new PageQuery(2, 20))` 返回 `current=2, size=20` 的 `Page` 对象，单测覆盖。

### 3.3 入参校验（`@Valid`）—— 不是新组件，是编码约定

**核实**：`spring-boot-starter-validation` 已在 `hify-common` 引入，`GlobalExceptionHandler` 已经实现 `MethodArgumentNotValidException` 的处理（`@Valid @RequestBody` 校验失败会正确转成 `Result.fail(PARAM_INVALID, ...)`）。**这条不需要新增任何基础设施**，每个 Create/Update 接口的 Request DTO 上按 JSR-303 注解写好校验规则、Controller 方法参数前加 `@Valid` 即可生效。

唯一的遗留细节：如果某个接口直接用 `@RequestParam`/`@PathVariable` 加校验注解（而不是包进一个 DTO），触发的是 `ConstraintViolationException`，目前 `GlobalExceptionHandler` 还没有为它写 handler（类头注释里已自己列出这个缺口）。这个不升级为独立条目，**跟着第一次真正写到这种接口时顺手补**即可。

### 3.4 统一时间序列化

**解决什么问题**：Jackson 默认把 `LocalDateTime` 序列化成 `[2026,3,16,10,30,0]` 这种数组——根源是 Spring Boot 自动装配的 `ObjectMapper` 默认开启了 `WRITE_DATES_AS_TIMESTAMPS`，`JavaTimeModule` 在这个开关打开时只能退化成按字段拆数组（`LocalDateTime` 没有时区/纪元，给不出真正的时间戳数值）。前端拿到数组解析不了。

**决策**：不需要新写 Java 类——`jackson-datatype-jsr310` 已经随 `spring-boot-starter-web` 传递引入，Spring Boot 会自动探测并注册 `JavaTimeModule`，只需要在 `application.yml` 关掉那个开关：

```yaml
spring:
  jackson:
    serialization:
      write-dates-as-timestamps: false
    time-zone: Asia/Shanghai
```

⚠️ 注意这个 `ObjectMapper` 是 Spring MVC 用的那个，和 `RedisConfig` 里为 Redis 单独构造的 `ObjectMapper`是两回事（`RedisConfig` 类头注释已经点明过，两者不能互相复用）——这条决策只影响 HTTP 响应的 JSON 格式，不影响 Redis 里存的 JSON。

**落点**：`hify-app/src/main/resources/application.yml`。

**验收标准**：任意一个返回 `LocalDateTime` 字段的接口，响应体里 `createdAt` 是 `"2026-08-12T10:30:00"` 这样的字符串，不是数组。

### 3.5 Spring Cache 集成（`@EnableCaching` + `RedisCacheManager`）

**技术澄清（和过程稿的一处修正）**：上一版过程稿把这条列为「需要拍板是否引入白名单外依赖」的开放问题——**现在可以确认不需要新依赖**。`@EnableCaching`/`@Cacheable` 来自 Spring 核心的 `spring-context`（任何 Spring Boot 应用天然自带），`RedisCacheManager` 类本身就在 `spring-data-redis` 里（`hify-common` 已经通过 `spring-boot-starter-data-redis` 引入，`RedisConfig` 已经在用这个 starter）。**不需要加 `spring-boot-starter-cache`，纯配置工作**，不违反「不引入技术栈以外依赖」的红线。

**决策**：`hify-common/config` 包新增 `CacheConfig`：

```java
@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public CacheManager cacheManager(RedisConnectionFactory connectionFactory) {
        RedisCacheConfiguration defaultConfig = RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(30))
                .serializeValuesWith(RedisSerializationContext.SerializationPair
                        .fromSerializer(/* 复用 RedisConfig 里已经配好的 GenericJackson2JsonRedisSerializer */));

        Map<String, RedisCacheConfiguration> namedConfigs = new HashMap<>();
        namedConfigs.put("chatContext", defaultConfig.entryTtl(Duration.ofHours(2)));
        // 其余按 CLAUDE.md 九节的对象逐个补:providerConfig / agentConfig 走默认 30min

        return RedisCacheManager.builder(connectionFactory)
                .cacheDefaults(defaultConfig)
                .withInitialCacheConfigurations(namedConfigs)
                .build();
    }
}
```

🔴 value 序列化必须**复用** `RedisConfig` 里已经配好的 `GenericJackson2JsonRedisSerializer`，不要另起一套——同一个 Redis 实例里，`@Cacheable` 写入的 key 和 `RedisUtil` 手动 `set` 的 key 如果用两套不同的序列化格式，排查时会互相看不懂对方写的内容。具体做法是把 `RedisConfig` 里构造 `ObjectMapper` 的那段私有方法提取成一个可复用的 Bean 或 `static` 方法，两处共用。

**落点**：`hify-common/config/CacheConfig.java`。使用方式是各模块 `service.impl` 的方法上按 `CLAUDE.md` 九节列出的对象加 `@Cacheable(cacheNames = "...", key = "#id")` / `@CacheEvict`，具体 `cacheNames` 由各模块自己在落地时定。

**验收标准**：一个简单的 `@Cacheable` 方法第一次调用后，`redis-cli` 里能 `SCAN` 到对应 key，且 `TTL` 符合预期（30min 或 2h）。

### 4.3 结构化日志配置（`logback-spring.xml` + 请求日志过滤器）

这一项包含两个不同的东西，分开说：

**① `logback-spring.xml` 区分开发/生产环境**：现在 `application.yml` 里的 `logging.pattern.console` 是唯一的日志格式配置，本地开发够用。生产环境通常需要不同的输出形式（比如结构化 JSON，方便日志采集系统解析），这个差异在本地单一环境下没有验证场景，**放到联调/准备部署前补**是合理的，不影响现在写业务代码。

**② 请求日志过滤器（记录 `method`/`path`/耗时）**：⚠️ 这里要和过程稿里的一个结论对齐，避免看起来自相矛盾——过程稿说过「Controller 入口日志不需要统一组件，各 Controller 自己按 `[API] 动作, 关键标识` 的格式打」，这条结论**说的是业务语义日志**（哪个动作、关键业务标识，这些信息只有 Controller 自己知道）。这里说的**是通用 HTTP 访问日志**（method + path + 状态码 + 耗时，和业务无关，类似 Nginx access log），两者不冲突，可以都要：业务日志由 Controller 手写，访问日志用一个轻量 `Filter` 统一兜底。

**同时，`traceId` 生成与 `MDC` 绑定，按本次决策合并进这个 Filter 一起做**（一、结论速览的差异说明 3 已提过）：一个 `Filter` 里顺带做两件事——生成/透传 `X-Request-Id` 并 `MDC.put`，以及记录访问日志——不用拆成两个 `Filter` 增加过滤器链开销。

**落点**：`hify-app/src/main/resources/logback-spring.xml`（①）+ `hify-common/config` 包新增一个 `RequestLogFilter`（②，同时承担 `traceId` 绑定）。
