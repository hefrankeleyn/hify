# Hify 代码组织方案对比（过程稿）

> 🔧 **本文档是过程稿，不是基准**。用于对比「Spring Boot 单体内部怎么组织代码」的候选方案并给出倾向，拍板后另出基准文档。

## 一、这个决策要解决的问题

### 1.1 约束

| 约束 | 对代码组织的含义 |
|------|------|
| **一个人开发** | 架构的成本不在写的时候，在**每天在里面找东西**的时候。任何「一个功能要在 5 个包之间跳」或「一个用例要写 4 个类」的结构都是持续性负债。 |
| **一期 50 人** | 3–5 QPS。性能与代码组织**无关**，别用性能理由做结构决策。 |
| **后续可能几千人** | 真正的诉求：**将来要动的时候动得了**。 |

### 1.2 先破一个误解

> **从 50 人到几千人，要改的不是代码组织。**

先把结论前置（推演见第七节）：几千人量级下，Hify 需要改的是 ① 向量检索换实现 ② 上游 LLM 的 HTTP 客户端换非阻塞 ③ JVM 与线程池参数 ④ 消息表归档 ⑤ 加实例。其中只有 ①② 涉及代码，且都封闭在**单一模块内部**。

所以代码组织这个决策的真实目标不是「支撑几千人」，而是两件事：

1. **让 ①② 这类替换点是替换一个实现类，不是刨一遍全项目**；
2. **让模块之间没有长在一起**——万一将来真要拆服务（大概率不需要），拆得动。

这两件事都不要求今天引入 MQ、RPC、服务发现，也不要求今天拆 Maven 模块。

### 1.3 评价维度

后面每个方案按这五项评估：

| 维度 | 问的是 |
|------|------|
| **日常改动成本** | 改一个完整功能，要开几个包？ |
| **新增功能成本** | 加一个模块 / 一个节点类型，要动几处已有代码？ |
| **边界强制力** | 谁保证约定不被破坏？靠自觉，还是靠机器？ |
| **可拆分性** | 将来要把一个模块搬走，要解开多少耦合？ |
| **一人可承受度** | 需要额外维护多少「架构本身」的代码？ |

## 二、候选方案

### 方案 A：技术分层（layer-first）

传统 Java 三层，按技术角色分包。

```
com.hify
├── controller/    ProviderController, AgentController, ChatController, ...
├── service/       ProviderService, AgentService, ChatService, ...
├── mapper/        ProviderMapper, AgentMapper, ...
├── entity/
├── dto/
└── config/
```

| | |
|---|---|
| **优点** | 零学习成本；新人（含未来的自己）一眼知道类放哪；框架示例全是这么写的。 |
| **代价** | 改「知识库上传」这一个功能，要在 `controller` / `service` / `mapper` / `entity` / `dto` 五个包之间来回跳，每个包里还混着另外五个模块的类。**边界强制力为零**——`ChatService` 注入 `KnowledgeMapper` 编译器不会拦，而且很顺手，赶进度时必然发生。 |
| **可拆分性** | 最差。一年后想把 knowledge 搬走，会发现它和 chat 已经通过共享 Mapper、跨表 JOIN、共享事务长成一块。 |
| **对 Hify 的判断** | ❌ 否决。Hify 有六个边界清晰的业务模块，A 方案恰好把这六条边界全抹平。 |

### 方案 B：按业务模块分包（package-by-feature，单 Maven 模块）

按业务能力分包，每个模块内部再分层；模块暴露 `api` 子包，其余对外不可见。

```
com.hify
├── common/     # 无业务含义的公共物
├── infra/      # 技术设施
├── provider/   ├── api/  └── internal/{web,service,client,mapper,entity}
├── agent/      ├── api/  └── internal/...
├── chat/       ├── api/  └── internal/...
├── knowledge/  ├── api/  └── internal/...
├── tool/       ├── api/  └── internal/...
└── workflow/   ├── api/  └── internal/...
```

| | |
|---|---|
| **优点** | 一个功能的全部代码在一个包下，改动收敛；`api` / `internal` 把「谁能用什么」写进了目录结构；模块要搬走时是**搬一个目录**。 |
| **代价** | 单 Maven 模块下，包可见性只能约束到 `public` 粒度——MyBatis-Plus 的 Mapper、Spring 要扫描的 Bean 都得是 public，**语言层面挡不住跨模块乱引用**，需要额外的机器校验（见 4.4）。 |
| **可拆分性** | 好。拆分时的工作量 ≈ 把 `api` 接口换成 HTTP/RPC 调用。 |
| **对 Hify 的判断** | ✅ **主推**。与 `CLAUDE.md` 已定的六模块划分完全对齐，成本几乎只是「换个分包方式」。 |

### 方案 C：Maven 多模块（编译期强制的模块化单体）

```
hify/
├── hify-common/      hify-infra/
├── hify-provider/    hify-agent/     hify-knowledge/
├── hify-tool/        hify-chat/      hify-workflow/
└── hify-boot/        # 启动器，聚合全部模块
```

模块间依赖写在 `pom.xml` 里，**编译器直接拦截**违规引用——`hify-provider` 没依赖 `hify-chat`，就绝对 import 不到。

| | |
|---|---|
| **优点** | 强制力最硬，没有任何绕过空间。依赖关系显式写在 pom 里，看 pom 就是看架构图。 |
| **代价** | 每次改跨模块接口都要 `mvn install` 上游模块，IDE 增量编译体验变差；新增模块要建目录、写 pom、改父 pom、配 Spring 扫描路径；`application.yml`、Flyway 脚本、测试配置的归属都要额外约定。**对一个人来说，这是每天都在付的税，换的是一个一年后才可能用上的保证。** |
| **可拆分性** | 最好，但优势相对 B 没有质变——B 已经解决了「模块搬得走」，C 多解决的是「模块搬走前不会被偷偷污染」。 |
| **对 Hify 的判断** | ⏸ **不是一期方案，但保留为升级路径**。触发条件见第八节。B → C 是机械迁移（包目录直接变成模块目录），不需要重写代码——这正是先做 B 的底气。 |

### 方案 D：六边形架构 / DDD 分层（ports & adapters）

每个模块内部再切三层，domain 层不依赖任何框架。

```
knowledge/
├── domain/       # 纯领域模型 + 端口接口，无 Spring / MyBatis 依赖
│   ├── model/    Document, Segment, Embedding
│   └── port/     DocumentRepository, VectorStorePort, EmbeddingPort
├── application/  # 用例编排
│   └── IngestDocumentUseCase, RetrieveUseCase
└── adapter/
    ├── in/web/           KnowledgeController
    └── out/persistence/  MyBatisDocumentRepository + DocumentPO + PO↔domain 转换
```

| | |
|---|---|
| **优点** | 领域逻辑与框架彻底解耦，可脱离 Spring 单测；换 ORM / 换数据库只动 adapter。 |
| **代价** | **一个 CRUD 要写 4 个类外加两次对象转换**（PO ↔ domain ↔ DTO）。Hify 六个模块里，`provider` / `agent` 管理面基本是纯 CRUD，套这套结构收益为零、成本翻三倍。 |
| **对 Hify 的判断** | ❌ 整体否决，✅ **局部借用**。真正有领域逻辑的地方（`chat` 的对话编排、`workflow` 的图执行、`knowledge` 的处理链）借用它的**思想**——独立的领域对象 + 面向接口的外部依赖——但不铺开它的目录形制。见第六节「分级设计」。 |

## 三、横向对比

| 维度 | A 技术分层 | **B 业务分包** | C Maven 多模块 | D 六边形 |
|------|------|------|------|------|
| 日常改动成本 | 差（跨 5 包） | **好**（收敛在一包） | 好 | 差（4 类 + 2 次转换） |
| 新增功能成本 | 低 | **低** | 中（建模块 + 改 pom） | 高 |
| 边界强制力 | **无** | 中（需外挂校验） | **强**（编译期） | 中 |
| 可拆分性 | 差 | **好** | 最好 | 好 |
| 一人可承受度 | 好 | **好** | 中（持续付税） | 差 |
| 与已定六模块的契合 | 冲突 | **一致** | 一致 | 一致但过重 |

> **结论：方案 B + 机器校验强制边界。** C 作为升级路径（迁移是机械的），D 的思想在运行时模块里局部借用。

## 四、倾向方案的落地形态

### 4.1 目录骨架

    ├── HifyApplication.java

★ 标记的四处是**预期会被替换的实现点**（见第七节）。

### 4.2 模块依赖方向

模块分三类，依赖是单向 DAG，不允许成环：

```
   ┌──────────────┐        ┌──────────────┐
   │     chat     │        │   workflow   │     ── 编排模块（消费能力）
   └──────┬───────┘        └──────┬───────┘
          │   ┌───────────────────┘
          ▼   ▼
   ┌──────────────┬──────────────┬──────────────┐
   │    agent     │  knowledge   │     tool     │  ── 配置 / 能力模块
   └──────────────┴──────┬───────┴──────────────┘
                         │ (仅向量化)
                         ▼
                  ┌──────────────┐
                  │   provider   │              ── 能力模块（最底层）
                  └──────┬───────┘
                         ▼
                  ┌──────────────┐
                  │ infra common │              ── 谁都能依赖，不依赖业务模块
                  └──────────────┘
```

| 规则 | 说明 |
|------|------|
| 编排 → 配置 / 能力 | ✅ 允许。`chat` 可依赖 `agent` / `provider` / `knowledge` / `tool` 的 `api` 包。 |
| 能力 → 编排 | ❌ **绝对禁止**。`provider` 依赖 `chat` 就说明抽象反了。 |
| 能力 ↔ 能力 | ⚠️ 默认禁止，**例外须显式声明**。一期唯一例外：`knowledge → provider`（向量化要调 embedding 模型）。 |
| `chat` ↔ `workflow` | ❌ 禁止互依赖。将来 workflow 要产出对话消息，走 `chat.api` 单向或 Spring 事件，不允许反向。 |
| 任何模块 → `common` / `infra` | ✅ 允许。反向 ❌ 禁止。 |

### 4.3 模块内部：`api` 与 `internal`

**`api` 包放什么**：其他模块调用本模块所需的接口 + 入参出参对象。

**关键一条：`api` 里的接口按调用方需求裁剪，不是内部 Service 的复制。** 例如 `chat` 只需要「按 id 拿 Agent 的完整配置」，那么：

```java
// agent/api/AgentQueryService.java —— 对外只有这一个方法
public interface AgentQueryService {
    /** 按 id 查 Agent 运行时配置，供对话与工作流编排使用 */
    AgentConfig getConfig(Long agentId);
}
```

而 `agent` 内部的增删改查、启用停用、配置校验，全在 `internal.service` 里，对外不可见。**`api` 包越薄，将来越好拆。**

**`internal` 包放什么**：Controller、Service 实现、Mapper、Entity、以及本模块专属的一切。

跨模块调用就是普通的构造器注入，同步调用，不引事件、不引 MQ：

```java
@Service
@RequiredArgsConstructor
public class ChatRuntime {
    private final AgentQueryService agentQueryService;   // agent.api
    private final ChatModelClientFactory clientFactory;  // provider.api
    private final RetrievalService retrievalService;     // knowledge.api
    private final ToolExecutor toolExecutor;             // tool.api
}
```

> **只有一种情况用 Spring 事件**：主流程不该被它拖慢、也不该被它失败影响的旁路（用量统计、审计日志）。一个人开发时，事件把调用链变成隐式的，排障要靠全局搜事件类型——**能同步调用就别发事件**。

### 4.4 边界强制力：谁来管

单 Maven 模块下，语言层面挡不住乱引用。一个人赶进度时，「就这一次直接注入对方 Mapper」一定会发生。所以**必须有机器管**。两个选项：

| | ArchUnit | Spring Modulith |
|---|---|---|
| 引入成本 | 一个 test 依赖 + 自己写约 30–50 行规则 | 一个 starter + 每模块一个 `package-info.java` |
| 校验方式 | 跑 `mvn test` | 一行 `ApplicationModules.of(HifyApplication.class).verify()` |
| 规则维护 | 规则是自己的代码，随项目演进要自己改 | 依赖规则由框架实现，只维护声明 |
| 表达能力 | 任意（包依赖、命名约定、注解、层次） | 模块依赖与封装为主，其它规则表达不了 |
| 额外收益 | 无 | 自动生成模块依赖图（PlantUML）与文档；`@ApplicationModuleTest` 模块级切片测试；事件外部化能力 |
| 束缚 | 无，包结构随便 | 要求「模块 = 主包下的直接子包」，开放子包须 `@NamedInterface` |

**倾向：引 Spring Modulith 为主。** 三条理由：

1. 一行 `verify()` 覆盖最重要的那条规则，**一个人最缺的是维护规则的精力**；
2. 它逼你在第一天就把 `api` / `internal` 的边界想清楚，这恰好是「将来能拆」的唯一前提；
3. 自动生成的模块依赖图可直接进架构文档，省一次手画。

它要求的包结构（模块 = `com.hify` 下的直接子包，`api` 用 `@NamedInterface` 开放）与 4.1 的骨架天然一致，**几乎是零额外改造**。

```java
// provider/package-info.java
@org.springframework.modulith.ApplicationModule(
        displayName = "模型提供商",
        allowedDependencies = {"common", "infra"}   // 显式声明，超出即校验失败
)
package com.hify.provider;
```

```java
// provider/api/package-info.java
@org.springframework.modulith.NamedInterface("api")
package com.hify.provider.api;
```

**补充 ArchUnit 写 Modulith 表达不了的规则**（约 20 行即可），例如：`web` 包的类不许注入任何 `*Mapper`；`internal` 包不许被 `api` 包引用；Service 方法上不许出现跨模块的 `@Transactional` 传播（见 5.1）。

**不引任何校验、纯靠自觉** 的选项也存在，但对一人长期项目不成立：约定唯一的执行者是赶进度时的你自己。

## 五、比包结构更重要的四条硬规矩

包结构决定「找东西方不方便」，下面四条决定「将来拆不拆得动」。**`CLAUDE.md` 已有的三条（不直连对方 Mapper、不跨模块 JOIN、状态外置）仍然有效，这里补四条同等重要的。**

### 5.1 跨模块调用不共享事务

`chat` 调用 `knowledge` 时，两者若在同一个事务里，数据库层就把它们焊死了——将来 `knowledge` 搬走，事务边界立刻断裂，且断裂时是**运行期的数据不一致**，不是编译错误。

规矩：**跨模块调用，被调方自己管事务；调用方不指望对方能被自己回滚。**

写代码时的具体形态：模块 `api` 的方法要么是只读查询，要么自身是完整的事务单元（内部 `@Transactional`）。跨模块的写操作若需要「一起成功或一起失败」，说明模块划分错了，应该合并到一个模块，而不是靠共享事务粘起来。

### 5.2 跨模块引用只用 ID，不用外键、不用对象引用

`chat` 的 `conversation` 表存 `agent_id`（一个 `bigint`），**不建指向 `agent` 表的外键约束**，Entity 里也不放 `Agent` 对象字段。

理由：外键是数据库层面的跨模块耦合，拆库时要先删外键、再补一致性逻辑；对象引用则会诱导出跨模块 JOIN 和延迟加载。用 ID + 需要时调 `api` 查，成本是每次多一次查询——**3–5 QPS 下这个成本是零，几千人时这一次查询也走缓存**。

### 5.3 只有一个使用方的抽象，放在使用方模块里

反过度抽象。典型的错误是把 `VectorStore` 接口提到 `infra` 里——它只有 `knowledge` 用，提出去只会让 knowledge 的核心逻辑漏在模块外面，还给人「这是个公共设施，谁都能用」的错误暗示。

判据：**接口放在它唯一使用方的模块内部；出现第二个使用方时再上移。**

按这条判，一期 `infra` 只应该有三样东西：`FileStorage`（knowledge 上传要用，将来别处也会用）、`crypto`（API Key 加解密，provider 和 tool 都要用）、全局 `config`。**如果 `infra` 长到第四第五个包，基本可以确定是在提前抽象。**

### 5.4 `chat` 与 `workflow` 共享的是能力接口，不是编排逻辑

这是本项目最容易走偏的一处。`chat` 和 `workflow` 都要「调模型 / 查知识库 / 调工具」，看起来该统一——甚至可以把「一轮对话」实现成一条固定的工作流。

**一期明确不这么做。** 共享下沉到能力接口层（`ChatModelClient` / `RetrievalService` / `ToolExecutor` 三个 `api` 接口两边都调，绝不各写一份），但**编排逻辑允许各有一套**：`chat.internal.runtime` 和 `workflow.internal.executor` 是两份代码。

理由：把 chat 实现成 workflow 的特例，会让 chat 这条主链路（SSE 流式、工具调用循环、上下文裁剪）背上图执行引擎的全部复杂度，而 chat 是使用频率最高、最需要保持简单的一条路。**重复两百行编排代码，换主链路可读，这笔交易在一人项目里划算。**

## 六、分级设计：不是所有模块都值得同一套结构

一刀切是方案 D 的失败之处。Hify 六个模块的性质差别很大，内部结构应当分级：

| 模块 | 性质 | 内部结构 | 要不要独立领域对象 |
|------|------|------|------|
| **provider** | 配置 CRUD + 客户端工厂 | **薄**：`web → service → mapper`，Entity 直接用 | 否（客户端实现除外） |
| **agent** | 纯配置 CRUD | **薄** | 否 |
| **tool** | MCP 配置 CRUD + 调用运行时 | **混合**：管理面薄；`mcp/` 包独立 | 部分（`ToolSpec` / `ToolResult`） |
| **knowledge** | CRUD + 有真逻辑的处理链 | **混合**：管理面薄；`pipeline/` + `vector/` 独立 | 是（`Segment` / `Embedding`） |
| **chat** | 运行时为主 | **厚**：持久化薄，`runtime/` + `sse/` 独立 | 是（`ChatContext` / `Message`） |
| **workflow** | 运行时为主 | **厚**：`definition/` + `executor/` 独立 | 是（`Graph` / `Node` / `NodeContext`） |

**薄模块的具体含义**：Controller 收 Request DTO，Service 直接操作 Entity，Mapper 落库，返回 Response DTO。**两层对象（DTO + Entity），中间不造第三种。** provider 和 agent 的管理面加起来大概二十来个接口，全是这个形状，套任何更重的结构都是纯亏。

**厚模块的具体含义**：持久化那部分仍然是薄的两层；但业务逻辑跑在独立的领域对象上，外部依赖走接口。以 workflow 为例：

```java
/** 节点执行器：新增节点类型只需加一个实现，不改主流程 */
public interface NodeExecutor {
    String nodeType();                            // "llm" / "retrieval" / "tool" / "condition"
    NodeResult execute(Node node, NodeContext ctx);
}
```

Spring 把全部实现注入成 `Map<String, NodeExecutor>`，图执行器按 `nodeType` 分派。新增节点类型 = 加一个类，主流程零改动。

## 七、50 人 → 几千人：真正要改的地方

### 7.1 容量推演

按 3000 注册用户、内部工具类平台日活率 30%、峰值同时在线 15% 估算（**均为估算，用于定位瓶颈的量级，不是承诺指标**）：

| 指标 | 一期 50 人 | 推演 3000 人 | 变化 |
|------|------|------|------|
| DAU | ~40 | ~900 | 22× |
| 峰值并发对话（SSE 长连接） | 3–5 | 100–150 | 30× |
| 峰值 QPS（含管理面） | 3–5 | 20–50 | 10× |
| 知识库分段总量 | 几百–几千 | 10 万–100 万 | 100×+ |
| 消息表年增量 | 十万级 | 千万级 | 100× |

### 7.2 到时候要动什么

| # | 要改的地方 | 为什么 | 改动范围 | 触发阈值 |
|---|------|------|------|------|
| 1 | **向量检索换实现**：`InMemoryVectorStore` → Qdrant / Chroma | 1536 维 float 约 6KB/条，10 万条常驻 600MB，内存暴力算不动。**这是最先崩的一环。** | `knowledge/internal/vector/` **一个包**，换一个 `VectorStore` 实现类 | 分段数 > 2 万（已在 `CLAUDE.md` 待定项记录） |
| 2 | **上游 LLM 的 HTTP 客户端换非阻塞** | 150 条并发 SSE，若上游用阻塞式客户端就是 150 个线程挂在那儿等 token | `provider/internal/client/` **一个包** | 峰值并发 SSE > 50 |
| 3 | **JVM 堆 + SSE 线程池参数** | `-Xmx512m` 撑不住；线程池 core 16 / max 64 不够 | 配置文件，零代码 | 同上 |
| 4 | **消息表归档 / 分区** | 千万级行的会话历史查询会拖慢 | `chat/internal/mapper` + 一个归档任务 | 消息表 > 500 万行 |
| 5 | **多实例 + Nginx 负载均衡** | 单实例 CPU / 连接数到顶 | 部署形态，零代码（前提：状态已外置） | 单实例 CPU 持续 > 70% |

**五项里只有 1、2 涉及代码，且各自封闭在一个包内。** 这就是「代码组织为扩容留的口子」的全部内容——不是模块化本身让系统能扩，而是模块化让这两处替换不会外溢。

### 7.3 顺带澄清一个常被误判的点

> **多实例部署下，SSE 不需要跨实例广播，也不需要粘性会话。**

Hify 的 SSE 是「一次请求 → 流式返回这次请求的结果」，整条流的生命周期在**同一个 HTTP 连接、同一个实例**内，天然不跨实例。只要会话上下文外置到 Redis / MySQL（`CLAUDE.md` 已定「状态外置」），加实例就是改 Nginx upstream，代码一行不动。

唯一的例外是**工作流做成异步执行**（提交任务 → 另开通道订阅进度）。那时才需要任务表 + 跨实例通知。→ 记入待定项。

## 八、什么时候该升级到方案 C（Maven 多模块）

不是「以后一定要升」，而是出现下列信号时再升。**没出现就不要升。**

| 触发信号 | 说明 |
|------|------|
| Modulith / ArchUnit 校验**开始被频繁绕过或注释掉** | 说明约定强制力不够了，需要编译期硬约束 |
| 某个模块要被**独立部署或独立发版** | 例如 knowledge 的文档处理要单独扩容 |
| 有**第二个人**加入 | 包边界靠自觉在多人下失效更快 |
| 单模块编译时间显著变长 | 多模块的增量编译反而更快（此项在几万行以内基本不会触发） |

**迁移成本**：B → C 是机械迁移——`com/hify/provider/` 整个目录变成 `hify-provider/src/main/java/com/hify/provider/`，加一个 pom，把 `allowedDependencies` 的声明翻译成 pom 依赖。**代码不用重写**，因为 B 阶段已经保证了依赖方向正确、`api` / `internal` 分离、无跨模块 JOIN 与共享事务。

> 这正是「先做 B」的底气：B 不是 C 的将就版本，B 是 C 的前置状态。

## 九、配套约定（实操细节）

| 项 | 约定 | 理由 |
|---|------|------|
| **Maven 结构** | 一期单模块 | 见第八节 |
| **Mapper 扫描** | `@MapperScan("com.hify.*.internal.mapper")` | 通配即可覆盖全部模块，新增模块零配置 |
| **Flyway 脚本** | 按模块分目录 `db/migration/{module}/`，版本号用**时间戳式** `V20260810_01__xxx.sql` | 分目录使模块搬走时脚本能一起搬；时间戳版本号避免多目录下版本冲突（Flyway 要求版本号全局唯一） |
| **表命名** | 模块前缀，如 `kb_document` / `chat_message` / `wf_definition` | 一眼看出归属；拆库时按前缀筛 |
| **DTO 层次** | 薄模块两层（Request/Response + Entity）；厚模块三层（+ 领域对象） | 见第六节 |
| **对象转换** | 薄模块手写或 MapStruct 均可；不为二十来个接口引框架也合理 | 一人项目，少一个依赖是少一个坑 |
| **配置项** | 各模块配置类放自己 `internal`，前缀 `hify.{module}.*` | 配置也归模块所有 |

## 十、一句话结论

> **按业务模块分包（`provider` / `agent` / `chat` / `knowledge` / `tool` / `workflow`），每模块 `api` 对外、`internal` 对内，单 Maven 模块起步，用 Spring Modulith 一行 `verify()` 把边界交给机器管。**
> **真正决定「将来拆不拆得动」的不是包结构，是四条硬规矩：跨模块不共享事务、只用 ID 不用外键、只有一个使用方的抽象不上移、共享能力接口而不共享编排逻辑。**
> **从 50 人到几千人，代码组织不需要改——要改的是向量存储实现、上游 HTTP 客户端、以及一堆配置参数。**

## 十一、待定项

| # | 待定项 | 说明 | 倾向 |
|---|--------|------|------|
| 1 | **引不引 Spring Modulith** | 备选：ArchUnit 自写规则 / 纯人肉约定。Modulith 会约束包结构，早期结构还在动时可能嫌烦 | 倾向引，理由见 4.4；若嫌束缚则退回 ArchUnit，**但不接受「纯靠自觉」** |
| 2 | **工作流是否异步执行** | 同步执行则多实例零成本；异步则需任务表 + 跨实例通知，影响 7.3 的结论 | 倾向一期同步执行 |
| 3 | **`chat` 与 `workflow` 编排逻辑最终是否合并** | 5.4 决定一期不合并；若 workflow 节点集持续扩张而 chat 链路稳定，可能长期都不合并 | 一期不合并，不预留合并接口 |
| 4 | **是否引 MapStruct** | 薄模块的 DTO ↔ Entity 转换 | 待定，手写也可接受 |
| 5 | **审计日志 / 用量统计走同步还是 Spring 事件** | 这是 4.3 里「事件」的唯一候选场景 | 倾向事件（`@TransactionalEventListener`），但仅限这一处 |
