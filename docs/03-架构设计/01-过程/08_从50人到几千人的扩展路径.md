## 〇、两个前置结论

### 结论一：从 50 到几千，代码组织一行都不用改

整条演进路径上要动的东西，归成五类：

| 类别 | 具体 | 是否动业务代码 |
|---|---|:---:|
| ① 副本数 | 应用 1 → 2 → 4 | ❌ |
| ② 参数 | 线程池、JVM 堆、连接池、容器配额 | ❌ |
| ③ **两个实现类** | 上游 HTTP 客户端换非阻塞；（向量存储已在一期用 pgvector 解决） | ✅ 但**各自封闭在一个包内** |
| ④ 数据治理 | 建索引、归档、分区 | ❌（SQL 与运维） |
| ⑤ 最后一步 | 拆出一个模块成独立服务 | ✅ 搬目录，不重写 |

**七个模块的划分、`service` 接口契约、四条硬规矩（不共享事务 / 不跨模块 JOIN / 只存 ID 不建外键 / 状态外置）——全程不变。** 这正是模块化单体在一期付出的那点代价所换的东西。

### 结论二：按指标触发，不按人数触发

**人数是果，不是因。** 3000 人轻度使用（每人每天两轮对话）的压力，可能小于 500 人重度使用（每人每天五十轮、大量文档导入）。

所以每个阶段的触发条件都写成**可观测指标**，人数只作为量级参考。**指标先越线的阶段先做，阶段之间不强制按编号顺序。**

| 阶段 | 参考人数 | 主触发指标 |
|:--:|---:|---|
| S1 | ~200 | 发版中断不可接受 **或** 峰值并发 SSE > 20 |
| S2 | ~500 | 分段数 > 1 万 **或** 向量检索 P95 > 200ms |
| S3 | ~1000 | 峰值并发 SSE > 50 |
| S4 | ~2000 | `chat_message` > 500 万行 **或** MySQL CPU 持续 > 70% |
| S5 | ~3000+ | 某模块需要独立的扩容或发版节奏 |

> **典型的顺序颠倒**：如果知识库是主要用法（大量文档、高频检索），S2 会在 S1 之前触发。别按编号做。

## 一、演进全景

```
S0  现状 · 50 人
    Nginx×1  App×1  MySQL×1  Redis×1  pgvector×1        [无索引 · 单副本]
                    │
      触发:发版中断不可接受 / 并发SSE>20
                    ▼
S1  ~200 人 · 应用无状态化 + 双副本                        [约 3–5 人天]
    Nginx×2  App×2   ← 前提:文件存储去本地化、定时任务外置、缓存全走 Redis
                    │
      触发:分段数>1万 / 检索P95>200ms
                    ▼
S2  ~500 人 · 向量层加固                                   [约 2–3 人天]
    pgvector 建 HNSW + 内存 512Mi→2Gi + embedding 降维 512
                    │
      触发:峰值并发 SSE > 50
                    ▼
S3  ~1000 人 · 上游非阻塞 + 纵向扩容                        [约 5–8 人天]
    provider/client 换 sendAsync   App×4   堆 512Mi→2Gi
                    │
      触发:消息表>500万行 / MySQL CPU>70%
                    ▼
S4  ~2000 人 · 数据治理 + 任务异步化                        [约 8–12 人天]
    消息归档  ·  任务表(非 MQ)  ·  Redis 主从
                    │
      触发:某模块需要独立扩容或发版节奏
                    ▼
S5  ~3000+ 人 · 拆出 knowledge（不是 chat）                 [约 10–15 人天]
    App(chat+其余)   knowledge-service   ← 大概率只拆这一个
```

**累计约 30–45 人天，分摊在两三年里。** 单看任何一步都不大——这是分阶段的全部意义。

## 二、S1（~200 人）：应用无状态化 + 双副本

### 触发条件

| 指标 | 阈值 |
|---|---|
| **发版中断的容忍度** | 用户开始抱怨「又在维护」 |
| 峰值并发 SSE | > 20 |
| 单副本 CPU | 持续 > 60% |

> **S1 的真实触发条件通常不是性能，是发版中断。** 50 人时一天中断两次没人在意；200 人时每次中断都有人正在对话被打断。**这一步是为可用性做的，不是为性能。** 承认这一点能避免"性能还够啊为什么要动"的困惑。

### 改什么

**⚠️ 真正的工作量不是把副本数从 1 改成 2（那是一行 YAML），是把应用变成真无状态。四项前置改造，缺一个都会出诡异 bug：**

| # | 前置改造 | 不做会怎样 |
|:--:|---|---|
| 1 | **文件存储去本地化**：TXT 内容存 MySQL（或上对象存储） | 用户在副本 A 上传、副本 B 读不到。**且 RWO PVC 会让滚动更新死锁**（新 Pod 挂不上卷，旧 Pod 等新 Pod Ready） |
| 2 | **定时任务外置**：应用内 `@Scheduled` → **K8s CronJob** | ⚠️ **多副本下每个定时任务跑 N 遍**。清理孤儿向量的任务跑两次还好，将来若有发通知/结算类任务就是事故。（不想改代码可用 ShedLock，但对一个人来说 CronJob 更简单） |
| 3 | **缓存全部走 Redis**：清掉所有进程内 `ConcurrentHashMap` 缓存 | 副本间缓存不一致——改了 Agent 配置，刷新页面时好时坏，极难排查 |
| 4 | **MCP 工具清单兜底缓存移到 Redis** | 同上 |

改完之后：

```yaml
spec:
  replicas: 2
  strategy:
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # 先起新再停旧
```

**其余调整：**
- Nginx 副本 1 → 2（纯静态无状态，随便加）
- `llm-chat` 线程池 core 32 → 48（单副本 max 64 × 2 = 128 总容量）
- **检查 MySQL `max_connections`**：默认 151。2 副本 × HikariCP 池 20 = 40，安全；但这个乘法要养成习惯，S3 加到 4 副本时会撞。

**Flyway 并发**：两副本同时启动会争 `flyway_schema_history` 的锁，后者等待——不会出错，但迁移慢时第二个副本可能启动超时。确保 `startupProbe.failureThreshold` 留足。

### 不改什么

| 不改 | 为什么 |
|---|---|
| 数据库全部单实例 | 3–5 QPS × 4 倍 = 20 QPS，MySQL 单实例余量仍是百倍 |
| pgvector 仍不建索引 | 分段数没到 1 万 |
| 不引 MQ / 不引服务注册 | 两个副本靠 K8s Service 就能互相不知道对方存在 |
| **不拆服务** | 没有任何模块需要独立扩容 |
| 不引 WebFlux | 真正的上限是业务线程池，不是 Web 层 |

### 成本

**约 3–5 人天**，其中 3 天在第 1 项（文件存储改造 + 数据迁移）。

> **这就是一期为什么应该直接把 TXT 存数据库**（`04` 基准第五节已提示）。一期做是零成本；S1 才做要连带迁移已有文档。

## 三、S2（~500 人）：向量层加固

### 触发条件

**两个指标谁先到算谁：**

| 指标 | 阈值 | 怎么测 |
|---|---|---|
| **分段数** | > 1 万 | `SELECT count(*) FROM kb_segment_vector` |
| **表体积 vs shared_buffers** | 表 > `shared_buffers` 的一半 | `pg_total_relation_size` |
| 向量检索 P95 | > 200ms | 检索方法日志 |

**换算成业务量**：1 万条分段 ≈ 500 万字 ≈ **250 篇 2 万字文档**。500 人的知识库到这个量不需要很久。

**⚠️ 这里有个断崖，不是缓慢劣化**：一旦表体积超过 `shared_buffers`（默认 128MB），每次检索从内存扫变成磁盘 IO，**耗时从毫秒跳到秒级**。所以监控要盯表体积，不能等用户投诉。

### 改什么

**1. 加内存，再建索引——顺序不能反**

```
pgvector 容器:  512Mi → 2Gi
shared_buffers: 128MB → 512MB
```

**⚠️ 先加内存的原因**：构建 HNSW 需要 `maintenance_work_mem`（默认仅 64MB）。在 512Mi 容器里对几万条 1536 维向量建索引**很可能直接 OOM**。

```sql
SET maintenance_work_mem = '512MB';
CREATE INDEX CONCURRENTLY ON kb_segment_vector USING hnsw (embedding vector_cosine_ops);
```

用 `CONCURRENTLY` 避免锁表——但它更慢，且**必须安排维护窗口**。建索引不是"执行一条 SQL"。

**2. embedding 降维（如果一期没做）**

`text-embedding-3-small` 的 `dimensions=512`：存储、内存、距离计算全部降到 **1/3**。

⚠️ **降维要重算全部历史向量**——维度变了旧向量不可用。到 S2 才做意味着要重跑一遍全量 embedding（几万次调用，有真实费用）。**一期就定 512 维能省掉这次返工。**

**3. 上下文裁剪（如果一期没做）**

到这个规模，长会话已经在批量报 400。系统提示 + 最近 10 轮 + 本轮 RAG，**RAG 结果不进历史**。

**4. topK 上限收紧到 5**，直接乘进 TPM 消耗。

### 不改什么

| 不改 | 为什么 |
|---|---|
| 不换专用向量库（Qdrant / Milvus） | pgvector + HNSW 到百万级分段都够。换向量库多一个要运维的组件，且检索质量提升有限 |
| 不做向量分片 | 单实例够 |
| MySQL 仍单实例 | 没到瓶颈 |
| 应用副本仍 2 | 检索变快之后线程占用反而降低 |

### 成本

**约 2–3 人天**（含一次维护窗口）。若还要补降维和上下文裁剪，加 3–4 天。

## 四、S3（~1000 人）：上游非阻塞 + 纵向扩容

### 触发条件

| 指标 | 阈值 |
|---|---|
| **峰值并发 SSE** | > 50（接近 `llm-chat` 单副本 max 64） |
| `llm-chat` 活跃线程数 | 持续 > 40 |
| 线程池拒绝次数 | 每天 > 0 |

**⚠️ 用「等效并发」判断，不是在线人数。** 一次调 3 个工具的对话 = 4 次 LLM 请求 ≈ **4 倍线程占用时长**。重度工具场景下「峰值并发 15」就等效于 60 条普通对话——64 的池子已经在边缘。

### 改什么

**1. 上游 HTTP 客户端换非阻塞（这一步是关键，能把 64 提到几百）**

```java
// 现在:同步读流,业务线程整轮阻塞在 read()
// 改成:IO 线程回调驱动,不占用业务线程池
httpClient.sendAsync(request, HttpResponse.BodyHandlers.fromLineSubscriber(
        new SseLineSubscriber(emitter, timeoutConfig)));
```

**改动范围只有 `hify-provider` 的 `client` 包一个包**——Controller 不动、Spring MVC 不动、MyBatis-Plus 不动。这正是一期把 `client` 包做成「只依赖方法入参、不注入 Mapper」的兑现点。

代价：编排代码变回调式，可读性下降。所以不是现在做，是并发真上去了再做。

**2. 纵向扩容**

| 项 | 现在 | S3 |
|---|---|---|
| 容器内存 | 1Gi | **4Gi** |
| JVM 堆 | `MaxRAMPercentage=50` → 512Mi | 同参数 → **2Gi**（不用改代码） |
| 应用副本 | 2 | **4** |
| `llm-chat` | 32/64/16 | 48/96/16 |

> `MaxRAMPercentage` 的价值在这一步兑现：改容器配额，JVM 自动跟随，不会漏改。

**3. ⚠️ 必须同时算一遍数据库连接数**

```
4 副本 × HikariCP 池 20 = 80 连接
+ 备份任务、运维连接 ≈ 90
MySQL 默认 max_connections = 151        ← 撑得住,但已经过半
```

**这是多副本扩容最容易漏的一步。** 要么调大 `max_connections` 到 300，要么把每副本池调小到 10——**后者更好**：3–5 QPS 下每副本 10 个连接绰绰有余，池子大只是浪费。

**4. Nginx 副本 2 → 3**（成本极低，顺手）

### 不改什么

| 不改 | 为什么 |
|---|---|
| **不引 WebFlux** | 第 1 项已经拿到了非阻塞的全部收益，且不用换掉 MyBatis-Plus。WebFlux 要求全链路非阻塞，代价是推翻技术选型 |
| MySQL 不做读写分离 | 20–50 QPS 对单实例仍是零压力 |
| 不拆服务 | 仍然没有模块需要独立扩容 |
| 不引 MQ | 没有需要削峰的写入 |

### 成本

**约 5–8 人天**，主要在第 1 项的回调式改造与回归测试。

## 五、S4（~2000 人）：数据治理 + 任务异步化

### 触发条件

| 指标 | 阈值 |
|---|---|
| `chat_message` 行数 | > 500 万 |
| MySQL CPU | 持续 > 70% |
| 慢查询（> 1s） | 每天 > 100 条 |
| 文档导入挤占对话 | `kb-index` 队列持续积压 |

**行数推算**：2000 人 × 每天 10 轮 × 2 条 = 4 万条/天 ≈ **1460 万条/年**。S4 会在这个规模下的第 4–5 个月触发。

### 改什么

**1. 消息表归档**

两个方案，按运维能力选：

| | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 冷热分离：`chat_message` 只留最近 3 个月，更早的搬到 `chat_message_archive`，每日 CronJob 搬运 | 简单、可回滚、查历史时前端明确切换 |
| B | MySQL 原生分区（按 `create_time` 月分区） | 对应用透明，但分区键必须进主键，改表结构；且 8.0 分区表有若干限制 |

**2. 文档处理异步化——用任务表，不要引 MQ**

现状是进程内线程池，多副本下有两个问题：任务不持久（Pod 重启丢失）、无法跨副本调度。

**直接引 MQ 是过度反应。用数据库当队列就够：**

```sql
CREATE TABLE kb_index_task (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    document_id BIGINT NOT NULL,
    status TINYINT NOT NULL,          -- 0待处理 1处理中 2成功 3失败
    retry_count INT NOT NULL DEFAULT 0,
    lock_owner VARCHAR(64),           -- Pod 名,便于排查
    lock_expire_at DATETIME,          -- 防止 Pod 崩溃后任务永久锁死
    KEY idx_status (status, id)
);
```

```sql
-- 多副本安全抢占:跳过已被锁的行,不阻塞
SELECT * FROM kb_index_task
WHERE status = 0 ORDER BY id LIMIT 5
FOR UPDATE SKIP LOCKED;
```

**为什么不引 MQ**：RabbitMQ/Kafka 各自是一个要监控、要备份、要处理堆积的组件。当前的量（每天几百个文档任务）用数据库队列完全够，且**任务状态天然可查、可重试、可在管理界面展示进度**——用 MQ 反而要另建一张状态表。

**真正需要 MQ 的信号**：任务量 > 每秒几十个，或需要多个消费者组。到那时再引也不迟——`kb_index_task` 表的接口形态与 MQ 消费者是同构的。

**3. Redis 单实例 → 主从 + 哨兵**

这一项是**可用性**不是性能——Redis 挂了会导致缓存全失效瞬间打穿 MySQL。

**4. MySQL 加一个从库**

先只用于**备份与报表**，不做读写分离。读写分离要处理主从延迟带来的「刚写完读不到」，收益不抵复杂度。

### 不改什么

| 不改 | 为什么 |
|---|---|
| **不做读写分离** | 20–50 QPS 下主库完全够；主从延迟的坑不值得踩 |
| 不分库分表 | 归档之后热表回到百万级 |
| **不引 MQ** | 任务表已够，见上 |
| **不拆服务** | 到这一步仍然不需要 |
| 不引 Elasticsearch | 全文检索需求未出现；出现了先试 MySQL 全文索引 |

### 成本

**约 8–12 人天**，归档与任务表各占一半。

## 六、S5（~3000+ 人）：拆出 knowledge，不是 chat

### 触发条件

**注意：触发条件不是「人多了」，而是「某个模块需要与其它模块不同的节奏」。**

| 信号 | 说明 |
|---|---|
| **某模块需要独立扩容** | 文档批量导入时需要临时开 10 个实例，而对话实例只要 4 个 |
| **某模块需要独立发版** | 知识库策略调优频繁，不想每次都重启对话服务 |
| **某模块需要不同机型** | 向量化是 CPU 密集，可能需要高主频机型；对话是 IO 密集 |
| **有第二个人加入** | 两人并行开发时模块边界靠自觉会更快失效 |

### 为什么第一个拆的是 knowledge

这与直觉相反——大多数人会先想拆 chat（"它最重要、流量最大"）。**但 chat 大概率永远不用拆：**

| | chat | knowledge |
|---|---|---|
| 瓶颈性质 | LLM 长连接数（IO 等待） | 文档解析 + 向量化（**CPU 密集**） |
| 扩容方式 | 加实例即可，线性有效 | 同左，但**与对话争抢的是 CPU 而非连接** |
| 负载形态 | 平稳（跟人数走） | **突发**（批量导入时 10 倍尖峰） |
| 发版节奏 | 稳定 | 分块策略、检索参数调优频繁 |
| 是否被别的模块依赖 | ❌ `chat` 的对外契约为空 | ✅ 被 `chat` / `workflow` 依赖 |

**决定性的是「负载形态」那一行**：knowledge 的突发负载会周期性挤占对话资源，而两者的扩容曲线完全不同。chat 的负载平稳、加实例就行，**没有任何拆分动机**。

（`03_拆分hify-chat的改动量评估.md` 算过拆 chat 的成本是 8–12 人天，结论也是"改动不大，但大概率不需要拆"。）

### 改什么

1. `hify-knowledge` 移出 reactor，加启动类与 `spring-boot-maven-plugin`；
2. `chat` / `workflow` 注入的 `RetrievalService` 从本地实现换成 **HTTP 实现**——**接口签名一个字不改**；
3. `knowledge` 与主应用**共用同一套 MySQL + pgvector**（拆服务不必拆库，这是省下的最大一块）；
4. 服务间认证：内部共享密钥；
5. 部署：多一个 Deployment，可独立配副本数与机型。

**代码几乎零重写**——因为一期就定好了：不共享事务、不跨模块 JOIN、只存 ID 不建外键、`api` 契约裁剪过。**这些规矩在这一步一次性兑现。**

### 不改什么

| 不改 | 为什么 |
|---|---|
| **不拆 chat** | 见上 |
| **不拆库** | 拆服务 ≠ 拆库。共用数据库省掉一整套数据同步 |
| 不引服务注册发现 | K8s Service + DNS 就是服务发现 |
| 不引 RPC 框架 | 两个 HTTP 接口，用 `RestClient` |
| 不引网关 | Nginx 加一条 location 即可 |
| 不引分布式链路追踪 | 两个服务，日志带同一个 traceId 够用 |

### 成本

**约 10–15 人天**，含联调与失败注入测试。

## 七、贯穿全程的「永远不改」

无论走到哪一阶段，下面这些都不变——它们是这套架构能平滑演进的原因，动了就等于重来：

| 永远不改 | 理由 |
|---|---|
| **七个模块的划分** | 边界是按业务能力划的，与规模无关 |
| **`service` 接口作为跨模块唯一契约** | S5 拆服务时，它直接变成远程接口 |
| **不共享事务** | 破了它，S5 拆分时会遇到运行期数据不一致——且不是编译错误 |
| **不跨模块 JOIN** | 破了它，S5 要重写每个 JOIN 为 API 调用 |
| **只存 ID、不建跨模块外键** | 破了它，拆库时要先删外键再补一致性逻辑 |
| **状态外置** | 破了它，S1 的多副本直接坏掉 |
| **一个进程、一个 jar**（S5 前） | 拆分是有触发条件的动作，不是默认状态 |
| **不引 WebFlux** | 收益在 S3 已由非阻塞客户端拿到，代价是推翻技术选型 |

## 八、每次扩容前的检查清单

**最贵的扩容是「扩错了地方」——加了副本，结果瓶颈在数据库。** 动手前逐条过：

| ✔ | 检查 |
|---|---|
| ☐ | **瓶颈定位有数据支撑吗？** 是哪个指标越线了，不是"感觉慢" |
| ☐ | **是不是配置问题？** 线程池、连接池、超时值先核一遍——参数改错造成的"性能问题"占比很高 |
| ☐ | **有没有更便宜的一步？** 纵向扩容（加内存/CPU）通常比横向便宜十倍 |
| ☐ | **改完怎么验证？** 先定验收指标，再动手 |
| ☐ | **多副本相关的三件事核过了吗？** 定时任务是否会重复执行、进程内缓存是否清干净、数据库连接数是否够 |
| ☐ | **能回滚吗？** 建索引、归档、拆服务都要有回退路径 |

## 九、一句话结论

> **从 50 人到几千人，五个阶段、约 30–45 人天，分摊在两三年里。代码组织一行都不用改——要改的是副本数、参数、两个实现类（上游 HTTP 客户端；向量存储已在一期用 pgvector 提前解决）、数据归档，以及最后可能拆一个模块。**
> **按指标触发，不按人数触发；阶段之间不强制按编号顺序，指标先越线的先做。**
> **两个反直觉的点：S1 的真实触发条件是发版中断而非性能（它的工作量也不在"改副本数"，而在文件存储去本地化、定时任务外置、进程内缓存清零）；S5 第一个该拆的是 knowledge 而不是 chat——因为 knowledge 是 CPU 密集且负载突发，chat 是 IO 密集且负载平稳，加实例就够。**

## 十、待定项

| # | 待定项 | 说明 | 倾向 |
|---|---|---|---|
| 1 | **一期是否直接把 TXT 存数据库** | 决定 S1 要不要做数据迁移。一期做零成本，S1 做要迁已有文档 | **一期就做** |
| 2 | **一期是否直接用 512 维 embedding** | 决定 S2 要不要重跑全量向量化（几万次调用，有真实费用） | **一期就定 512 维**，需先用真实文档验一次召回率 |

| 4 | **S4 的归档方案** | 冷热分离 vs 原生分区 | 冷热分离 |
| 5 | **是否需要写一份「等效并发」的容量换算表** | S3 的触发判断依赖它，否则按人数会低估四倍 | 并入部署基准的容量章节 |
