## 〇、四条约束（决定了下面所有关系的形态）

| 约束 | 来源 | 对表设计的含义 |
|---|---|---|
| **表名带模块前缀** | 分层基准 9.2 | `provider_*` `agent_*` `chat_*` `kb_*` `mcp_*` `wf_*` `sys_*` |

## 二、逐模块表清单

### 2.1 `provider` —— 模型提供商（2 张）

| 表 | 职责 | 量级 |
|---|---|---|
| `provider_config` | 提供商配置：类型、baseURL、API Key（密文）、状态 | 几～几十行 |
| `provider_model` | 该提供商下可用的模型：模型名、类型（chat / embedding）、上下文长度、**向量维度**、状态 | 几十行 |

**关系**：`provider_config` **1:N** `provider_model`（模块内）。

**为什么需要 `provider_model` 而不是让用户手填模型名**，三个理由：

1. Agent 配置页要有下拉列表；
2. chat 与 embedding 是两类模型，选择时必须区分；
3. **embedding 模型必须记录向量维度**——维度变了历史向量全部作废，这个信息要能查到（关联到 `05_Hify扩展路径（基准）` 待定项 2）。

### 2.2 `agent` —— Agent 定义（1 张）

| 表 | 职责 | 量级 |
|---|---|---|
| `agent_definition` | 名称、系统提示词、模型引用、模型参数、**三组绑定关系**、状态 | 几十～几百行 |

**三组绑定关系用 JSON 数组存 ID，不建关联表**（沿用分层基准 4.1 的 Entity 形态）：

| 绑定 | 存法 |
|---|---|
| 模型 | `model_id`（单值，指向 `provider_model`） |
| 知识库 | `knowledge_base_ids` JSON 数组 |
| MCP 工具 | `mcp_tool_refs` JSON 数组 |

**JSON vs 关联表的取舍：**

| | JSON 字段 | 关联表 |
|---|---|---|
| 读取 Agent 完整配置 | ✅ 一次查询 | ❌ 三次查询或 JOIN |
| **反查「哪些 Agent 用了这个知识库」** | ⚠️ `JSON_CONTAINS` 走不了索引，全表扫 | ✅ 走索引 |
| 表数量 | 1 张 | 4 张 |

**选 JSON**，因为反查的代价可算：Agent 总数在几百行以内，全表扫也是毫秒级，而反查只在「删除知识库前给影响面提示」这一个低频场景用到。

**触发改造的条件**：`agent_definition` 超过约 2000 行，或出现高频反查需求 → 改为 `agent_knowledge_base` / `agent_mcp_tool` 两张关联表。

### 2.3 `chat` —— 对话（2 张）

| 表 | 职责 | 量级 |
|---|---|---|
| `chat_conversation` | 会话：标题、`agent_id`、状态 | 万级 |
| `chat_message` | 消息：角色、内容、token 用量、**工具调用记录（JSON）** | ⚠️ **千万级/年** |

**关系**：`chat_conversation` **1:N** `chat_message`（模块内，最强的父子关系）。

**工具调用记录一期放 `chat_message` 的 JSON 字段，不单独建表。** 一轮助手回复可能包含多次工具调用，独立成 `chat_message_tool_call` 表在「按工具维度统计用量」时更方便——但一期没有这个需求，而 JSON 已经够展示和排障。触发条件：需要按工具聚合统计时再拆。

**`chat_message` 是全库唯一会到千万级的表**，两点直接影响设计：

- **必须有 `(conversation_id, id)` 复合索引**，在建表脚本里就写——查询形态只有「按会话拉最近 N 条」这一种。后期补索引要锁表（`04_Hify一期性能处置（基准）` 5.1 已定为建表规范）。
- 归档的触发条件是 500 万行，方案见 `05_Hify扩展路径（基准）`。

### 2.4 `knowledge` —— 知识库（MySQL 3 张 + pgvector 1 张）

| 表 | 库 | 职责 | 量级 |
|---|---|---|---|
| `kb_knowledge_base` | MySQL | 知识库：名称、embedding 模型引用、分块参数、状态 | 几十行 |
| `kb_document` | MySQL | 文档：文件名、大小、**处理状态**、分段数、状态 | 百～千行 |
| `kb_document_content` | MySQL | **原始文本内容**（大字段） | 与 `kb_document` 同 |
| `kb_segment_vector` | **pgvector** | 分段文本 + 向量 | ⚠️ **万～百万级** |

**关系**：

- `kb_knowledge_base` **1:N** `kb_document`（模块内）
- `kb_document` **1:1** `kb_document_content`（模块内）
- `kb_document` **1:N** `kb_segment_vector`（★ **跨库逻辑引用**）

**两个值得单独说的设计判断：**

**① 原文单独一张表，不放在 `kb_document` 里。**

原文是 `LONGTEXT` 级别的大字段。放进主表会让每次 `SELECT *` 查文档列表都把全部正文捞出来——文档列表页是高频操作，几百篇文档就是几十 MB 的无谓传输。拆成 1:1 的从表，列表查询完全不碰它。

（这条同时落实了 `05_Hify扩展路径（基准）` 待定项 1「TXT 内容存数据库」——存这里。）

**② MySQL 里不建 `kb_segment` 表，分段完全在 pgvector。**

一个自然的想法是「MySQL 存分段元数据、pgvector 只存向量」。**不这么做**：

| 方案 | 后果 |
|---|---|
| MySQL 存分段元数据 + PG 存向量 | 检索命中后还要拿着 segment_id 回 MySQL 查文本 → **每次检索多一次跨库查询**，且要维护两张表的分段级一致性 |
| **PG 存分段文本 + 向量（选这个）** | 检索一次查询就拿到可直接注入提示词的文本；**跨库一致性只需维护到 document 级别** |

分段是知识库的内部实现细节（分块参数一改，分段就全变了），没有必要在两个库里各维护一份。

**跨库一致性怎么保证**（不做分布式事务）：

1. 删文档 → `kb_document` 软删除（`status = 0`），检索时按 `document_id` 过滤；
2. 每日 CronJob 清理已软删文档对应的 `kb_segment_vector` 行；
3. 重新分块 → 先删旧向量再写新的，失败则文档状态置为「处理失败」，可重试。

### 2.5 `mcp` —— MCP 工具（2 张）

| 表 | 职责 | 量级 |
|---|---|---|
| `mcp_server` | Server 配置：名称、URL、传输方式、鉴权信息（密文）、状态 | 几～几十行 |
| `mcp_tool` | 从 Server 发现的工具清单：工具名、描述、`input_schema`、最后同步时间、状态 | 几十～几百行 |

**关系**：`mcp_server` **1:N** `mcp_tool`（模块内）。

**工具清单为什么要落库而不只放 Redis**，两个理由：

1. 既有约定要求「MCP Server 不可用时工具清单走缓存兜底」——Redis 会失效、会被清空，**数据库才是可靠的兜底层**（Redis 做一级缓存，DB 做二级兜底）；
2. Agent 绑定工具时需要一个**稳定的引用目标**。绑到一个只存在于缓存里的东西，缓存一没 Agent 配置就悬空了。

`mcp_tool` 由定时任务或手动触发从 Server 同步，同步时对已消失的工具做软删除而不是物理删除——避免 Agent 绑定悬空。

### 2.6 `workflow` —— 工作流（3 张）

| 表 | 职责 | 量级 |
|---|---|---|
| `wf_definition` | 定义：名称、**JSON 图定义**、版本号、状态 | 几十行 |
| `wf_execution` | 执行记录：`definition_id`、状态、入参、最终结果、耗时 | 千～万级 |
| `wf_node_execution` | 节点执行记录：`execution_id`、节点 id、节点类型、输入输出、耗时、状态 | 万～十万级 |

**关系**：`wf_definition` **1:N** `wf_execution` **1:N** `wf_node_execution`（均模块内）。

**`wf_node_execution` 一期就要有。** 工作流是 JSON 配置的、没有可视化编辑器——出错时如果不能定位到「卡在哪个节点、那个节点收到了什么、输出了什么」，调试基本不可能进行。**它是 JSON 工作流方案能落地的前提，不是可选的观测增强。**

**版本号的作用**：定义改了以后，历史执行记录仍要能对应到当时的定义。`wf_execution` 记录执行时的 `definition_version`，不做级联更新。

### 2.7 `sys` —— 用户（1 张）

| 表 | 职责 | 量级 |
|---|---|---|
| `sys_user` | 账号、密码哈希、角色（管理员 / 普通用户）、状态 | 几十行 |

**归属**：按分层基准第八节的新模块门槛判——它没有任何模块需要依赖（各表的 `creator_id` 从 `UserContext` 取，不需要调用户模块的接口）——所以**不新建模块，表和 CRUD 放 `hify-app`**。

**关系**：所有表通过 `creator_id` 逻辑引用它。这是全库唯一的「所有人都引用」的表，图上不画线。

依赖 `01_Hify产品决策（基准）` 待定项 2（登录与角色是否做）；若不做，这张表不建。

## 三、关系分类与一致性维护

**三类关系，维护方式完全不同：**

| 类型 | 实例 | 建外键 | 删除行为 | 一致性靠什么 |
|---|---|:---:|---|---|
| **A. 模块内父子** | `conversation→message`<br>`kb_base→document`<br>`document→content`<br>`server→tool`<br>`definition→execution→node_execution` | ❌ | 父软删除，子随查询过滤 | 应用层保证；定时任务清理孤儿 |
| **B. 跨模块逻辑引用** | `agent→provider_model`<br>`chat→agent`<br>`agent→kb_base`<br>`agent→mcp_tool` | ❌ | **只停用不物理删** | 运行时校验：`chat` 装配时发现引用失效 → 明确报错 |
| **C. 跨库引用** | `kb_document→kb_segment_vector` | ❌（跨库不可能建） | 文档软删除 + 每日清理向量 | 定时任务对账 |

### 3.1 全库不建任何外键

**分层基准只禁止了跨模块外键，这里进一步建议：模块内也不建。** 三个理由：

1. **一致性**——一半有外键一半没有，最容易出错；
2. 软删除模式下外键的约束意义本来就有限（父行不会真的消失）；
3. **二期分库时零改动**——不用先删外键。

代价是父子一致性完全靠应用层。对一个人的项目，规则统一比数据库帮你兜底更重要。

### 3.2 跨模块引用的失效处理

按分层基准 5.3，**管理面保存 Agent 时不校验绑定对象是否存在**（校验会引出 `agent → knowledge`、`agent → mcp` 两条同层依赖，违规）。失效在三处兜住：

| 时机 | 处理 |
|---|---|
| **配置时** | 前端下拉列表只列出启用中的对象，用户选不到不存在的 |
| **运行时**（`chat` 装配 Agent 配置） | 引用失效 → 明确报错「所选模型已停用，请检查 Agent 配置」 |
| **删除时** | 只停用不物理删除；需要影响面提示时由前端调 `GET /api/agents?providerId=x` 组合 |

## 四、表的量级分布（决定索引与归档策略）

| 量级 | 表 | 关注点 |
|---|---|---|
| **千万级/年** | `chat_message` | ⚠️ 建表即建 `(conversation_id, id)` 复合索引；500 万行触发归档 |
| **万～百万级** | `kb_segment_vector` | ⚠️ 1 万条触发建 HNSW 索引 + 加内存 |
| 万～十万级 | `wf_node_execution` | 需要定期清理执行记录（如保留 90 天） |
| 万级 | `chat_conversation` | `(creator_id, update_time)` 索引 |
| 千级以下 | 其余全部 | **无需任何优化** |

**只有前两张表需要在设计阶段就考虑性能，其余十几张表在可预见的未来都是「几百行的配置表」。** 不要给它们做分区、加缓存或提前优化。

## 五、一句话结论

> **15 张表：`provider` 2、`agent` 1、`chat` 2、`knowledge` 3(MySQL)+1(pgvector)、`mcp` 2、`workflow` 3、`sys` 1。**
> **关系分三类：模块内父子（5 组）、跨模块逻辑引用（4 条，只存 ID）、跨库引用（1 条）。全库不建任何外键，一致性靠软删除 + 定时清理 + 运行时校验。**
> **三个值得注意的设计判断：Agent 的绑定关系用 JSON 数组而非关联表（反查是低频操作，Agent 总数几百行）；文档原文单独一张 1:1 从表（避免列表查询捞出大字段）；MySQL 里不建分段表，分段文本与向量一起放 pgvector（检索一次查询拿到可注入的文本，跨库一致性只需维护到 document 级）。**

## 六、待定项

| # | 待定项 | 说明 | 倾向 |
|---|---|---|---|
| 1 | **是否建 `sys_user`** | 依赖产品决策待定项 2（登录与角色是否做） | 做最简登录，表放 `hify-app` |

| 5 | **是否需要 `provider_call_log`** | `04_LLM调用的线程超时重试与容错` 4.5 已定一期只打日志不建表 | 一期不建 |
| 6 | **`kb_document_content` 是否够用** | 一期只支持 TXT；支持 PDF/Word 后二进制原文要换对象存储 | 一期够用，届时换 `FileStorage` 实现 |
