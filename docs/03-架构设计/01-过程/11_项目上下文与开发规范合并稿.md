## 一、项目概述

Hify 是一个简版的 AI Agent 开发平台（参考 Dify），可本地部署，面向团队内部小规模使用（20–50 人同时在线）。

**核心约束**：一个人开发 · 本地部署 · 内部 20–50 人。
**取舍原则**：一切以「最匹配当前约束」为准，不追求技术最全。

### 1.1 做什么

- 多模型提供商管理（OpenAI、Claude、Gemini、Ollama）
- Agent 创建与配置（选模型、绑工具、设系统提示词）
- 对话引擎（流式响应、多轮对话、上下文管理）
- 知识库 + RAG（一期只支持 TXT 文档，固定长度分块）
- 简版工作流（JSON 配置，线性 + 条件分支，不做可视化拖拽）
- MCP 工具接入（Agent 可通过 MCP 协议调用外部工具）
- 管理控制台（模型管理、Agent 配置、对话界面）

### 1.2 不做什么

- 不做可视化工作流拖拽编排
- 不做多租户 / 权限体系
- 不做插件市场、计费系统
- 不做文本生成应用、WebApp 发布、嵌入组件
- 不做标注与微调

### 1.3 技术栈

| 层 | 选型 |
|---|---|
| 后端 | Spring Boot 3.x + MyBatis-Plus + MySQL 8.x + Redis 7.x |
| 向量 | PostgreSQL + pgvector |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus |
| 容器化 | Docker + K8s（生产）/ Docker Compose（本地依赖） |
| 容错 | Resilience4j（仅 circuitbreaker） |

**不引入技术栈以外的依赖。** 需要时先问，不自行添加。

### 1.4 容量目标

20–50 人同时在线，峰值 3–5 QPS，**瓶颈在 LLM 长连接，不在并发**。

## 二、架构

### 2.1 应用架构：模块化单体

**一个 Spring Boot 应用、一个进程、一个 jar，Maven 多模块组织。** 模块化只在编译期，运行时不拆。

| 模块 | 职责 |
|---|---|
| `hify-app` | 启动模块：入口、全局配置、集成测试。无业务代码 |
| `hify-provider` | 模型提供商管理 + 模型客户端 |
| `hify-agent` | Agent 定义与配置 |
| `hify-chat` | 对话引擎：SSE、上下文装配、RAG 注入、工具循环 |
| `hify-mcp` | MCP Server 配置、工具发现与调用 |
| `hify-workflow` | 工作流定义解析与执行 |
| `hify-knowledge` | 知识库：解析、分块、向量化、检索 |
| `hify-common` | 公共模块：响应体、异常、常量、工具类、加解密 |

**模块数量一期封顶 8 个。** 新增模块必须同时满足：① 有独立业务能力边界；② 至少两个已有模块要依赖它；③ 不新增会导致已有模块产生本不该有的依赖。不满足就放进已有模块的子包。

### 2.2 依赖方向：四层，只能向下

```
L4  hify-app            （聚合全部）
         ▼
L3  hify-chat / hify-workflow          编排层
         ▼
L2  hify-agent / hify-knowledge / hify-mcp    配置 / 能力层
         ▼
L1  hify-provider                       能力底座
         ▼
L0  hify-common                         公共，不依赖任何业务模块
```

| 规则 | 说明 |
|---|---|
| 只能向下依赖 | L3 → L2/L1/L0 ✅；L1 → L3 ❌（抽象反了） |
| **同层禁止** | `chat ↔ workflow` ❌、`knowledge ↔ mcp` ❌ |
| 可跳级向下 | `chat → provider` ✅ |

**各模块的 pom 依赖矩阵：**

| 模块 | 依赖 |
|---|---|
| `hify-common` | 无 |
| `hify-provider` | `common` |
| `hify-agent` | `common` |
| `hify-knowledge` | `common`, `provider`（向量化） |
| `hify-mcp` | `common` |
| `hify-chat` | `common`, `provider`, `agent`, `knowledge`, `mcp` |
| `hify-workflow` | `common`, `provider`, `knowledge`, `mcp` |
| `hify-app` | 全部 |

> 需要新依赖时先问是不是抽象反了；确认合理再改 pom **并更新本表**。

### 2.3 代码组织：扁平九包

每个业务模块内部固定为：

```
com.hify.{module}/
├── controller/        REST 接口
├── service/           业务逻辑接口 ← 同时是本模块的对外契约
├── service/impl/      业务逻辑实现
├── mapper/            MyBatis-Plus Mapper
├── entity/            数据库实体
├── dto/               请求 / 响应 / 跨模块契约对象
├── config/            配置类
├── exception/         模块级错误码
└── constant/          模块级常量
```

**厚模块可追加的专属包（白名单，不在表里的包不许建）：**

| 模块 | 追加包 | 职责 |
|---|---|---|
| `provider` | `client` | LLM HTTP 客户端：请求构造、SSE 解析、重试、错误映射 |
| `mcp` | `client` | MCP 协议客户端、工具清单发现与缓存 |
| `knowledge` | `pipeline` `vector` `storage` | 处理链 / 向量存储 / 文件存储 |
| `chat` | `sse` `runtime` `domain` | SSE 生命周期 / 对话编排 / 领域对象 |
| `workflow` | `definition` `executor` `domain` | 图解析 / 节点执行 / 领域对象 |

**为什么 `service` 必须是接口、`service/impl` 必须分开**：模块间没有 `api`/`internal` 目录隔离，`service` 接口包就是**模块边界本身**——`hify-chat` 依赖 `hify-agent` 后，只允许看到 `com.hify.agent.service` 下的接口，看不到 `service.impl`、`mapper`、`entity`。这不是分层洁癖。

### 2.4 部署架构

**生产：K8s，一期单副本。K8s 只作为部署壳。**

```
浏览器 → Nginx（静态文件 + 反代 + SSE 透传）→ Spring Boot
                                                   ├→ MySQL（业务数据）
                                                   ├→ Redis（缓存 + 会话）
                                                   ├→ pgvector（向量）
                                                   └→ 外部 LLM API（出网）
```

| 项 | 值 |
|---|---|
| 副本数 | **1**（一期） |
| 容器内存 limit | 1Gi |
| JVM | `-XX:MaxRAMPercentage=50`（→ 堆 512Mi），**不写死 `-Xmx`** |
| 本地开发 | Compose 起 MySQL/Redis/pgvector，应用在 IDE 跑 |

**用什么**：Deployment 保活、PVC 持久化、ConfigMap/Secret 管配置、`rollout undo` 回滚。
**不用什么**：多副本、HPA、Service Mesh、Helm、多环境 namespace。

## 三、编码规范

> 本节合并阿里巴巴 Java 开发手册的强制条款与项目自身约定。**标 🔴 的是红线，违反即错。**

### 3.1 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 类 | UpperCamelCase | `AgentService` |
| 方法 / 参数 / 变量 | lowerCamelCase | `getAgentConfig` |
| 常量 | 全大写下划线分隔 | `MAX_RETRY_ATTEMPTS` |
| 包 | 全小写，**单数** | `com.hify.agent.service` |
| 抽象类 | `Abstract` / `Base` 开头 | `AbstractNodeExecutor` |
| 异常类 | `Exception` 结尾 | `BizException` |
| 测试类 | 被测类名 + `Test` | `AgentServiceTest` |
| 枚举 | 类名 `Enum` 结尾，成员全大写 | `AgentStatusEnum.ENABLED` |

🔴 **禁止不规范缩写**（`AbstractClass` 不写成 `AbsClass`，`condition` 不写成 `condi`）。
🔴 **POJO 的布尔属性不加 `is` 前缀**——`private Boolean enabled` 而非 `isEnabled`，否则部分序列化框架取不到属性。
🔴 **接口里的方法和常量不加任何修饰符**（不写 `public`）。

**分层命名固定后缀：**

| 角色 | 类名格式 |
|---|---|
| 控制器 | `XxxController` |
| 业务接口 | `XxxService` |
| 业务实现 | `XxxServiceImpl` |
| 数据访问 | `XxxMapper` |
| 数据库实体 | `XxxEntity` |
| HTTP 入参 | `Xxx{Create\|Update\|Query}Request` |
| HTTP 出参 | `Xxx{\|Detail}Response` |
| 跨模块契约对象 | 业务名词无后缀（`AgentConfig`、`RetrievedChunk`） |
| 错误码枚举 | `XxxErrorCode` |
| 配置属性 | `XxxProperties` |

**Service 方法名固定动词：**

| 语义 | 前缀 |
|---|---|
| 查单个 | `get` |
| 查多个 | `list` |
| 分页 | `page` |
| 统计 | `count` |
| 新增 | `create` |
| 修改 | `update` |
| 删除（软删） | `delete` |
| 判断存在 | `exists` |

### 3.2 常量

🔴 **不允许魔法值直接出现在代码中。**

```java
// ❌
if (status == 1) { ... }
if (retryCount > 3) { ... }

// ✅
if (StatusConstant.ENABLED.equals(status)) { ... }
if (retryCount > RetryConstant.MAX_ATTEMPTS) { ... }
```

- `long` 赋值用大写 `L`：`long timeout = 3000L`（小写 `l` 易与 `1` 混淆）。
- **不要用一个全局常量类装所有常量**——按模块放各自的 `constant` 包，按功能分类。

### 3.3 注释

🔴 **类、字段、方法必须用 Javadoc（`/** */`），不用 `//`。**

```java
/**
 * Agent 管理业务实现。
 * <p>本类是本模块的事务边界，所有写操作在此开启事务。
 */
@Slf4j
@Service
@RequiredArgsConstructor
public class AgentServiceImpl implements AgentService {

    /** Agent 数据访问 */
    private final AgentMapper agentMapper;

    /**
     * 创建 Agent。
     *
     * @param request 创建请求，不能为 null
     * @return 新建 Agent 的主键 id
     * @throws BizException 名称重复或未指定模型时抛出
     */
    @Override
    @Transactional(rollbackFor = Exception.class)
    public Long create(AgentCreateRequest request) { ... }
}
```

| 规则 | 说明 |
|---|---|
| 🔴 接口中的所有方法必须有 Javadoc | 接口是契约，调用方只看得到它 |
| 🔴 `@ModuleApi` 级接口必须写清 **null 语义** 和 **抛什么异常** | 跨模块调用方唯一能看到的信息 |
| 🔴 枚举的每个字段必须有注释 | |
| 方法内部注释 | 在被注释语句**上方**另起一行用 `//`，不写行尾 |
| 改代码同时改注释 | 注释与代码不一致比没有注释更糟 |
| 🔴 无用代码直接删除 | 不要注释掉留着，Git 有历史 |

### 3.4 日志

🔴 **用 `@Slf4j`（SLF4J 门面），不直接使用 Logback / Log4j 的 API。**

| 位置 | 级别 | 内容 |
|---|---|---|
| Controller 入口 | `info` | `[API] 动作, 关键标识`。**不打全量 body** |
| Service 写方法入口 | `info` | 关键入参（id、名称）。不打大字段（提示词、文档内容） |
| Service 读方法入口 | `debug` | 查询条件 |
| 业务分支不通过 | `warn` | 原因 + 上下文，随后抛 `BizException` |
| 外部调用失败 | `error` | 目标 + 耗时 + 异常，**带堆栈** |
| 长流程关键节点 | `info` | 「RAG 命中 N 条」「工具调用第 N 次」「对话完成，耗时 Xms，token Y」 |

🔴 **五条硬规则：**

1. 一律用 `{}` 占位，**禁止字符串拼接**：`log.info("创建 Agent, name={}", name)`。
2. **API Key / Token / MCP 鉴权信息一律不进日志**；必须打时用 `SensitiveUtil.mask()`（保留首尾各 4 位）。
3. **流式输出禁止逐 token 打日志**，只在流开始、流结束、异常三处打。
4. **循环体内禁止 `info`**，需要时降为 `debug`。
5. 生产环境不输出 `debug`。

### 3.5 OOP

| # | 规则 |
|:--:|---|
| 🔴 1 | 所有覆写方法必须加 `@Override` |
| 🔴 2 | **包装类之间的值比较全部用 `equals`**，不用 `==`（`Integer` 缓存只覆盖 -128~127，超出会返回 false） |
| 🔴 3 | **POJO / DTO / Entity 的属性必须用包装类型**（`Integer` 而非 `int`）——基本类型无法表达「未设置」 |
| 🔴 4 | **POJO 类不设任何属性默认值**（`private Integer status = 1;` ❌）——默认值由 Service 或数据库负责 |
| 🔴 5 | 用类名访问静态成员，不用对象引用 |
| 🔴 6 | 构造方法里禁止任何业务逻辑 |
| 🔴 7 | 禁止同时存在 `getXxx()` 和 `isXxx()` |
| 8 | `equals` 用常量或确定非 null 的对象调用；推荐 `Objects.equals(a, b)` |
| 9 | 覆写 `equals` 必须同时覆写 `hashCode` |
| 10 | 不使用已过时的类和方法 |

### 3.6 集合

| # | 规则 |
|:--:|---|
| 🔴 1 | **禁止在 `foreach` 里 `remove` / `add`**——用 `Iterator.remove()` 或 `removeIf()` |
| 🔴 2 | `Arrays.asList()` 的返回值**不支持增删**（是 `Arrays` 内部类，不是 `ArrayList`） |
| 🔴 3 | 集合转数组用 `toArray(new T[0])`，不用无参 `toArray()` |
| 🔴 4 | 遍历 Map 用 `entrySet()`，不用 `keySet()` 再 `get`（两次查找） |
| 🔴 5 | **查询结果为空返回空集合，不返回 `null`** |
| 6 | 初始化时指定容量：`new HashMap<>((int)(n / 0.75f) + 1)` |
| 7 | `subList` 的结果不可强转为 `ArrayList` |
| 8 | 注意 `ConcurrentHashMap` 不允许 null 键值 |

### 3.7 异常

| # | 规则 |
|:--:|---|
| 🔴 1 | **只抛 `BizException`**，禁止 `throw new RuntimeException` / `new Exception` |
| 🔴 2 | **禁止吞异常**——`catch` 块必须至少有 `log.warn/error`，否则重抛 |
| 🔴 3 | **能预检查的 `RuntimeException` 不用 catch 处理**——`NullPointerException`、`IndexOutOfBoundsException` 应该用 `if` 预判 |
| 🔴 4 | **异常不用于流程控制** |
| 🔴 5 | Controller **禁止写 `try-catch`**，统一由 `@RestControllerAdvice` 处理 |
| 🔴 6 | ⚠️ **异步线程里的异常不会进 `@RestControllerAdvice`**——SSE 的异步任务必须自己兜底 |
| 🔴 7 | `finally` 里禁止 `return`；资源用 try-with-resources 关闭 |
| 8 | 只对不稳定代码段 try-catch，不要包一大段 |
| 9 | 事务方法内 catch 了异常又需要回滚时，手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` |

**错误码定义在各模块的 `exception` 包**，不集中到 `common`（否则 common 会依赖业务概念）。

### 3.8 并发与线程池

| # | 规则 |
|:--:|---|
| 🔴 1 | **禁止显式 `new Thread()`**，线程资源必须通过线程池提供 |
| 🔴 2 | **禁止用 `Executors` 创建线程池**（`newFixedThreadPool` 队列无界会 OOM，`newCachedThreadPool` 线程数无界会 OOM），必须用 `ThreadPoolTaskExecutor` / `ThreadPoolExecutor` 显式构造 |
| 🔴 3 | **禁止使用默认的 `SimpleAsyncTaskExecutor`**——它每个任务新建线程且无上界 |
| 🔴 4 | 线程池必须有**有意义的名字前缀**（`llm-chat-` / `kb-index-`） |
| 🔴 5 | `SimpleDateFormat` 线程不安全——用 `DateTimeFormatter` |
| 🔴 6 | **`ThreadLocal` 用完必须 `remove()`**（线程池复用线程，不清会串数据） |
| 🔴 7 | ⚠️ **异步线程里 `ThreadLocal` 是空的**——`UserContext` / `MDC` / `RequestContextHolder` 都取不到。**进入异步前取出来作为参数显式传入** |
| 8 | 多个资源加锁时保持一致的加锁顺序 |
| 9 | 定时任务用 `ScheduledExecutorService`，不用 `Timer` |

### 3.9 控制语句与格式

| # | 规则 |
|:--:|---|
| 🔴 1 | `if` / `else` / `for` / `while` **必须用大括号**，即使只有一行 |
| 🔴 2 | `switch` 必须有 `default`；每个 `case` 要么 `break`/`return`，要么注释说明贯穿 |
| 🔴 3 | `switch` 的 `String` 变量若来自外部参数，先判 `null` |
| 4 | 缩进 4 空格，禁用 tab；单行不超过 120 字符 |
| 5 | 文件编码 UTF-8，换行符 LF |
| 6 | 用卫语句提前返回，避免深层嵌套（嵌套不超过 3 层） |
| 7 | 不在条件判断里写复杂表达式——先赋值给命名清晰的布尔变量 |
| 8 | 避免取反逻辑（`!(a < b)` → `a >= b`） |

### 3.10 Lombok

**能用注解就用，不手写样板代码。**

| 注解 | 用在 |
|---|---|
| `@Data` | Entity、Request、Response |
| `@Value` + `@Builder` | 跨模块契约 DTO（不可变） |
| `@Slf4j` | 所有需要日志的类 |
| `@RequiredArgsConstructor` | 所有 Spring Bean（配合 `private final` 依赖） |
| `@UtilityClass` | 工具类（自动 final + 私有构造 + 静态方法） |

🔴 **禁止字段注入**——不用 `@Autowired` 修饰字段，一律 `@RequiredArgsConstructor` + `private final`。

## 四、分层与调用规则

### 4.1 各层职责与允许依赖

| 层 | 唯一职责 | 可以调 | 🔴 禁止出现 |
|---|---|---|---|
| `controller` | HTTP 适配：收参、`@Valid` 校验、调 service、包 `Result` | `service`、`dto` | 业务判断、`@Transactional`、Entity、Mapper、`service.impl` |
| `service` | **声明**本模块能干什么（接口，无实现） | `dto` | 任何实现、Entity、Mapper、`Page`/`Wrapper`、HTTP 概念 |
| `service.impl` | 业务规则 + 事务边界 + 编排 | `mapper`、`entity`、`dto`、其它模块的 `service` | HTTP 概念（`HttpServletRequest`、`Result`）、手写 SQL |
| `mapper` | 单表 CRUD | `entity` | 业务逻辑、`@Transactional`、跨模块 JOIN |
| `entity` | 与数据库表一一对应 | 无 | 业务方法、对象引用字段 |
| `dto` | 数据传输 | 无 | 业务方法、MyBatis 注解、注入 Bean |

**Controller 方法体不超过 3 行**（日志 + 调用 + 返回）。超过说明业务逻辑漏到了 web 层。

### 4.2 跨模块调用

🔴 **五条规则：**

1. **只能引用对方的 `service`（接口）/ `dto` / `constant` / `exception`**——出现 `import com.hify.{他}.{service.impl|mapper|entity|controller|config}` 即违规。
2. 注入的必须是**接口**，构造器注入。
3. 依赖方向按 2.2 的矩阵，**只能向下、同层禁止**。
4. **只传 id 与对方 `dto`**，禁止传 Entity / `*Request` / `Page` / `Wrapper` / `SseEmitter`。
5. 同步调用。**一期不引 Spring 事件、不引 MQ**（唯一例外：审计日志、用量统计这类旁路，且必须用 `@TransactionalEventListener`）。

**唯一合法形态：**

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class ChatRuntime {
    private final AgentQueryService agentQueryService;    // com.hify.agent.service
    private final ChatModelClientFactory clientFactory;   // com.hify.provider.service
    private final RetrievalService retrievalService;      // com.hify.knowledge.service
    private final ToolExecutor toolExecutor;              // com.hify.mcp.service
}
```

### 4.3 关联关系只存 ID，不做存在性校验

Agent 绑定模型 / 知识库 / MCP 工具，**管理面保存时不校验对方是否存在**——校验会引出 `agent → knowledge`、`agent → mcp` 两条同层依赖，违规。

三处兜住：① 前端下拉只列启用中的对象；② **运行时由 `chat` 装配配置时校验**，失效则明确报错；③ 删除一律做停用，不做反向引用检查。

> **通则：跨模块的反向查询上移到前端解决，后端不建反向依赖。**

### 4.4 事务

🔴 **`@Transactional` 只允许出现在 `service.impl` 的 public 方法上。** 其它任何包（`controller` / `runtime` / `executor` / `client` / `sse` / `pipeline`）出现都是错的。

写方法一律 `@Transactional(rollbackFor = Exception.class)`；只读方法不加。

🔴 **事务方法内禁止四件事：**

| 禁止 | 原因 |
|---|---|
| 调用 LLM / MCP / 任何 HTTP | 耗时以秒计，长时间占住数据库连接 |
| 调用其它模块的**写**方法 | 跨模块共享事务，在数据库层焊死两个模块 |
| `Thread.sleep` / 等锁 / 等 Future | 同上 |
| 创建 `SseEmitter` 或向其 `send` | 流式输出生命周期以分钟计 |

**跨模块调用不共享事务**：被调方自己管事务，调用方不指望对方能被自己回滚。若跨模块写操作需要「一起成功或一起失败」，说明模块划分错了，应合并模块。

**长流程拆短事务：**

```
[短事务1] 创建会话 + 落库用户消息    ← service.impl，毫秒级
(无事务)  RAG 检索 → 流式调模型 → 工具循环   ← runtime，秒~分钟级
[短事务2] 落库助手消息 + 更新会话时间  ← service.impl，毫秒级
```

## 五、数据库规范

### 5.1 数据模型（16 张表）

| 功能域 | 表 | 库 |
|---|---|---|
| 模型 | `model_provider` → `model`（1:N） | MySQL |
| 知识库 | `knowledge_base` → `document` → `document_chunk`（1:N 链） | MySQL / **chunk 在 pgvector** |
| 工具 | `tool` | MySQL |
| Agent | `agent`；`agent_knowledge_base`、`agent_tool`（N:N 中间表） | MySQL |
| 工作流 | `workflow` → `workflow_node`（1:N） | MySQL |
| 对话 | `conversation` → `message`（1:N）；`message_reference`（N:N，RAG 溯源） | MySQL |
| 用户 | `user` → `api_key`（1:N） | MySQL |

**关键关系：**
- `agent → model` 多对一；`agent ↔ knowledge_base`、`agent ↔ tool` 多对多
- `conversation → agent / workflow` 多对一（用 `target_type` + `target_id` 多态字段）
- `message ↔ document_chunk` 多对多，**跨库**，中间表 `message_reference` 落在 MySQL

🔴 **中间表归「持有绑定关系」的模块**（`agent_knowledge_base` / `agent_tool` 归 `hify-agent`），**只存两个 ID，绝不 JOIN 对方主表**。

🔴 **`message_reference` 必须存引用快照**（`content_snapshot` + `document_id` + `score`），不能只存 `chunk_id`——chunk 会因重新分块而变化或消失，只存 id 会让历史溯源指向错误内容。

### 5.2 通用字段

**每张表必备五字段，直接抄，不改类型：**

```sql
`id`         BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT           COMMENT '主键 id',
`created_at` DATETIME(3)      NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
`updated_at` DATETIME(3)      NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '更新时间',
`deleted`    BIGINT UNSIGNED  NOT NULL DEFAULT 0                COMMENT '逻辑删除:0 未删,已删存删除时刻毫秒时间戳',
`creator_id` BIGINT UNSIGNED  NOT NULL DEFAULT 0                COMMENT '创建人 id',
```

| 规则 | 说明 |
|---|---|
| 🔴 主键 `BIGINT UNSIGNED` 自增，**禁止 UUID** | UUID 无序导致聚簇索引页分裂；36 字节 vs 8 字节 |
| 🔴 时间用 `DATETIME(3)`，**不用 `TIMESTAMP`** | `TIMESTAMP` 有 2038 上限且会做时区转换 |
| 🔴 **只设 `DEFAULT`，不设 `ON UPDATE`** | `ON UPDATE` 会在逻辑删除时也改动更新时间；由 `MetaObjectHandler` 控制 |
| 🔴 **`deleted` 用 `BIGINT` 存删除时间戳**，不用 `TINYINT` | 见 5.3 —— 这是唯一能让唯一索引与软删除共存的方案 |
| 🔴 **禁止 NULL**，空值用 `''` 或 `0` | |
| 🔴 枚举用 `VARCHAR(32)` 或 `TINYINT`，**不用 MySQL `ENUM`** | 改枚举值要改表结构 |
| 🔴 小数用 `DECIMAL`，禁止 `FLOAT` / `DOUBLE` | 精度丢失 |
| 🔴 每列必须有 `COMMENT` | |

**表级声明必须显式写全：**

```sql
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='Agent 定义';
```

> `COLLATE` 不统一会导致跨表字符列比较时**索引失效**且报错晦涩（`Illegal mix of collations`）。

### 5.3 🔴 唯一索引与软删除的共存方案

**问题**：`deleted TINYINT` + `UNIQUE(name)` 时，建「客服助手」→ 删除 → 再建同名 → **唯一键冲突**（被删的行还占着 name）。`UNIQUE(name, deleted)` 也只能删一次。

**方案**：`deleted` 存**删除时刻的毫秒时间戳**（未删为 0），唯一索引带上它：

```sql
`deleted` BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '逻辑删除:0 未删,已删存删除时刻毫秒时间戳',
UNIQUE KEY `uk_agent_name` (`name`, `deleted`)
```

这样每次删除产生一个不同的 `deleted` 值，**可无限次删除并重建同名**。

```java
@TableLogic(value = "0", delval = "UNIX_TIMESTAMP(NOW(3)) * 1000")
private Long deleted;
```

> ⚠️ **实现时需验证**：MyBatis-Plus 对 `delval` 中 SQL 表达式的处理在不同版本行为不同（可能被当作字面量加引号）。若不生效，改为在 `service.impl` 里显式 `update` 设置该字段。

### 5.4 索引

| 规则 | 说明 |
|---|---|
| 🔴 命名 | 普通索引 `idx_{表名}_{字段}`；唯一索引 `uk_{表名}_{字段}` |
| 🔴 **复合索引定序** | **① 等值列 → ② `deleted` → ③ 排序列 / 范围列** |
| 🔴 **`deleted` 必须进复合索引** | `@TableLogic` 让每条查询都带 `AND deleted = 0`，不进索引要逐条回表过滤 |
| 🔴 `deleted` 不单独建索引 | 区分度太低，优化器不会选 |
| 🔴 **业务上唯一的字段必须建 `UNIQUE INDEX`** | 不能只在代码层校验（配合 5.3 的方案） |
| 🔴 多对多中间表**两个方向都要索引** | `(agent_id, kb_id)` + `(kb_id, agent_id)` |
| 🔴 **禁止在 `TEXT` / `BLOB` 上建索引** | |
| 🔴 **不建任何外键** | 一切外键概念在应用层解决 |
| 单表二级索引 ≤ 5 个 | 每个索引都要在写入时维护 |
| `VARCHAR` 上建索引须指定长度 | 区分度达 90% 即可，如 `KEY idx_name (name(20))` |

**范围列之后的列用不上索引**——范围列永远放最后。

**实例（`message` 表）：**

```sql
-- 查询形态(全项目唯一一种):按会话游标分页
-- SELECT * FROM message WHERE conversation_id=? AND deleted=0 AND id<? ORDER BY id DESC LIMIT 20
KEY `idx_message_conversation` (`conversation_id`, `deleted`, `id`)
```

🔴 **索引失效的六种写法（AI 最容易犯）：**

| # | 失效写法 | 改成 |
|:--:|---|---|
| 1 | `WHERE DATE(created_at) = '2026-08-11'` | `WHERE created_at >= '2026-08-11 00:00:00' AND created_at < '2026-08-12 00:00:00'` |
| 2 | `WHERE user_id = '123'`（列是 `BIGINT`）**隐式类型转换** | `WHERE user_id = 123` |
| 3 | `LIKE '%助手'` 前导模糊 | `LIKE '助手%'` |
| 4 | `WHERE a = 1 OR b = 2`（分属不同索引） | 拆成 `UNION ALL` |
| 5 | 索引 `(a,b,c)` 查 `WHERE a=1 AND c=3`（跳列） | 调整索引顺序 |
| 6 | `WHERE status != 1` | `WHERE status IN (0, 2)` |

> 第 2 条在 MyBatis-Plus 里尤其常见——DTO 字段是 `String` 直接塞进 `eq()`。**Wrapper 的值类型必须与列类型一致。**

### 5.5 分页

| 场景 | 方案 |
|---|---|
| 管理面列表（< 1 万行的小表） | 普通 `LIMIT offset, n` + `COUNT(*)` |
| 🔴 **`message` / `message_reference`（大表）** | **必须游标分页，且不查 `COUNT`** |

```sql
-- 首屏
SELECT * FROM message WHERE conversation_id=? AND deleted=0 ORDER BY id DESC LIMIT 20;
-- 下一页:带上一页最后一条的 id
SELECT * FROM message WHERE conversation_id=? AND deleted=0 AND id < ? ORDER BY id DESC LIMIT 20;
```

**无论翻到第几页，扫描行数恒定 20。** 而 `LIMIT 1000000, 20` 会实际扫描 1,000,020 行。

| 规则 | 说明 |
|---|---|
| 🔴 `OFFSET` 分页最大 10000 条 | 超过必须改游标分页 |
| 🔴 大表关闭 count | `new Page<>(pageNo, pageSize, false)` |
| 🔴 `pageSize` 上限 100 | 用 `@Max(100)` 在 Request DTO 上约束 |
| `COUNT` 只在第一页查 | 翻页不重复查 |
| 必须显示总数时 | 显示 `100+`，或用近似值 |

### 5.6 大表预判

**建表时就要算一遍二期（2000 人）的行数，分三档：**

| 档 | 行数 | 处置 | 本项目的表 |
|:--:|---|---|---|
| **L0 配置表** | < 1 万 | **什么都不做** | 12 张（模型、Agent、知识库、工具、工作流、用户…） |
| **L1 增长表** | 1 万–500 万 | 建对索引 + 定期清理 | `conversation`、`document_chunk` |
| **L2 大表** | > 500 万 | 建表时就为归档做准备 | **`message`、`message_reference`** |

🔴 **L2 表建表时必须做的三件事**（事后成本高得多）：主键 `BIGINT`、索引一次建对、归档维度字段就位（两表按同一个 `conversation` 一起归档）。

> 千万行表上 `ADD INDEX` 在 MySQL 8 是 ONLINE 的（不阻塞读写），但耗时几十分钟、大量吃 IO，且首尾需要短暂 MDL——若此时有长事务未提交，后续查询会全部排队等锁。

### 5.7 pgvector

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE document_chunk (
    id                BIGSERIAL PRIMARY KEY,
    knowledge_base_id BIGINT       NOT NULL,
    document_id       BIGINT       NOT NULL,
    chunk_index       INT          NOT NULL,
    content           TEXT         NOT NULL,
    embedding         vector(1536) NOT NULL,
    created_at        TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_chunk_kb_doc ON document_chunk (knowledge_base_id, document_id);
CREATE INDEX ON document_chunk USING hnsw (embedding vector_cosine_ops);
```

| 规则 | 说明 |
|---|---|
| 🔴 **维度固定 1536** | 一旦落地不可改——改维度要重跑全量向量化 |
| 🔴 **必须建 HNSW 索引** | 用 `vector_cosine_ops` |
| 🔴 **查询运算符必须与索引 `ops` 匹配** | `<=>` ↔ `vector_cosine_ops`。不匹配**不报错**，只是悄悄退化成全表扫 |
| 🔴 **检索必须加 `LIMIT`**，禁止全量排序 | |
| 🔴 建索引前先调 `maintenance_work_mem` | 默认 64MB，在小内存容器里建索引会 OOM：`SET maintenance_work_mem = '512MB';` |
| ⚠️ **带过滤的检索要验证召回** | HNSW 是先取 `ef_search` 个候选再按 `WHERE` 过滤，目标知识库占比小时可能召回不足。调 `SET hnsw.ef_search = 100;`（默认 40），并用已知答案的查询验证 |

```sql
SELECT id, content, 1 - (embedding <=> $1) AS score
FROM document_chunk
WHERE knowledge_base_id = ANY($2)
ORDER BY embedding <=> $1     -- 必须与索引 ops 一致
LIMIT 5;
```

**跨库一致性不做分布式事务**：删文档 → `document` 软删除 → 检索按 `document_id` 过滤 → 每日 CronJob 清理孤儿向量行。

### 5.8 MyBatis-Plus 与 SQL

| # | 规则 |
|:--:|---|
| 🔴 1 | **禁止 `SELECT *`**——尤其含大字段的表 |
| 🔴 2 | **禁止跨模块 JOIN**（两个不同模块的表出现在同一条 SQL） |
| 🔴 3 | **禁止跨库 JOIN**（MySQL 与 pgvector 之间，物理上也做不到） |
| 🔴 4 | 复杂 SQL 写 XML（`resources/mapper/{module}/`），**禁止 `@Select` 注解 SQL** |
| 🔴 5 | XML 参数用 `#{}`，**禁止 `${}`**（SQL 注入） |
| 🔴 6 | **禁止存储过程、触发器、事件** |
| 🔴 7 | 不用 MyBatis-Plus 的 `IService` / `ServiceImpl` | 会把 CRUD 语义混进业务 Service，诱导 Controller 直接传 Entity |
| 🔴 8 | **禁止无 `WHERE` 无分页的 `selectList`** |
| 9 | 一律 `extends BaseMapper<XxxEntity>`；简单查询用 `LambdaQueryWrapper` 写在 `service.impl` |
| 10 | 超过三个表禁止 JOIN（模块内） |
| 11 | `IN` 后面的集合元素控制在 1000 个以内 |

| 13 | 删除 / 修改前先 `SELECT` 确认 |

## 六、外部调用（LLM）

### 6.1 四道超时闸

🔴 **单一超时值挡不住 LLM 的失败形态，必须四个值：**

| # | 闸 | 默认 | Ollama |
|:--:|---|---:|---:|
| 1 | 连接超时 | 3s | 3s |
| 2 | 首字节超时 | 30s | 90s |
| 3 | **流间隔超时** | 30s | 60s |
| 4 | 整体超时 | 300s | 600s |

🔴 **第 3 道闸必须自己实现**——标准 HTTP 客户端的 read timeout 只覆盖第一个字节，流开始后上游卡死十分钟也不会超时。要在读流循环里算「距上一个 chunk 多久」。

🔴 **不等式必须成立**：`Nginx(360s) > SseEmitter(300s) ≥ 上游整体(300s)`。顺序反了会出现「后端还在正常生成，代理先掐了连接」。

**其它超时**：连通性测试 10s；非流式的同步调用 60s。

### 6.2 线程隔离

🔴 **两个独立线程池，绝不共用：**

| 池 | 用途 | 配置 |
|---|---|---|
| `llm-chat-` | SSE 对话编排 | **core 32 / max 64 / queue 16** |
| `kb-index-` | 文档解析、分块、向量化 | core 2 / max 4 / queue 64 |

🔴 **`queue` 必须小。** JDK 线程池是「核心满 → 进队列 → 队列满才扩容」，`core 16 / queue 128` 会让第 17～144 个请求全部排队、线程数永远停在 16——对分钟级长任务是致命的。

拒绝策略用 `AbortPolicy`，捕获后返回「当前对话数已达上限，请稍后重试」。**不用 `CallerRunsPolicy`**（会让 Tomcat 线程去跑分钟级任务）。

🔴 **每个 provider 一个信号量**（舱壁）：Ollama **上限 3**（本地推理超过显存并发能力后是集体劣化不是排队），云 API 20。

### 6.3 熔断

🔴 **超时、隔离、熔断三者必须一起做**——超时产生失败信号，熔断消费信号快速失败，隔离限制影响范围。**没有超时，熔断器统计到的失败率永远是 0，等于没装。**

```java
CircuitBreakerConfig.custom()
    .slidingWindowType(SlidingWindowType.TIME_BASED)   // 🔴 时间窗,不是计数窗
    .slidingWindowSize(60)
    .minimumNumberOfCalls(5)
    .failureRateThreshold(50)
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .permittedNumberOfCallsInHalfOpenState(2)
    .recordExceptions(IOException.class, TimeoutException.class)
    .ignoreExceptions(BizException.class)              // 🔴 业务错误不计入
    .build();
```

| 🔴 | 说明 |
|---|---|
| 用**时间窗**不用计数窗 | 3–5 QPS 下计数窗要几分钟才填满，熔断永远来不及触发 |
| `ignoreExceptions(BizException.class)` | 401（Key 错）、400（上下文超长）是请求自己的问题，计入会让熔断被无辜打开 |
| **熔断器按 providerId 分实例** | OpenAI 挂了不能影响 Ollama |

### 6.4 重试

🔴 **铁律：首字节到达之后一律不重试。** 用户屏幕上已有半句话，重试会把两段不连贯的文本拼在一起。

| 可重试 | 不可重试 |
|---|---|
| 连接失败 / DNS / 连接超时 | 401 认证失败、403 无权限 |
| 429（**优先读 `Retry-After`**） | 400（含上下文超长）、404 模型不存在 |
| 500 / 502 / 503 / 504 / 529 | 413 请求过大 |
| 首字节超时（**仅 1 次**） | **任何首字节之后的失败** |

退避 500ms → 1500ms（±30% 抖动），**最多 2 次**，**总预算 60s**。

🔴 **工具已执行之后的那一轮 LLM 请求，重试上限降为 0**（只允许重试纯连接失败）——否则会重复执行有副作用的工具。工具调用轮次上限 **5 轮**。

### 6.5 失败降级

| 故障 | 期望行为 |
|---|---|
| LLM 不可用 | **明确报错推给前端**，不静默失败、不无限等待 |
| MCP Server 不可用 | 工具清单走缓存兜底；调用失败作为工具结果交回模型，**不中断对话** |
| 向量检索失败 | **降级为不注入知识库**，对话仍可用 |

错误事件要带 `retryable`（决定前端是否显示「重试」按钮）和 `actionHint`（`check_provider_config` / `new_conversation`）。

## 七、SSE 流式响应

🔴 **必须用 `SseEmitter`，不用阻塞式 `@ResponseBody`**——后者每条连接独占一个 Tomcat 工作线程。
🔴 **不引入 WebFlux**——真正的上限是业务线程池不是 Web 层，且换 WebFlux 要连 MyBatis-Plus 一起换掉。

### 7.1 服务端

```java
@PostMapping(value = "/completions", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter completions(@Valid @RequestBody ChatCompletionRequest request) {
    SseEmitter emitter = sseSessionManager.create(request.getConversationId());

    // 🔴 ThreadLocal 在异步线程里不存在,必须现在取出来显式传进去
    Long userId = UserContext.getUserId();
    String traceId = MDC.get("traceId");

    llmChatExecutor.execute(() -> {
        MDC.put("traceId", traceId);
        try {
            chatRuntime.stream(request, userId, emitter);
            emitter.complete();
        } catch (Exception e) {
            // 🔴 异步线程的异常不会进 @RestControllerAdvice,必须自己兜底
            sseSessionManager.sendError(emitter, e);
        } finally {
            MDC.clear();
        }
    });
    return emitter;
}
```

| 🔴 | 规则 |
|---|---|
| 1 | `SseEmitter` 超时 **300s**，配 **15s 心跳**（注释帧）。心跳同时是探测客户端断连的手段——往已关闭的连接写会立即抛异常 |
| 2 | `onCompletion` / `onTimeout` / `onError` **三个回调都要挂**，缺一个漏一种断连场景 |
| 3 | 断连时必须**取消上游 LLM 请求**（关闭流 + `cancel` Future），否则用户关了页面 token 还在烧 |
| 4 | `release()` 必须**幂等**（多个回调可能都触发） |
| 5 | `emitter.send()` 抛 `IOException` 是**正常路径**（客户端断了），`log.warn` 不要 `log.error` 打全栈 |
| 6 | 事件命名：`message`（增量）/ `error` / `done`；心跳用注释帧 |

### 7.2 Nginx

```nginx
location /api/ {
    proxy_pass http://hify-app:8080;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    gzip off;                    # 🔴 红线
    proxy_buffering off;         # 🔴 红线
    proxy_cache off;
    proxy_read_timeout 360s;     # 🔴 必须 > SseEmitter 的 300s
    client_max_body_size 50m;
}
location / {
    root /usr/share/nginx/html;
    try_files $uri $uri/ /index.html;
    gzip on;                     # 静态资源开压缩
    gzip_min_length 1024;
    gzip_comp_level 5;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml font/woff2;
    # 🔴 gzip_types 绝不能包含 text/event-stream
}
```

### 7.3 前端

🔴 **不能用原生 `EventSource`**——它只支持 GET（对话要传 messages，塞不进 URL）、不能带 `Authorization` 头、且断线会自动重连（导致重复生成、重复扣 token）。

**用 `fetch` + `ReadableStream` 手工解析 SSE**，配 `AbortController` 支持「停止生成」。

## 八、接口规范

### 8.1 路径

RESTful：`/api/v1/{资源复数名}`

```
GET    /api/v1/providers                       列表（分页）
POST   /api/v1/providers                       创建
GET    /api/v1/providers/{id}                  详情
PUT    /api/v1/providers/{id}                  更新
DELETE /api/v1/providers/{id}                  删除（软删）
POST   /api/v1/providers/{id}/test-connection  非 CRUD 操作用动词
```

### 8.2 统一响应

所有接口返回 `Result<T>`：

```json
{ "code": 200, "message": "success", "data": {} }
```

分页返回 `Result<PageResult<T>>`，`PageResult` 含 `list` / `total` / `page` / `pageSize`。

🔴 **`Result` 是 HTTP 层概念**——`service` 接口返回裸对象，绝不包 `Result`。

### 8.3 分页参数

请求：`page`（从 1 开始）、`pageSize`（默认 20，**最大 100**）。

```java
@Data
public class PageQuery {
    @Min(1)
    private Integer page = 1;
    @Min(1) @Max(100)          // 🔴 上限必须有,否则一次拉全表能打爆堆
    private Integer pageSize = 20;
}
```

### 8.4 空值约定

🔴 列表字段空时返回 `[]` 不返回 `null`；字符串字段空时返回 `""` 不返回 `null`；对象不存在时返回 `null`。

### 8.5 错误码

四位数字，按模块分段：

| 段 | 模块 |
|---|---|
| 1000–1999 | 通用 |
| 2000–2999 | Provider |
| 3000–3999 | Agent |
| 4000–4999 | Chat |
| 5000–5999 | MCP |
| 6000–6999 | Workflow |
| 7000–7999 | Knowledge |

错误码枚举定义在各模块的 `exception` 包，**不集中到 `common`**。

## 十、扩展路径

**三阶段，触发条件驱动，条件不到不动。**

| 阶段 | 规模 | 触发条件 | 改什么 | 不改什么 |
|---|---|---|---|---|
| 一期 | 50 人 | — | 单副本 | — |
| 二期 | 500 人 | 响应变慢、CPU/内存持续告警 | 多副本 + MySQL 主从 + CDN | 单体不动、pgvector 不换、Redis 单节点 |
| 三期 | 2000 人+ | LLM 队列堆积、检索 P99 > 2s | MQ 异步、Qdrant、MySQL 分库 | 单体不拆、Redis 不动 |
| 四期 | 几千人 | 模块发布频率互相干扰、某模块资源消耗远超其他 | 拆微服务、API Gateway、Redis 集群 | MySQL 架构不动、K8s 编排层不动 |

**多副本的前置改造（二期真正的工作量，不是改 replicas）：**
① 文件存储去本地化 ② 定时任务改 K8s CronJob（否则每个任务跑 N 遍）③ 进程内缓存清零 ④ 会话上下文外置。

**说明**：SSE 不需要连接粘连——一次请求在同一条 HTTP 连接、同一实例内完成，负载均衡只在建连时发生一次。

## 十二、行为指令

### 12.1 写代码前

1. **先确认要改的模块**，以及它在 2.2 依赖矩阵里的位置——需要新增跨模块依赖时**先问**。
2. **先看同模块已有的类**，模仿它们的写法（命名、注释密度、日志粒度），不要另起一套风格。
3. 涉及数据库的，**先算一遍二期行数**，确定是 L0 / L1 / L2（5.6）。

### 12.2 写代码时

| 规则 | 说明 |
|---|---|
| **用最简单直接的方式实现** | 不引入设计模式，除非明确要求 |
| **不做过度抽象** | 只有一个使用方的接口不要提取；只有一个实现的类不要拆接口（`service` 例外，它是模块边界） |
| **不引入技术栈以外的依赖** | 需要时先问 |
| **所有外部调用必须有超时** | 无一例外 |
| **配置项外化到 `application.yml`** | 不硬编码；前缀 `hify.{module}.*` |
| **能用 Lombok 就用** | 不手写 getter/setter/构造器 |
| **注释和日志同步写** | 不是事后补 |

**新增一个 CRUD 功能的固定顺序：**

```
① Flyway 脚本(含五个必备字段 + 索引)  → ② Entity → ③ Mapper
→ ④ Request/Response DTO(含校验注解) → ⑤ ErrorCode 枚举
→ ⑥ Service 接口 → ⑦ ServiceImpl(写方法加 @Transactional)
→ ⑧ Controller(返回 Result,方法体 ≤ 3 行)
```

**「这个类该放哪」决策树：**

```
处理 HTTP 请求            → controller/
声明业务能力(接口)        → service/
实现业务规则 / 开事务     → service/impl/
数据库单表操作            → mapper/
和数据库表一一对应        → entity/
层间 / 模块间传数据       → dto/
读配置 / 装配 Bean        → config/
错误码                    → exception/
常量、枚举                → constant/
调外部系统                → client/      (仅 provider / mcp)
SSE 连接管理              → sse/         (仅 chat)
对话编排                  → runtime/     (仅 chat)
图解析 / 节点执行         → definition/ executor/  (仅 workflow)
文档处理 / 向量 / 文件    → pipeline/ vector/ storage/  (仅 knowledge)
不落库的领域对象          → domain/      (仅厚模块)
都不是 → 对照 2.3 白名单;不在表里就是设计有问题,先讨论
```

### 12.3 改代码时

1. **先理解相关模块的设计意图**，不要只看要改的那一行。
2. **不为新功能破坏已有接口契约**——`service` 接口的签名改动要评估所有调用方。
3. **改完确保已有测试通过**，包括架构测试（ArchUnit）。
4. **不改已发布的 Flyway 脚本**，新增一个。

### 12.4 写完后自查

| ✔ | 检查 |
|---|---|
| ☐ | 第十一节 20 条红线过一遍 |
| ☐ | 新建的包在 2.3 白名单里 |
| ☐ | 每个 public 方法有 Javadoc（参数 / 返回值 / 异常） |
| ☐ | 每个方法有入口日志和失败分支日志 |
| ☐ | 能用 Lombok 的地方没手写样板代码 |
| ☐ | 建表脚本含五个必备字段、索引、`COMMENT`、`COLLATE` |
| ☐ | `mvn test` 通过 |

### 12.5 不确定时

| 情况 | 怎么办 |
|---|---|
| **架构选择** | 给 2–3 个方案对比，**由我拍板**，不要自己选 |
| **规范没覆盖** | **先问，不要自己编规矩** |
| **需要新依赖** | 先问 |

### 12.6 禁止的行为
