# Hify 容量规划与运维（基准版 · 依据课程）

> 📌 本文档为 **Hify 容量规划与运维的决策基准（source of truth）**，以课程给出的方案为准。
> `09_Hify容量规划与运维.md` 为作者的独立分析（过程记录），二者核心结论高度一致；**如有冲突，以本文档为准**。
> 场景：AI Agent 平台，Docker Compose 本地部署，20–50 人同时在线，主要压力在对话接口（流式 SSE）。
> 技术栈（依据 `08`）：Spring Boot 3.x + MyBatis-Plus + MySQL 8.x + Redis 7.x + Docker Compose。
> 整理日期：2026-07-12

---

## 一、核心结论

> **QPS 极低，瓶颈不是并发；真正的压力点是「LLM 长连接管理」，而非请求量。**

- Spring Boot **单实例**轻松应对本场景。
- 唯一需要认真对待的是 **SSE 长连接**。
- 缓存策略**简单直接**：只缓存变更极少的配置，不缓存 LLM 响应。
- 数据持久化是**硬性要求**：一切数据挂 volume，容器内不存任何数据。

---

## 二、QPS 估算

| 步骤 | 取值 | 计算 |
|------|------|------|
| 在线用户 | 50 人 | — |
| 活跃率 | 60% | 30 人活跃 |
| 每人每分钟消息 | 2 条 | — |
| 对话峰值 QPS | **~1 QPS** | 30 人 × 2 条/分 ÷ 60s ≈ 1 |
| 放大系数 | ×3 | RAG 检索等内部调用放大 |
| **系统峰值 QPS** | **3–5 QPS** | — |

**结论**：3–5 QPS 对 Spring Boot 单实例是「轻松级」。**真正的瓶颈是 LLM 响应延迟（3–30 秒/次）长时间占用连接**——这不是 QPS 问题，是**长连接管理**问题。

---

## 三、SSE 长连接（唯一需要认真对待的压力点）

- 50 个并发 SSE 连接，每个持续 **10–30 秒** → **50 个线程被长期占用**。
- Spring Boot 默认 **200 线程够用**，但必须注意以下三个坑：

| # | 要点 | 说明 |
|---|------|------|
| 1 | **用 `SseEmitter`，不要用普通 `@ResponseBody`** | 普通阻塞式会把线程死死占住；`SseEmitter` 是为流式/异步长连接设计的正确方式。 |
| 2 | **设 60 秒超时** | 防止「僵尸连接」长期挂着不释放，耗尽线程/资源。 |
| 3 | **Nginx 反向代理关闭缓冲 `proxy_buffering off`** | ⚠️ 最容易漏的坑：不关闭的话，流式数据会被 Nginx **攒批再发**，用户**看不到打字机效果**，要等 LLM 全部输出完才一次性吐出来——流式体验直接失效。 |

---

## 四、缓存策略（简单直接）

| 对象 | 决策 | 理由 |
|------|------|------|
| **模型提供商配置 / Agent 配置** | ✅ **Redis 缓存** | 变更频率极低，高读低写，最适合缓存。 |
| **LLM 响应** | ❌ **不缓存** | 同一问题在不同时间，答案可能不同，缓存会返回过期/错误结果。 |
| **对话历史** | ❌ **直接读数据库** | 50 人规模数据量小，缓存收益不大，徒增复杂度。 |

> 缓存原则：**只在「变更极少 + 收益明确」处用缓存**。因为短期 QPS 不高，其余一律直连数据库——**主动放弃缓存以换取更低的开发复杂度**，是本场景下正确的取舍。

---

## 五、数据持久化（硬性要求）

必须挂载 volume 的数据目录：
- **MySQL 数据目录**
- **向量数据库数据目录**
- **上传的文档文件**

> ⚠️ **容器内不存储任何数据。** 这条看似常识，但真有人忘了挂载——容器一重启，数据全没。务必逐项确认 volume 挂载。

## 六、最终运维预期

| 项 | 结论 |
|----|------|
| **部署方式** | Docker Compose 一键启动。 |
| **JVM 内存** | 设上限 **`-Xmx512m`**，防止容器被 **OOM Kill**。 |
| **用户量** | 20–50 人同时在线，**单机部署够用**。 |
| **QPS** | 峰值 **3–5 QPS**，瓶颈在 **LLM 长连接**，不在并发。 |
| **监控** | 起步用 **Spring Boot Actuator + 日志**；后期接 **Prometheus + Grafana**。 |
| **扩容** | 一期单机；**架构上不堵死扩容的路**——第 04 讲做模块化设计，为后续拆分留口子。 |

## 七、一条重要认知：你必须「看得懂」这些建议

> **上面四类建议（QPS 估算 / SSE 长连接 / 缓存策略 / 数据持久化），你必须真正看得懂。如果看不懂就照单全收，整个项目就会失控。**

- 看得懂，才能做**有意识的取舍**。例如：正因为判断「短期 QPS 不高」，才敢**主动放弃复杂缓存**，用一点性能余量换取更低的开发复杂度——这是理解之后的主动决策，而非偷懒。
- 看不懂，就无法判断 AI/参考给的建议在你的场景下是否成立、哪些能砍、哪些是坑，最终被建议牵着走、越加越复杂，直至失控。
- **AI 是加速器，不是你判断力的替代品。** 采纳任何建议的前提，是你能读懂它、并能对它负责。

**一处差异（诚实记录，采纳课程）：缓存策略的繁简。**
- 作者 `09` 提了更丰富的缓存层（配置、会话上下文、Embedding、RAG 检索、LLM 响应精确匹配……）。
- 课程更**克制**：只缓存配置，**不缓存 LLM 响应**（时效性），历史直读库。
- **谁更对（本场景）：课程。** 理由：① 对「单人开发 + 50 人 + 低 QPS」，作者的富缓存方案属于**为规模过度设计**，多出的每一层缓存都是开发/失效/一致性的复杂度；② 尤其「LLM 响应精确匹配缓存」，对会调工具、答案随时间变化的 Agent 而言，课程「不缓存」的默认更安全。
- **修正**：以课程的极简缓存为基准；作者 `09` 的富缓存方案降级为「未来规模上来后的备选清单」，非一期实施。

> 一句话对账：**大方向双方独立收敛（强信号，说明判断可靠）；细节上课程更懂"为当前规模做减法"，作者在缓存上偏保守（过度设计），已采纳课程的极简策略。**
