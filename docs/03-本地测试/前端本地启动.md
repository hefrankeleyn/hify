# hify-web 本地启动说明

前端 `hify-web` 的本地开发说明。后端与依赖容器的启动见同目录 [`README.md`](./README.md)。

`hify-web` **不进 Maven reactor**（父 pom 的 `<modules>` 里没有它），构建走独立的 `pnpm` 命令，
与后端完全解耦——改一行 CSS 不需要重启后端，也不会中断在途的 SSE 对话。

---

## 一、前置要求

| 组件 | 要求 | 本机已验证版本 |
|---|---|---|
| Node.js | ≥ 20.19（Vite 8 的下限） | `v26.5.0` |
| pnpm | 任意近期版本 | `11.5.2` |

端口 **5173**（开发服务器）需空闲。**8080**（后端）不需要提前起，前端能独立启动，
只是调接口时会失败——见第五节。

> 用 npm / yarn 也能装，但仓库里锁的是 `pnpm-lock.yaml`。混用会产生第二份 lock 文件，
> 依赖版本可能与已验证的组合不一致。统一用 pnpm。

---

## 二、两步启动

```bash
# 1. 装依赖（在 hify-web 目录执行）
cd hify-web && pnpm install

# 2. 起开发服务器
pnpm dev
```

pnpm 全局 store 里已有缓存时，`pnpm install` 约 1.6 秒（实测，删掉 `node_modules` 重装）；
首次冷装要走网络下载，耗时视网络而定。

看到这几行即成功，冷启动约 150ms：

```
  VITE v8.2.1  ready in 149 ms

  ➜  Local:   http://localhost:5173/
  ➜  Network: http://192.168.1.6:5173/   en0
```

浏览器打开 <http://localhost:5173/>，会自动跳到 `/chat`，标签页标题变成「对话 - Hify 管理控制台」。

**不需要建 `.env`。** 仓库根 `.gitignore` 第 70 行忽略了 `.env`，所以代码里对两个环境变量
都写了同值默认值（`utils/request.ts`、`router/index.ts`），克隆下来直接就能跑。
需要本地覆盖时再 `cp .env.example .env`。

## 三、全部命令

```bash
pnpm dev              # 开发服务器，带 HMR
pnpm build            # 类型检查 + 生产构建 → dist/
pnpm type-check       # 只做类型检查，不出产物
pnpm preview          # 用静态服务器预览 dist/（验证构建产物，不走 HMR）
```

`pnpm build` 的产物体积（已验证）：

```
dist/assets/index-*.css    357.54 kB │ gzip:  47.94 kB
dist/assets/index-*.js   1,004.05 kB │ gzip: 326.49 kB
                                       ─────────────────
                                       合计 gzip ≈ 374 kB
```

主要是 Element Plus 全量引入的体积。三个业务页面各自懒加载，单页 < 0.2kB。

> ⚠️ **类型检查失败时 `vite build` 不会执行**（实测 `pnpm build` 退出码 1，日志里不会出现
> `vite building`）。所以构建成功等于类型检查也过了，不必分两步跑。

## 四、开发服务器与后端的关系

### 接口一律走相对路径，靠代理转发

前端发出的都是相对路径 `/api/v1/xxx`（axios 的 `baseURL` 是 `/api`，api 文件里再带 `/v1`），
由 `vite.config.ts` 的 `server.proxy` 转发到 `http://localhost:8080`。
生产环境由 Nginx 做同样的事。两边行为一致，因此**不存在跨域，后端不需要开 CORS**。

验证代理是否通（后端需已启动）：

```bash
curl http://localhost:5173/api/v1/health
# {"code":200,"message":"success","data":"Hify is running"}
```

页面上也能看：打开**模型管理**页（`/providers`），它在加载时会自动调一次这个接口——

| 后端状态 | 页面显示 |
|---|---|
| 连通 | 绿色「后端已连接：Hify is running」 |
| 不通 | 红色「后端未连接」，同时弹一个 `ElMessage` 错误提示 |

### 代理超时设成了 360s，不是默认值

```ts
timeout: 360_000,
proxyTimeout: 360_000,
```

对齐生产 Nginx 的 `proxy_read_timeout 360s`，必须大于后端 `SseEmitter` 的 300s
（CLAUDE.md 6.1 的不等式 `Nginx(360s) > SseEmitter(300s) ≥ 上游整体(300s)`）。
用默认值会在开发环境复现「后端还在正常生成，代理先掐了连接」这个故障形态。

**SSE 经代理是逐块透传的，不缓冲**——已用假后端实测：三个 chunk 按 300ms 间隔分别到达，
不是最后一次性吐出来。

### 端口固定 5173，不自动漂移

`vite.config.ts` 里设了 `strictPort: true`。端口被占时**直接失败**：

```
error when starting dev server:
Error: Port 5173 is already in use
```

不设这个的话 Vite 会静默换到 5174，而你以为还在 5173——排查代理问题时会浪费很多时间。

## 五、后端没起会怎样

前端能正常启动和渲染，只有调接口时失败。

**代理层**返回 502，开发服务器控制台打一行：

```
[vite] http proxy error: /api/v1/health
AggregateError [ECONNREFUSED]:
```

**页面上**弹一个 `ElMessage` 错误提示。文案由 `utils/request.ts` 的拦截器按情况区分：

| 情况 | 提示文案 |
|---|---|
| 后端没起 / 代理不通（HTTP 5xx） | 服务器异常（HTTP 502） |
| 连接层就失败，连响应都没有 | 无法连接服务器，请确认后端服务已启动 |
| 请求超时 | 请求超时，请稍后重试 |
| 后端返回了 `Result` 但 `code != 200` | 直接展示后端的 `message` |

拦截器同时会 reject 一个 `ApiError`，业务代码只写 happy path，不必每个页面 try 一遍。

## 六、当前可以做什么

**基本什么都做不了——目前只有脚手架。** 后端除 `/api/v1/health` 外没有任何业务接口，
所以前端也没有对应的页面实现。

已就位的：

| 项 | 状态 |
|---|---|
| 目录结构、路由、布局（`App.vue` 里的左侧菜单 + 右侧内容区） | ✅ 可用 |
| `Result` / `PageResult` 类型与 `utils/request.ts` 封装 | ✅ 可用，未接真实业务接口 |
| `utils/sse.ts` + `composables/useSse.ts` | ✅ 解析器已实现，未接真实对话接口 |
| Pinia、Element Plus（中文 locale） | ✅ 已装配 |
| `src/api/` | 只有 `health.ts` |
| 三个业务页面（模型管理 / Agent 管理 / 对话） | 基本是空壳。模型管理页多一条后端连通状态，另两个只显示一行页面名 |

页面已用无头 Chrome + CDP 逐条整页加载验证：三条路由各自渲染正确、菜单高亮跟随当前路由、
`/` → `/chat` 重定向、未知路径落到 404 页，路由标题均正确。

> 各业务模块的 `api/*.ts` 有意**没有提前建**——后端 DTO 还没定，先写等于替后端编一套契约，
> 后面对不上要返工。等对应的 Controller 落地再逐个补。

## 七、排错

**`pnpm install` 卡住**
npm 源不通。换源后重试：
```bash
pnpm config set registry https://registry.npmmirror.com
```

**`Error: Port 5173 is already in use`**
```bash
lsof -nP -iTCP:5173 -sTCP:LISTEN     # 找出占用进程
```
这是 `strictPort: true` 的预期行为，见第四节。要临时换端口用 `pnpm dev --port 5174`，
但**别改 `vite.config.ts` 里的 5173**——那是团队约定的固定端口。

**页面能打开，但所有接口都报「服务器异常（HTTP 502）」**
后端没起。见第五节，先按 [`README.md`](./README.md) 把后端跑起来。

**接口 404，但后端明明有这个接口**
检查版本号有没有漏掉。`utils/request.ts` 的 `baseURL` 是 **`/api`，不含版本号**，
所以 api 文件里要写 `/v1/health`（→ 实际请求 `/api/v1/health`）。
只写 `/health` 会打到 `/api/health`，后端没有这个路径。

**`pnpm build` 报 `ERR_PACKAGE_PATH_NOT_EXPORTED: './lib/tsc'`**
TypeScript 被升到了 7.x。TS 7 不再导出 `typescript/lib/tsc`，当前版本的 `vue-tsc` 起不来。
`package.json` 里已锁 `~5.9.3`，**在 vue-tsc 支持 TS 7 之前不要动这个 pin**。
误升了就回退：
```bash
pnpm add -D typescript@~5.9.3
```

**改了 `vite.config.ts` 的代理配置但不生效**
Vite 不会热更新自己的配置文件，需要重启 `pnpm dev`。

**IDE 报 `vite.config.ts` 不在任何 tsconfig 项目里**
tsconfig 拆成了三个：根 `tsconfig.json` 只做聚合，`tsconfig.app.json` 管 `src/`、
`tsconfig.node.json` 管 `vite.config.ts`。这是为了让浏览器代码用 Node 全局（`process` / `__dirname`）
时能编译报错——合成一个的话 `@types/node` 的全局声明会漏进 `src/`。
详见 `hify-web/README.md` 的「为什么 tsconfig 拆成三个」。
