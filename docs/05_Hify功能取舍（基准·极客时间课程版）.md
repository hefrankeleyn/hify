## 一、项目定位与约束

**Hify**：基于 Dify 理念做的**简化版 AI Agent 平台**。

| 约束 | 含义 |
|------|------|
| 一个人开发 | 人力极其有限，凡「大而全的框架」一律降级或不做。 |
| 面向团队内部 20–50 人 | 不需要规模化 / 计费 / 对外获客；权限可极简。 |
| 本地部署 | 数据不出内网，模型走本地或少量云 API。 |

---

## 二、基准取舍表（三档：做 / 降级做 / 不做）

### ✅ 做（一期核心，完整实现）

| 功能 | 理由 | 落地要点 |
|------|------|----------|
| **多模型提供商管理** | 平台基础 | 提供统一的模型接入层，支持配置多个模型提供商（本地 + 云 API）。 |
| **Agent 创建与配置** | 核心载体 | Hify 的中心对象：用户创建 Agent、配置提示词/模型/知识库/工具。 |
| **对话引擎（流式、多轮）** | 交互通道 | 支持流式输出与多轮上下文记忆，是用户与 Agent 交互的通道。 |
| **MCP 工具接入** | 区别于聊天机器人的关键能力 | 通过 **MCP（Model Context Protocol）** 标准协议接入工具，复用现成生态，让 Agent 能真正「干活」。 |
| **管理控制台** | 用户操作入口 | 一个 Web 控制台，作为创建 Agent、管理配置、使用对话的统一入口。 |

### 🟡 降级做（一期带上，但做最简版）

| 功能 | 理由 | 降级方式 |
|------|------|----------|
| **知识库 + RAG** | 内部部署的核心价值 | **一期只支持 TXT**：上传 TXT → 分段 → 向量检索 → 注入。其余格式（PDF/Word 等）后置。 |
| **工作流** | 需要编排能力，但可视化太重 | **用 JSON 配置**定义工作流，**不做可视化拖拽**。 |
| **可视化工作流编排** | 前端拖拽实现极重 | 一期只做降级版（或暂以 JSON 配置替代），完整的拖拽式编排后置。 |

### ❌ 不做（本场景不需要 / 超出范围）

| 功能 | 理由 |
|------|------|
| **多租户 / 权限体系** | 内部团队不需要隔离。 |
| **插件市场 / 计费 / 微调** | 超出一人开发范围。 |

---

## 三、一句话总览

> Hify 一期 = 一个**本地部署的 Web 控制台**，用户可以创建并配置 **Agent**（接入统一管理的多模型、通过 **MCP** 调用工具、挂载**仅支持 TXT 的最小 RAG 知识库**），通过**流式多轮对话引擎**使用；需要编排时用 **JSON 配置工作流**；不做多租户/权限、不做插件市场/计费/微调。

---

## 四、建议建设顺序（跟随课程实践用）

1. **平台地基** —— 管理控制台骨架 + 多模型提供商管理（统一模型接入层）。
2. **能对话** —— Agent 创建与配置 + 流式多轮对话引擎，跑通「建一个 Agent 并对话」。
3. **能干活** —— MCP 工具接入，让 Agent 能调用工具。
4. **能用数据** —— 知识库 + RAG 降级版（仅 TXT）。
5. **能编排** —— 工作流 JSON 配置（不做可视化）。

> 完成 1–5，Hify 一期主线即打通。可视化编排、多格式 RAG 等留待后续迭代；多租户/权限、插件市场/计费/微调不在计划内。

---

## 五、关键名词速记

- **MCP（Model Context Protocol）**：一种标准化的工具/上下文接入协议，接入后可复用现成的开源工具服务器生态，是 Hify 让 Agent「能干活」的关键选型。
- **RAG（检索增强生成）**：把用户上传的文档向量化检索后注入提示词，让 Agent 基于内部数据回答。
- **降级做**：一期就交付该功能，但砍到最简版本（如 RAG 只支持 TXT、工作流只用 JSON），以保证产品完整性、避免日后大改。
