# Hify 功能取舍决策（基于 Dify 裁剪）

> 目标：基于 Dify 做一个**简化版 AI Agent 平台 Hify**。
> 约束：**① 一个人开发 ② 面向团队内部 20–50 人 ③ 本地部署**。
> 方法：从 `02_Dify核心功能模块梳理.md` 的功能列表出发，逐项判断「必须做 / 可延后 / 砍掉」并说明理由。
> 整理日期：2026-07-12

---

## 〇、先定判断框架（为什么这么砍）

在动手砍之前，先明确三条约束各自意味着什么——这决定了每个功能的去留：

| 约束 | 它意味着什么 | 对功能取舍的影响 |
|------|--------------|------------------|
| **一个人开发** | 开发/维护人力极其有限，任何「大而全」的子系统都是黑洞。 | 优先砍**建设成本高**的东西（可视化编辑器、插件生态、多供应商适配层）。宁可硬编码，不做框架。 |
| **内部 20–50 人** | 不需要海量并发、不需要计费、不需要对外获客。但需要**基本的多用户和登录**。 | 砍掉一切「规模化 / 商业化 / 对外」功能；保留最低限度的账号与权限。 |
| **本地部署** | 数据不出内网，模型可用本地（Ollama）或少量云 API。 | 砍掉云 SaaS、复杂多供应商；模型接入收敛到 1–2 个。 |

**一条主线**：Agent 平台不可压缩的核心价值 =
> **接上模型** + **配好提示词** + **挂上自己的数据/工具** + **能发布给同事用**。

凡是不服务这条主线的，一律延后或砍掉。判断每个功能时问一句：**「没有它，这条主线还能跑通吗？」** 能跑通就不是 MVP 必需。

## 一、逐模块取舍

图例：✅ 必须做（MVP 核心）｜🕒 可延后（V2 再说）｜❌ 砍掉（本场景不需要）

### 1. 应用类型（Dify 有 5 种）

| 功能 | 结论 | 理由 |
|------|------|------|
| 智能体 Agent | ✅ | 这是产品定位本身（AI **Agent** 平台），必须有：能推理 + 调工具 + 多步完成任务。 |
| 聊天助手 Chatbot / 对话流 Chatflow | ✅（合并为「对话应用」一种） | 内部最高频的场景就是「基于知识库问答」。但不必区分 Chatbot 与 Chatflow 两种类型，合并成一种「带知识库的对话应用」即可。 |
| 文本生成 Text Generation | ❌ | 单轮生成用「对话应用 + 一句提示词」就能覆盖，单独做一种应用类型是重复建设。 |
| 工作流 Workflow（可视化 DAG 编排） | 🕒 | **最诱人也最烧钱的功能**。可视化节点编辑器是整个 Dify 里对一个人来说工程量最大的部分（拖拽、连线、变量流转、调试器）。MVP 不做；Agent 内部用代码把「检索→调工具→回答」串起来即可满足绝大多数需求。 |

### 2. 提示词编排（Prompt IDE）

| 功能 | 结论 | 理由 |
|------|------|------|
| 提示词编辑 + 变量表单 | ✅ | 核心且便宜。一个文本框 + `{{变量}}` 占位 + 输入表单就够。 |
| 多模型并排对比 | ❌ | 调优阶段的锦上添花。本地就一两个模型，没有对比的必要，建设成本却不低。 |

### 3. 知识库 / RAG

| 功能 | 结论 | 理由 |
|------|------|------|
| 上传文档 + 分段 + 向量检索 | ✅ | 「用自己的数据」是内部平台的最大价值，必须有一个能跑的最小 RAG：上传 PDF/Word/TXT → 切块 → 向量入库 → 检索注入。 |
| 混合检索 + Rerank 重排 | 🕒 | 能提升召回质量，但先用「向量检索 Top-K」就能用。等效果不够了再加。 |
| 多数据源 ETL（Notion / 网页抓取等） | ❌ | 每个数据源都是一套对接。内部场景「手动上传文件」足够，其余按需再说。 |
| 经济索引（关键词） / 复杂元数据过滤 | ❌ | 收敛到「一种向量索引」，减少分支与维护。 |

### 4. 工作流节点

| 功能 | 结论 | 理由 |
|------|------|------|
| 可视化节点体系（LLM/分类/分支/代码/HTTP/迭代…） | 🕒 | 依附于「工作流」这一延后项，一并延后。 |
| Agent 内部所需能力：知识检索、工具调用 | ✅ | 这些能力**必须有**，但**不以可视化节点形式提供**——直接写进 Agent 的执行逻辑里（ReAct/Function Calling）。 |

### 5. 工具与插件

| 功能 | 结论 | 理由 |
|------|------|------|
| 让 Agent 调用工具（Function Calling） | ✅ | Agent 的灵魂。没有工具调用，Agent 就退化成聊天机器人。 |
| 少量内置工具（搜索 / HTTP 请求 / 计算等，硬编码） | ✅ | 先内置 2–3 个最常用的，代码写死即可。 |
| 自定义工具（OpenAPI 导入） | 🕒 | 接内部系统会用到，但可以先用「配置一个 HTTP 工具」的简版，不做完整 OpenAPI 解析。 |
| 插件市场 / 插件打包 / 插件生态体系 | ❌ | 一个巨大的生态工程，单人无力维护，内部也用不上。 |

### 6. 模型管理

| 功能 | 结论 | 理由 |
|------|------|------|
| 接入 1 个本地模型（Ollama）+ 可选 1 个云 API | ✅ | 本地部署的刚需。收敛到 1–2 个即可。 |
| LLM + Embedding 两类模型 | ✅ | RAG 需要 Embedding，对话需要 LLM，这两类必须支持。 |
| 数十家供应商的统一适配层 | ❌ | Dify 值钱的地方之一，但也是巨量适配代码。单人场景写死 1–2 家 API 即可。 |
| Rerank / 语音 / TTS / 审核等多模型类型 | ❌ | 非核心场景，按需再加。 |

### 7. 可观测与运营

| 功能 | 结论 | 理由 |
|------|------|------|
| 基础会话日志（存输入/输出/报错） | ✅ | 出问题必须能排查，20–50 人用一定会有问题。最低限度：把每次对话落库。 |
| 监控看板 / 费用统计 | 🕒 | 内部无计费压力，先不做；想看用量时再补个简单统计页。 |
| 标注回复 / 人工优化闭环 | 🕒 | 有价值但非首发，效果不好时再引入。 |
| 第三方 Tracing（LangSmith/Langfuse） | ❌ | 引入外部依赖，本地内部场景不必要。 |

### 8. 发布与集成

| 功能 | 结论 | 理由 |
|------|------|------|
| 发布成一个内网可访问的 Web 页面 | ✅ | 「能发布给同事用」是主线的终点，必须有一个能直接打开使用的聊天页面。 |
| 应用 API（供内部系统调用） | ✅（简版） | 内部集成会用到，但只需一个「带 token 的 REST 接口」，不必做完整的开放平台。 |
| 嵌入式组件 / difyctl CLI | ❌ | 对外/多渠道分发能力，内部场景用不上。 |

### 9. 平台与部署

| 功能 | 结论 | 理由 |
|------|------|------|
| Docker Compose 本地部署 | ✅ | 约束直接要求。一套 compose 拉起（应用 + 向量库 + 数据库）。 |
| 简单登录 + 2 种角色（管理员 / 普通用户） | ✅ | 20–50 人必须有账号体系，但只需最粗的权限划分。 |
| 工作空间 / 团队 | 🕒 | 单团队内部先不分空间，人多了再说。 |
| SSO / 精细 RBAC / 多租户 / 云 SaaS | ❌ | 企业级 & 规模化能力，本场景明确不需要。 |

## 二、MVP 一句话结论

**Hify V1 = 一个能本地部署、带简单登录的 Web 平台，用户可以：配置一个「带知识库 + 会调工具的 Agent 对话应用」，并把它发布成一个内网聊天页面 / API 给同事用。**

技术栈收敛：**1 套 Docker Compose**（Web 应用 + 一个向量库如 pgvector/Chroma + Postgres）+ **1–2 个模型**（Ollama 本地 + 可选云 API）+ **硬编码的 2–3 个内置工具**。

---

## 三、建议的建设顺序（单人视角）

1. **地基**：Docker Compose + 登录 + 建应用的骨架。
2. **能对话**：接 1 个模型 + 提示词编辑 → 跑通最简对话应用。
3. **能用数据**：最小 RAG（上传→分段→向量检索→注入）。
4. **能干活**：给 Agent 加 Function Calling + 2–3 个内置工具。
5. **能给人用**：发布成内网 Web 页面 + 带 token 的 API + 会话日志。

> 这 5 步跑通，主线（接模型 + 配提示词 + 挂数据/工具 + 发布）就完整了。其余全部标 🕒/❌ 的功能，都等真实使用暴露出需求后再增量补。

## 四、取舍速查表

| 类别 | ✅ 必须做 | 🕒 可延后 | ❌ 砍掉 |
|------|----------|-----------|--------|
| 应用类型 | Agent、对话应用（合一） | 工作流(可视化) | 文本生成(独立类型) |
| Prompt | 编辑+变量 | — | 多模型对比 |
| 知识库/RAG | 上传+分段+向量检索 | 混合检索/Rerank | 多数据源ETL、经济索引、复杂元数据 |
| 工作流节点 | (并入 Agent 的检索/工具能力) | 可视化节点 | — |
| 工具/插件 | 工具调用+内置工具 | 自定义HTTP工具 | 插件市场/生态 |
| 模型管理 | 本地模型+Embedding | — | 多供应商适配、Rerank/语音/TTS |
| 可观测 | 会话日志 | 监控看板、标注 | 第三方Tracing |
| 发布集成 | 内网Web页面、简版API | — | 嵌入组件、CLI |
| 平台部署 | Docker部署、登录+2角色 | 工作空间 | SSO/RBAC/多租户/云 |
