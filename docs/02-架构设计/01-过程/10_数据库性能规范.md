## 〇、红线清单

> 建任何一张表、写任何一条查询之前，先对照这 12 条。

| # | 红线 | 判据 |
|:--:|---|---|
| 1 | 主键必须 `BIGINT UNSIGNED AUTO_INCREMENT` | 出现 `INT` 主键或 UUID 主键 |
| 2 | 必备五字段一个不少 | 缺 `id` / `create_time` / `update_time` / `deleted` / `creator_id` |
| 3 | 字符集必须 `utf8mb4` + `utf8mb4_0900_ai_ci` | 建表语句未显式声明 |
| 4 | **不建任何外键** | 出现 `FOREIGN KEY` / `REFERENCES` |
| 5 | **不建业务唯一索引** | 出现 `UNIQUE KEY`（与软删除冲突，见 1.4） |
| 6 | 软删除表的复合索引，`deleted` 放等值列之后、排序列之前 | 见 2.3 |
| 7 | 单表二级索引 ≤ 5 个 | 数一下 |
| 8 | 每列必须有 `COMMENT` | 出现无注释的列 |
| 9 | **大表禁止 `LIMIT offset, n` 深分页** | `message` / `message_reference` 上出现 `OFFSET > 1000` |
| 10 | **大表列表禁止查 `COUNT(*)`** | 见 4.3 |
| 11 | 索引列上不许用函数、不许隐式类型转换 | 见 2.5 |
| 12 | pgvector 的查询运算符必须与索引 `ops` 匹配 | 见 5.3 |

## 一、通用字段约定

### 1.1 五个必备字段的确切定义

**直接抄这五行，不要改类型。**

```sql
`id`          BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT           COMMENT '主键 id',
`create_time` DATETIME(3)      NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
`update_time` DATETIME(3)      NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '更新时间',
`deleted`     TINYINT UNSIGNED NOT NULL DEFAULT 0                COMMENT '逻辑删除:0 未删 1 已删',
`creator_id`  BIGINT UNSIGNED  NOT NULL DEFAULT 0                COMMENT '创建人 id',
```

**每个选择的理由：**

| 选择 | 理由 |
|---|---|
| `BIGINT UNSIGNED` 而非 `INT` | `INT UNSIGNED` 上限 42.9 亿。`message_reference` 年增千万级，看着够但一旦到顶是**线上改表**——差 4 个字节不值得赌 |
| **自增而非 UUID** | UUID 无序 → InnoDB 聚簇索引页分裂严重，写入性能显著下降；且 36 字节 vs 8 字节，每个二级索引都要带一份主键 |
| `DATETIME(3)` 而非 `TIMESTAMP` | `TIMESTAMP` 有 2038 上限，且会做时区转换（与「应用/JVM/MySQL 统一 `Asia/Shanghai`」的约定叠加时容易出错）。毫秒精度便于同秒内排序 |
| **只设 `DEFAULT`，不设 `ON UPDATE`** | `ON UPDATE CURRENT_TIMESTAMP` 会在**任何** UPDATE 时改动，包括逻辑删除——那不是业务意义上的「更新」。更新时间由应用层 `MetaObjectHandler` 控制，DB 默认值只做兜底 |
| `deleted` 用 `TINYINT` 而非 `BIT` | MyBatis-Plus `@TableLogic` 与 `TINYINT` 配合最省事；`BIT` 在各类客户端里显示混乱 |

### 1.2 表级声明

```sql
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci
  COMMENT='Agent 定义';
```

**`COLLATE` 必须显式写且全库统一。** MySQL 8 默认是 `utf8mb4_0900_ai_ci`，但如果某张表建成了 `utf8mb4_general_ci`，将来两表的字符列做比较时**索引会失效**——排序规则不一致的列比较无法走索引，且报错信息晦涩（`Illegal mix of collations`）。

### 1.3 可选字段（不是通用，按需加）

| 字段 | 何时加 |
|---|---|
| `status TINYINT` | 有「启用/停用」语义时。**与 `deleted` 是两回事**：`deleted` 是记录级删除，`status` 是业务状态 |
| `version INT` | 有并发更新冲突风险时（如 Agent 配置多人同改）。一期 50 人，大部分表**不需要** |
| `remark VARCHAR(500)` | 用户可填备注时 |

### 1.4 ⚠️ 不建业务唯一索引

**这是一条反直觉但必要的规则。** 唯一索引与逻辑删除天然冲突：

```sql
UNIQUE KEY uk_name (`name`)
-- 建一个叫「客服助手」的 Agent → 删掉 → 再建一个同名的 → ❌ 唯一键冲突
-- 因为被删的那行还在表里(deleted=1),name 仍占着
```

三种常见「解法」都有代价：

| 解法 | 问题 |
|---|---|
| `UNIQUE KEY (name, deleted)` | **只能删一次**——删第二个同名的又冲突（两行都是 `deleted=1, name=X`） |
| `deleted` 存删除时间戳而非 0/1 | 可行，但与 `@TableLogic` 的默认约定不符，全项目要改 |
| **应用层校验（选这个）** | 查一次再插，理论上有并发窗口 |

**一期采用应用层校验**，理由很实际：50 人规模下「两个人在同一毫秒创建同名 Agent」的概率接近零，而唯一索引 + 软删除的组合会带来**必然发生**的坑（删了重建同名，是很常见的操作）。

**唯一索引的唯一例外**：技术性唯一约束且不参与软删除的，可以建——例如 `agent_knowledge_base (agent_id, knowledge_base_id)` 这类中间表（重复插入无意义，且中间表用物理删除）。

## 二、索引设计

### 2.1 命名规范

| 类型 | 格式 | 示例 |
|---|---|---|
| 主键 | `PRIMARY KEY` | — |
| 普通索引 | `idx_<列名简写>` | `idx_conversation_id`、`idx_kb_doc` |
| 唯一索引（仅中间表） | `uk_<列名简写>` | `uk_agent_kb` |

### 2.2 复合索引的列顺序：三步定序

**按这个顺序排，不要凭感觉：**

```
① 等值条件列（WHERE col = ?）        ——— 放最前，区分度高的在前
② 软删除列（deleted）                ——— 见 2.3
③ 排序列（ORDER BY）/ 范围列（>、<、BETWEEN、LIKE 'x%'）
```

**范围列之后的列用不上索引**——这是最左前缀原则最实际的推论。所以范围列永远放最后。

**实例（`message` 表）：**

```sql
-- 查询形态(全项目唯一一种):按会话拉最近 N 条
SELECT * FROM `message`
WHERE conversation_id = ? AND deleted = 0
ORDER BY id DESC LIMIT 20;

-- 索引:等值(conversation_id) → 软删除(deleted) → 排序(id)
KEY `idx_conversation` (`conversation_id`, `deleted`, `id`)
```

### 2.3 ⚠️ `deleted` 要进复合索引，但只在等值列之后

**这条容易搞反。** 常见的说法是「区分度低的列不建索引」，`deleted` 区分度极低（几乎全是 0），于是很多人把它排除在外。但在本项目里必须放进去：

**因为 `@TableLogic` 让每一条查询都自动带 `AND deleted = 0`。**

| 索引 | 执行过程 |
|---|---|
| `(conversation_id, id)` | 按 `conversation_id` 定位 → 逐条**回表**读 `deleted` 判断 → 丢弃已删的。已删行多时会多读很多次 |
| **`(conversation_id, deleted, id)`** | 按 `conversation_id` + `deleted` 定位到精确区间 → 区间内 `id` 天然有序 → **直接倒序读 20 条，零浪费** |

**规则：软删除表的复合索引，`deleted` 放在所有等值列之后、排序/范围列之前。**

**但 `deleted` 绝不单独建索引**——`KEY idx_deleted (deleted)` 完全无用（区分度太低，优化器不会选）。

### 2.4 索引数量上限：单表 ≤ 5 个二级索引

每个二级索引都要在**每次 INSERT / UPDATE / DELETE 时同步维护**，且占额外磁盘。

**判据：一张表如果需要第 6 个索引，先问是不是查询形态设计错了。** 本项目 16 张表里，除 `message`、`document_chunk` 外都只需要 1–2 个。

### 2.5 索引失效清单（AI 最容易写出的六种）

| # | 写法 | 为什么失效 | 改成 |
|:--:|---|---|---|
| 1 | `WHERE DATE(create_time) = '2026-08-11'` | 索引列上用函数 | `WHERE create_time >= '2026-08-11 00:00:00' AND create_time < '2026-08-12 00:00:00'` |
| 2 | `WHERE user_id = '123'` （`user_id` 是 `BIGINT`） | **隐式类型转换** | `WHERE user_id = 123` |
| 3 | `WHERE name LIKE '%助手'` | 前导模糊 | 改后缀匹配 `LIKE '助手%'`，或上全文索引 |
| 4 | `WHERE a = 1 OR b = 2`（a、b 分属不同索引） | OR 跨列 | 拆成两条 `UNION ALL`，或建复合索引 |
| 5 | 索引 `(a,b,c)` 但查 `WHERE a=1 AND c=3` | 跳列，`c` 用不上 | 调整索引顺序，或补 `b` 的条件 |
| 6 | `WHERE status != 1` | 否定条件区分度差，优化器倾向全扫 | 改为 `IN (0, 2)` 枚举正向值 |

**第 2 条在 MyBatis-Plus 里尤其容易发生**——DTO 里字段是 `String`，直接塞进 `eq()` 就成了字符串比较。**Wrapper 的值类型必须与列类型一致。**

### 2.6 覆盖索引：只在高频小结果集用

```sql
-- 会话列表只需要 id / title / update_time
KEY `idx_user_cover` (`user_id`, `deleted`, `update_time`, `title`)
```

把 `SELECT` 需要的列都放进索引，就不用回表。**但代价是索引变宽、写入变慢**——只对「高频 + 结果集小 + 列少」的查询用，全项目预计不超过两处。

## 三、大表预判与应对

### 3.1 预判方法：建表时就算一遍

```
年增行数 = 日增行数 × 365
日增行数 = 用户数 × 人均日操作次数 × 每次产生的行数
```

**按一期 50 人和二期 2000 人各算一遍**，取二期的数决定分级。

### 3.2 三档分级与处置

| 档 | 行数量级 | 处置 | 本项目的表 |
|:--:|---|---|---|
| **L0 配置表** | < 1 万 | **什么都不做**。不加缓存、不分区、不优化 | `model_provider` `model` `knowledge_base` `tool` `agent` `agent_knowledge_base` `agent_tool` `workflow` `workflow_node` `user` `api_key` `document`（11–12 张） |
| **L1 增长表** | 10 万 – 500 万 | 建对索引即可；定期清理 | `conversation` `document_chunk`（pgvector）`workflow_node_execution`（若采纳） |
| **L2 大表** | > 500 万 | **建表时就要为归档做准备**，见 3.3 | `message` `message_reference` |

**L0 占了四分之三的表。** 对它们做任何优化都是浪费——不要给它们加索引、加缓存、做分区。

### 3.3 L2 大表：建表时必须做的三件事

`message` 与 `message_reference` 年增千万级。**这三件事只能在建表时做，事后成本高得多：**

| # | 做什么 | 为什么只能现在做 |
|:--:|---|---|
| 1 | **主键 `BIGINT UNSIGNED`** | 到顶了改主键类型 = 重建表 |
| 2 | **复合索引一次建对**（见 2.2） | 见下方 ⚠️ |
| 3 | **归档维度字段就位**：`message` 有 `conversation_id`、`message_reference` 有 `message_id`，两者按同一个 `conversation` 一起归档 | 事后补关联字段要回填历史数据 |

> ⚠️ **一处更正**：本项目早前文档写过「后期补索引要锁表」——**这个说法不准确**。MySQL 8.0 的 `ALTER TABLE ... ADD INDEX` 默认是 ONLINE 的（`ALGORITHM=INPLACE, LOCK=NONE`），**不阻塞读写**。
>
> 但「建表时建对」的结论不变，理由换成三条更真实的：① 千万行表上建索引**耗时几十分钟并大量消耗 IO**，期间查询整体变慢；② 开始和结束时需要短暂的**元数据锁（MDL）**，若此时有长事务未提交，会造成后续查询全部排队等 MDL——这才是线上事故的常见形态；③ 单副本部署下，任何一次这种操作都没有备用实例分担。

### 3.4 应对策略阶梯（先便宜后昂贵）

```
① 建对索引        ← 绝大多数「慢」的真实原因
② 改查询写法      ← 深分页、COUNT(*)、SELECT *
③ 定期清理        ← 执行记录类数据保留 90 天
④ 冷热分离        ← message 只留 3 个月,更早的搬 message_archive
⑤ 原生分区        ← 分区键必须进主键,改表结构
⑥ 分库            ← 二期的事
```

**不要跳级。** 本项目预计走到 ④ 就够（`05_Hify扩展路径（基准）` 已定）。

## 四、分页查询

### 4.1 ⚠️ 深分页：`LIMIT 1000000, 20` 会实际扫描 100 万零 20 行

MySQL 的 `LIMIT offset, n` 是**先取出 offset+n 行再丢弃前 offset 行**，不是「直接跳到第 offset 行」。

| 查询 | 实际扫描 |
|---|---|
| `LIMIT 0, 20` | 20 行 |
| `LIMIT 10000, 20` | 10,020 行 |
| `LIMIT 1000000, 20` | **1,000,020 行** ← 秒级甚至更慢 |

### 4.2 两种分页，按表分级选

| 场景 | 表 | 方案 |
|---|---|---|
| 管理面列表（Agent、模型、知识库…） | **L0 小表** | 普通 `LIMIT offset, n` + `COUNT(*)`。几百行，随便查 |
| **消息历史、引用记录** | **L2 大表** | ⚠️ **必须用游标分页，且不查 COUNT** |

**游标分页（seek method）——推荐写法：**

```sql
-- 首屏
SELECT * FROM `message`
WHERE conversation_id = ? AND deleted = 0
ORDER BY id DESC LIMIT 20;

-- 下一页:带上一页最后一条的 id
SELECT * FROM `message`
WHERE conversation_id = ? AND deleted = 0 AND id < ?   -- ★ 关键
ORDER BY id DESC LIMIT 20;
```

**无论翻到第几页，扫描行数恒定 20。** 配合 `(conversation_id, deleted, id)` 索引完美。

**代价**：不能跳页（没有「第 500 页」）。但消息历史的交互本来就是「向上滚动加载更多」，天然契合。

**兜底方案——延迟关联**（必须支持跳页且表大时用）：

```sql
SELECT m.* FROM `message` m
INNER JOIN (
  SELECT id FROM `message`
  WHERE conversation_id = ? AND deleted = 0
  ORDER BY id DESC LIMIT 10000, 20     -- 子查询只走索引,不回表
) t ON m.id = t.id;
```

### 4.3 ⚠️ 大表不要查 `COUNT(*)`

`PaginationInnerInterceptor` 默认会额外执行一次 `SELECT COUNT(*)`。在千万行表上这条 count **可能比数据查询本身慢十倍**（要扫完整个索引）。

```java
// L2 大表:显式关闭总数查询
Page<MessageEntity> page = new Page<>(pageNo, pageSize, false);   // ★ 第三个参数 = searchCount
```

**替代方案**：

| 需求 | 做法 |
|---|---|
| 无限滚动 | 不需要总数。多查一条判断「还有没有下一页」 |
| 必须显示数量 | 显示 `100+`；或维护一个计数字段；或用 `SHOW TABLE STATUS` 的近似值 |

### 4.4 分页参数的硬约束

```java
/** 分页查询基类。所有列表请求继承它。 */
@Data
public class PageQuery {
    /** 页码,从 1 开始 */
    @Min(1)
    private Integer pageNo = 1;

    /** 每页条数,上限 100——防止一次拉全表 */
    @Min(1) @Max(100)
    private Integer pageSize = 20;
}
```

**`pageSize` 上限必须有。** 否则前端传 `pageSize=99999` 就是一次全表扫 + 几百 MB 的响应体，能直接把堆打爆。

## 五、pgvector 专项

### 5.1 建表

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE document_chunk (
    id                BIGSERIAL PRIMARY KEY,
    knowledge_base_id BIGINT       NOT NULL,   -- 逻辑引用 MySQL,跨库不建外键
    document_id       BIGINT       NOT NULL,
    chunk_index       INT          NOT NULL,
    content           TEXT         NOT NULL,
    embedding         vector(512)  NOT NULL,   -- ★ 维度见 5.2
    create_time       TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 过滤用的普通索引(检索总是先限定知识库范围)
CREATE INDEX idx_chunk_kb_doc ON document_chunk (knowledge_base_id, document_id);
```

### 5.2 维度：建议 512，且**必须记录在 `model` 表里**

| 维度 | 单向量体积 | 1 万条 | 10 万条 |
|---:|---:|---:|---:|
| 1536 | 6 KB | 60 MB | 600 MB |
| **512** | **2 KB** | **20 MB** | **200 MB** |

`text-embedding-3-small` 支持 `dimensions=512`，存储、内存、距离计算全部降到 1/3，中文短文本上召回率损失通常很小。

**⚠️ 维度一旦定了就不能改**——换维度等于历史向量全部作废，要重跑全量 embedding。所以：

1. **一期就定 512**（`05_Hify扩展路径（基准）` 待定项 2）；
2. **`model` 表必须记录该 embedding 模型的维度**，`knowledge_base` 记录它用的是哪个 embedding 模型——换模型时能立刻判断向量是否需要重建。

### 5.3 ⚠️ 索引 `ops` 必须与查询运算符匹配（pgvector 最常见的坑）

pgvector 有三组距离运算符，**索引建的是哪一组，查询就必须用哪一个，否则索引直接不生效**（不报错，只是悄悄全表扫）：

| 运算符 | 距离 | 对应索引 ops |
|:---:|---|---|
| `<=>` | 余弦距离 | `vector_cosine_ops` |
| `<->` | L2（欧氏） | `vector_l2_ops` |
| `<#>` | 负内积 | `vector_ip_ops` |

**本项目统一用余弦：**

```sql
-- 查询
SELECT id, content, 1 - (embedding <=> $1) AS score
FROM document_chunk
WHERE knowledge_base_id = ANY($2)
ORDER BY embedding <=> $1        -- ★ 必须与索引 ops 一致
LIMIT 5;

-- 索引(触发条件到了再建,见 5.4)
CREATE INDEX ON document_chunk USING hnsw (embedding vector_cosine_ops);
```

**排查提示**：`EXPLAIN ANALYZE` 里若看到 `Seq Scan` 而不是 `Index Scan`，先检查运算符是否与 `ops` 匹配。

### 5.4 索引：一期不建，> 1 万条再建 HNSW

| 分段数 | 处置 |
|---:|---|
| < 1 万 | **不建索引**。顺序扫描 20–50ms，且**过滤条件下召回完全准确**（见 5.5） |
| ≥ 1 万 **或** 表体积 > `shared_buffers` 一半 | 先加内存，再建 HNSW |

```sql
-- 顺序不能反:先加容器内存与 shared_buffers,再建索引
SET maintenance_work_mem = '512MB';   -- 默认 64MB,在 512Mi 容器里建索引会 OOM
CREATE INDEX CONCURRENTLY ON document_chunk USING hnsw (embedding vector_cosine_ops);
```

**HNSW vs IVFFlat**：选 **HNSW**——IVFFlat 要求建索引时表里已有代表性数据（靠聚类分桶），而知识库是持续增长的，早期建的 IVFFlat 会随数据增长而劣化。HNSW 构建慢、占空间多，但增量友好、召回率更稳。

### 5.5 ⚠️ 带过滤条件的向量检索会召回不足

**检索总是带 `WHERE knowledge_base_id = ANY(...)`**（只在 Agent 绑定的知识库里搜）。这与 HNSW 索引有一个结构性冲突：

```
HNSW 的执行方式:先按向量相似度取出 ef_search 个候选 → 再用 WHERE 过滤
若候选里属于目标知识库的不足 k 个 → 返回结果少于 k 条,甚至为空
```

**知识库越多、目标知识库占比越小，这个问题越严重。**

| 应对 | 说明 |
|---|---|
| **一期无索引 → 天然没有这个问题** | 顺序扫描是先过滤再算距离，召回完全准确。**这是一期不建索引的一个额外好处** |
| 建索引后：调大 `ef_search` | `SET hnsw.ef_search = 100;`（默认 40）。牺牲一点延迟换召回 |
| 建索引后：开启迭代扫描 | pgvector 0.8+ 支持 `SET hnsw.iterative_scan = relaxed_order;`——候选不足时自动继续扫 |
| 数据量极大时：按 `knowledge_base_id` 分区 | 每个分区独立建索引，过滤变成分区裁剪 |

**建 HNSW 索引时必须同步验证召回**：用一组已知答案的查询，对比建索引前后的命中情况。**不验证就上索引，等于把检索质量的下降藏起来。**

## 七、禁止清单

| 禁止 | 原因 |
|---|---|
| `SELECT *`（尤其含大字段的表） | `document_content` / `message` 有大文本，全查会打爆堆 |
| 存储过程、触发器、事件 | 逻辑藏在数据库里，代码里搜不到，排障成本极高 |
| `FOREIGN KEY` | 已定 |
| 业务 `UNIQUE KEY` | 与软删除冲突（1.4） |
| **跨模块 JOIN** | 两个不同模块的表出现在同一条 SQL 里 |
| **跨库 JOIN** | MySQL 与 pgvector 之间，物理上也做不到 |
| `LIMIT` 大 offset（L2 表） | 深分页（4.1） |
| 大表 `COUNT(*)`（L2 表） | 4.3 |
| 生产环境 `ALTER TABLE` 不看执行计划 | 千万行表上的 DDL 要评估耗时与 MDL 影响（3.3） |
| 在事务里做远程调用 | 数据库连接被占住整轮 LLM 调用 |

## 八、一句话结论

> **五个必备字段照抄不改；全库不建外键、不建业务唯一索引（与软删除冲突，改应用层校验）；复合索引按「等值列 → `deleted` → 排序/范围列」定序——`deleted` 必须进索引，因为 `@TableLogic` 让每条查询都带上它。**
> **16 张表里 12 张是 L0 配置表（< 1 万行），对它们做任何优化都是浪费；只有 `message` 和 `message_reference` 是 L2 大表，它们的三件事只能在建表时做：`BIGINT` 主键、索引一次建对、归档维度字段就位。**
> **两条最容易踩的：L2 表禁止 `LIMIT offset` 深分页和 `COUNT(*)`，改游标分页 + `searchCount=false`；pgvector 的查询运算符必须与索引 `ops` 匹配（`<=>` ↔ `vector_cosine_ops`），不匹配时不报错、只是悄悄退化成全表扫。**

## 九、待定项

| # | 待定项 | 说明 | 倾向 |
|---|---|---|---|
| 1 | **embedding 维度定 512 还是 1536** | 一旦定了改不了（要重跑全量向量化） | **512**，需先用真实文档验召回率 |
| 2 | **`update_time` 要不要设 `ON UPDATE`** | 设了会在逻辑删除时也变动 | 不设，由应用层控制 |
| 3 | **中间表要不要软删除** | `agent_knowledge_base` 等改绑定时是改还是删 | **物理删除**（绑定关系无保留价值），因此可建唯一索引 |
| 4 | **`message_reference` 的归档粒度** | 与 `message` 同批走，还是独立策略 | 同批（按 `conversation`） |
| 5 | **是否需要慢查询日志与定期巡检** | 一期无 Prometheus | 开 `slow_query_log`，阈值 1s，每周看一次 |
