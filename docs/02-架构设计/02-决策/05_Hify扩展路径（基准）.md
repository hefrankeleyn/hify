## 〇、最高原则

> **每个阶段有明确的触发条件，条件不到就不动。**

这条比任何一个技术选型都重要。它的含义是：

- **不预备**——不为「以后可能要用」提前引入组件；
- **不整包做**——一个阶段里的三四项改动，哪项的触发条件先到就先做哪项，不打包上线；
- **触发条件必须是可观测指标**——「感觉慢了」不是触发条件。

## 二、第一阶段：50 → 500 人

### 2.1 触发条件

| 指标 | 阈值 |
|---|---|
| **响应变慢** | 用户可感知，且能对应到具体接口 |
| **`docker stats` / K8s CPU** | 持续告警（> 70%） |
| **内存** | 持续告警（接近 limit） |
| 峰值并发 SSE | > 20 |
| 发版中断 | 开始有用户抱怨被打断 |

> 后两项是补充的量化口径——CPU / 内存告警是「已经难受了」的信号，而并发数与发版中断能让你**提前一步**发现。

### 2.2 改什么

| # | 改动 | 说明 |
|:--:|---|---|
| 1 | **Spring Boot 1 副本 → 2–3 副本** | 主改动。真正的工作量见 2.4 |
| 2 | **MySQL 加一主一从** | 见下方细化 |
| 3 | **静态资源上 CDN** | 见下方细化 |
| 4 | Nginx 1 → 2 副本 | 无状态，顺手 |
| 5 | `llm-chat` 线程池 core 32 → 48 | 参数 |

**细化 ①：主从 ≠ 读写分离，建议先只做「从」。**

| | 做什么 | 建议 |
|---|---|---|
| **加从库** | 主从复制，从库用于**备份与故障切换** | ✅ **这一阶段做** |
| **读写分离** | 应用层把读请求分流到从库 | ⏸ **暂缓**——500 人约 10–20 QPS，MySQL 单实例余量仍是百倍；分流带来的主从延迟（「刚保存完刷新看不到」）是纯负债 |

主从的价值在这一阶段是**可用性**，不是性能。读写分离等到主库 CPU 真的持续 > 70% 再开。

**细化 ②：CDN 在纯内网场景收益接近零。**

| 访问形态 | CDN 收益 |
|---|---|
| 办公室千兆内网 | ❌ 约 20ms，无感；且与「数据不出内网」的部署约束有冲突 |
| **多地办公 / VPN / 居家** | ✅ **明显**，1MB 的包在 5–10Mbps 下能省 1–1.6 秒 |

**判据：有没有跨地域或远程访问的用户。** 没有的话，`04_Hify一期性能处置（基准）` 里已开的 gzip 就够了；有的话 CDN 值得做。

### 2.3 不改什么

| 不改 | 理由 |
|---|---|
| **整体单体架构不动** | 没有任何模块需要独立扩容或独立发版 |
| **pgvector 不换** | 分段数没到万级，顺序扫描仍是毫秒级 |
| **Redis 单节点不动** | 数据量 < 100MB，QPS 两位数，余量千倍 |
| 不引 MQ | 二期的事 |
| 不引 WebFlux | 真正的上限是业务线程池，不是 Web 层 |

### 2.4 难点：多副本的四项前置改造

> ⚠️ **更正：SSE 不需要连接粘连（sticky session）。** 详见第七节更正 ①。
>
> Hify 的 SSE 是「一次 POST 请求 → 在同一条 HTTP 连接上流式返回这次的结果」。整条流的生命周期在**同一条 TCP 连接、同一个实例**内——负载均衡只在建连那一刻发生一次，连接建立后由 TCP 钉死在那个 Pod 上，**不存在「被随机分发到不同实例」的场景**。
>
> **因此这一阶段不需要配置任何会话粘连。** Redis 会话共享仍然要做，但它解决的是**多轮对话上下文的外置**（换个实例也能读到历史），不是连接粘连——两件事容易混为一谈。

**真正的难点是把应用变成真无状态。** 副本数从 1 改成 2 是一行 YAML，下面四项才是工作量，**缺任何一项都会出诡异 bug**：

| # | 前置改造 | 不做会怎样 |
|:--:|---|---|
| 1 | **文件存储去本地化**：TXT 内容存 MySQL（或对象存储） | 用户在副本 A 上传、副本 B 读不到。**且 `ReadWriteOnce` PVC 会让滚动更新死锁**——新 Pod 挂不上卷，旧 Pod 又在等新 Pod Ready |
| 2 | **定时任务外置**：应用内 `@Scheduled` → **K8s CronJob** | ⚠️ **多副本下每个定时任务跑 N 遍。**清理孤儿向量跑两次还好，将来若有通知/结算类任务就是事故 |
| 3 | **缓存全走 Redis**：清掉所有进程内 `ConcurrentHashMap` 缓存 | 副本间不一致——改了 Agent 配置，刷新页面时好时坏，极难排查 |
| 4 | **会话上下文外置到 Redis / MySQL** | 换实例读不到历史。**这就是「Redis 会话共享」真正要解决的问题** |

**顺带必须核对的：**

- **数据库连接数**：`副本数 × HikariCP 池大小`。3 副本 × 20 = 60，MySQL 默认 `max_connections` 151，安全——但这个乘法要养成习惯。
- **Flyway 并发启动**：多副本同时启动会争 `flyway_schema_history` 的锁，后者等待（不出错，但迁移慢时第二个副本可能启动超时，`startupProbe.failureThreshold` 要留足）。

### 2.5 成本

**约 3–5 人天**，其中 3 天在第 1 项（文件存储改造 + 已有文档迁移）。

> **这就是一期应该直接把 TXT 存数据库的原因**（`04` 基准第五节已提示）：一期做是零成本，二阶段才做要连带数据迁移。

## 三、第二阶段：500 → 2000 人

### 3.1 触发条件

| 指标 | 阈值 |
|---|---|
| **LLM 调用队列堆积** | `llm-chat` 线程池队列持续非空、出现拒绝 |
| **对话成功率下降** | 失败率 > 1%，或 429 频繁出现 |
| **知识库检索 P99 > 2s** | 检索方法日志 |

### 3.2 改什么

| # | 改动 | 说明 |
|:--:|---|---|
| 1 | **引入消息队列（RocketMQ / Kafka）做 LLM 异步调用削峰** | 见下方细化 ③ |
| 2 | **pgvector → 独立 Qdrant** | 见下方细化 ④ |
| 3 | **MySQL 按业务模块分库** | 见下方细化 ⑤ |

**细化 ③：MQ 削峰对「文档处理」成立，对「对话」要看产品形态。**

削峰的前提是**请求可以延后处理**。这一点在两类负载上表现完全不同：

| 负载 | 能否削峰 | 说明 |
|---|:---:|---|
| **文档解析 + 向量化** | ✅ **完全成立** | 用户提交后就走开了，晚 5 分钟完成没有区别。**这是 MQ 在本项目最扎实的用途** |
| **对话请求** | ⚠️ **要看产品形态** | 用户在屏幕前等着。异步化不会缩短总时长——只是把等待从「连接上等」换成「轮询里等」。真正的收益是**撞限流时排队而不是失败**，但那意味着产品上要接受「您排在第 3 位」这种交互 |

**建议的做法：分两步，先做便宜的那半。**

1. **先只把文档处理异步化**——而且这一步可以**不用 MQ**：用一张任务表 + `SELECT ... FOR UPDATE SKIP LOCKED` 就能安全地多副本消费，任务状态天然可查、可重试、可在管理界面展示进度。
2. **对话异步化单独评估**——它的代价是前端从 SSE 改成轮询或 WebSocket，是 breaking change（见 3.4）。等对话确实开始因限流批量失败了再做。

> **真正需要引 MQ 的信号**：任务量 > 每秒几十个，或需要多个独立消费者组。到那时再引不迟——任务表的接口形态与 MQ 消费者是同构的，换起来是机械的。

**细化 ④：迁 Qdrant 之前，先建 HNSW 索引 + 加内存并复测。**

「检索 P99 > 2s」这个触发条件，第一反应不应该是换组件。当前 pgvector 是**无索引顺序扫描 + 512Mi 容器**，这两项都还没优化过：

```
第 1 步  pgvector 容器 512Mi → 2Gi,shared_buffers 128MB → 512MB
第 2 步  SET maintenance_work_mem = '512MB';
         CREATE INDEX CONCURRENTLY ... USING hnsw (embedding vector_cosine_ops);
第 3 步  复测 P99。达标就停在这里
第 4 步  仍不达标 → 迁 Qdrant
```

⚠️ **顺序不能反**：构建 HNSW 需要 `maintenance_work_mem`（默认仅 64MB），在 512Mi 容器里对几万条 1536 维向量建索引**很可能直接 OOM**。而且建索引要安排维护窗口，不是随手执行一条 SQL。

pgvector + HNSW 通常能撑到百万级分段。**多数情况下第 3 步就够了，能省掉一个要独立运维的组件。**

**细化 ⑤：分库如果是为性能，不成立；如果是为三期铺路，成立。**

2000 人约 20–50 QPS，MySQL 单实例余量仍是数十倍——**分库不会让它变快**。而 `chat_message` 的体积问题（年增约 1460 万行）**归档就能解决，不需要分库**。

但分库有另一个正当理由：**为三期拆微服务铺路**。而且本项目分库的机械成本很低——「不跨模块 JOIN、不建跨模块外键、只存 ID」这三条硬规矩已经执行了，按模块切库不需要重写任何查询。

**判据**：如果三期拆服务已经在明确规划里，二期分库是合理的前置；如果三期还很远，先做归档、把分库留给三期一起做。

### 3.3 不改什么

| 不改 | 理由 |
|---|---|
| **Spring Boot 仍是单体，不做微服务拆分** | 拆分的触发条件是「模块间发布/资源互相干扰」，那是三期的事 |
| **Redis 架构不动**（仍单节点） | 数据量与 QPS 都远未到 |
| 不引 API Gateway | Nginx + K8s Service 够用 |
| 不做分布式链路追踪 | 单体内部，日志 traceId 够用 |

### 3.4 难点：LLM 异步化是 breaking change

前端要从 SSE 改成轮询或 WebSocket，影响面覆盖整个对话交互：

| 影响项 | 说明 |
|---|---|
| 前端对话组件 | 重写数据获取层 |
| 增量内容的传递 | 从「HTTP 流」变成「轮询拉取增量」或「WebSocket 推送」 |
| 错误与重试语义 | 轮询下要能区分「还在生成」「已失败」「已完成」 |
| 任务状态持久化 | 生成中的部分内容要落库，否则轮询拿不到 |
| **连接粘连**（WebSocket 方案） | ⚠️ **这里才真正需要**——见下 |

> **注意一个顺序上的反直觉**：连接粘连的需求不是多副本带来的（那是第一阶段的误判，见更正 ①），而是**异步化本身**带来的。一旦改成「提交任务 → 另开通道订阅进度」，接收通道所在的实例与执行任务的实例可能不同，这时才需要跨实例通知（Redis Pub/Sub）或粘连。
>
> **这是把对话异步化留到最后做的又一个理由：它引入的复杂度不止前端。**

**成本估算：约 10–15 人天**（含前端）。这也是「不到触发条件不做」在整条路径上最该被严格执行的一处。

## 四、第三阶段：2000 → 几千人

### 4.1 触发条件

| 信号 | 说明 |
|---|---|
| **单个模块的发布频率互相干扰** | 知识库策略调优频繁，每次都要重启对话服务 |
| **某模块资源消耗远超其他模块** | 如 Agent 执行 / 文档向量化的 CPU 占用挤占对话 |
| 有第二个人加入 | 模块边界靠自觉在多人下失效更快 |

**注意触发条件的性质变了**：前两阶段是「量」的信号（CPU、并发、P99），这一阶段是「**节奏**」的信号——某个模块需要与其它模块不同的发布或扩容节奏。**人数本身不是拆分理由。**

### 4.2 改什么

| # | 改动 | 说明 |
|:--:|---|---|
| 1 | **按模块拆微服务**：Agent 执行 / 知识库 / 对话历史 各自独立 | 见下方拆分顺序 |
| 2 | **引入 API Gateway 替代 Nginx 路由** | 统一鉴权、限流、灰度 |
| 3 | **Redis 换集群模式** | 见下方细化 ⑥ |

**拆分顺序建议：先拆资源特性最不同的那个。**

不要一次拆三个。按「与主链路的资源特性差异」排序，差异最大的先拆：

| 模块 | 负载特性 | 与对话的冲突 | 优先级 |
|---|---|---|:---:|
| **知识库（文档解析 + 向量化）** | **CPU 密集 · 突发**（批量导入 10 倍尖峰） | 周期性挤占对话 CPU | **1** |
| **Agent 执行** | 视工具而定，可能长耗时 | 占用编排线程 | 2 |
| 对话历史 | IO 密集 · 平稳 | 几乎无冲突 | 3（可不拆） |

**决定性的是「突发」那一行**：知识库的负载曲线与对话完全不同，两者共用实例意味着要按峰值配容量。对话历史则是平稳负载、加实例就线性有效，**拆它收益最小**。

**细化 ⑥：需求是可用性，「集群模式」解决的是容量分片。**

| | 解决什么 | 本项目的需求 |
|---|---|---|
| **Redis 主从 + 哨兵** | **高可用**（主挂了自动切换） | ✅ **这才是需要的**——Redis 挂了会导致缓存全失效瞬间打穿 MySQL |
| **Redis Cluster（集群模式）** | **容量与吞吐分片**（数据超过单机内存 / QPS 超过单机上限） | ⚠️ 几千人下数据量约几百 MB、QPS 几百，**远未触及单机上限** |

**建议改为「Redis 主从 + 哨兵」。** Cluster 的分片能力用不上，却要付出多 key 操作受限、运维复杂度上升的代价。真到容量不够时再上 Cluster。

### 4.3 不改什么

| 不改 | 理由 |
|---|---|
| **MySQL 主从架构不动** | 二期已建好，够用 |
| **Qdrant 不动** | 二期已迁（若确实迁了） |
| **K8s 编排层不动** | Deployment / Service / Ingress 那套不变，只是多几个 Deployment |
| 不拆对话历史 | 见 4.2 优先级表 |
| 不引服务注册发现 | K8s Service + DNS 就是服务发现 |
| 不引 RPC 框架 | 服务间用 HTTP + `RestClient` |

### 4.4 难点

> ⚠️ **更正：不需要 Saga 或 TCC。** 详见第七节更正 ②。
>
> 引入分布式事务的前提是**存在跨服务的事务**。但本项目从一开始就定了硬规矩：**跨模块调用不共享事务**（`02_Hify模块内部分层（基准）` 6.3）——模块对外接口要么是只读查询，要么自身是完整的事务单元。
>
> **如果这条规矩一直被遵守，拆分时没有任何事务需要被"分布式化"，Saga / TCC 无从谈起。** 如果拆分时发现真的需要 Saga，那说明规矩在某处被破了——**正确的动作是回头修那处代码，而不是引入 Saga 来兼容它**。引 Saga 等于把一个设计缺陷固化成基础设施。

**那么第三阶段真正的难点是什么？**

| 难点 | 说明 |
|---|---|
| **跨服务的最终一致性**（不是事务） | 例：文档在知识库服务被删，对话服务里的引用成了孤儿。**处置方式已定**：软删除 + 定时清理，不做分布式事务 |
| **调用链路可观测性** | 一个请求跨 2–3 个服务，日志要能串起来。**做法**：traceId 在 HTTP 头透传，日志带上——不引 SkyWalking/Jaeger |
| **服务间认证** | 内部共享密钥即可，不引 mTLS |
| **失败传播** | 知识库服务挂了，对话要降级为不注入知识库（**既有降级策略已覆盖**） |
| **发布顺序与接口兼容** | 拆分后两个服务独立发版，接口变更要向前兼容一个版本 |

**代码改动极小**：`chat` / `workflow` 注入的 `RetrievalService` 从本地实现换成 HTTP 实现，**接口签名一个字不改**——这正是「跨模块走 Service 接口」这条规矩在此处的兑现。

**成本：约 10–15 人天**（拆第一个服务），含联调与失败注入测试。

## 五、贯穿全程「永远不改」

无论走到哪一阶段，下面这些都不变。它们是这条路径能平滑走下来的原因，动了就等于重来：

| 永远不改 | 在哪一步兑现 |
|---|---|
| **七个模块的划分** | 三期拆分时直接按它切 |
| **跨模块只走 `service` 接口** | 三期换成远程调用，签名不变 |
| **不共享事务** | 三期不需要 Saga / TCC（更正 ②） |
| **不跨模块 JOIN** | 二期分库时不用重写任何查询 |
| **只存 ID、不建跨模块外键** | 二期分库时不用先删外键 |
| **状态外置** | 一阶段多副本直接成立 |
| **文件存储走抽象接口** | 一阶段换实现类即可 |

## 六、执行纪律

| 纪律 | 含义 |
|---|---|
| **条件不到就不动** | 每项改动都必须能指出是哪个指标越了哪条线 |
| **一个阶段内不打包** | 三四项改动分别有各自的触发条件，谁先到做谁 |
| **先纵向后横向** | 加内存 / 加 CPU 通常比加副本、换组件便宜十倍，先试 |
| **换组件前先调参数** | Qdrant 之前先建索引加内存；MQ 之前先试任务表 |
| **改完要能验证** | 动手前先定验收指标 |
| **改完要能回滚** | 建索引、分库、拆服务都要有回退路径 |

### 6.1 每次扩容前的检查清单

| ✔ | 检查 |
|---|---|
| ☐ | 瓶颈定位有数据支撑吗？是哪个指标越线了 |
| ☐ | 是不是配置问题？线程池、连接池、超时值先核一遍 |
| ☐ | 有没有更便宜的一步？（纵向扩容、调参数、建索引） |
| ☐ | 多副本相关三件事核过了吗？定时任务重复执行、进程内缓存、数据库连接数 |
| ☐ | 改完怎么验证？能回滚吗？ |

## 七、本文档对原方案做的更正与细化

**全部列在这里，可逐条驳回。** 两处「更正」是技术事实层面的，且**都让难点变小**；四处「细化」是判断层面的建议。

| # | 类型 | 原方案 | 本文档 | 理由 |
|:--:|---|---|---|---|
| ① | 🔴 **更正** | 一阶段难点：SSE 需要连接粘连，用 Redis 会话共享解决 | **不需要连接粘连**。Redis 会话共享仍做，但目的是上下文外置 | SSE 是「一次请求 → 同一条 HTTP 连接返回」，整条流在同一 TCP 连接、同一实例内，负载均衡只在建连时发生一次。**难点降级** |
| ② | 🔴 **更正** | 三阶段难点：需引入 Saga 或 TCC | **不需要**。真正的难点是最终一致性、链路可观测性、接口兼容 | 「跨模块不共享事务」已是硬规矩，遵守了就没有跨服务事务。若真需要 Saga，说明规矩被破了，该修代码而非引 Saga。**难点降级** |
| ③ | 🟡 细化 | 一阶段：MySQL 加读写分离 | **先只加从库（备份 + 故障切换），读写分离暂缓** | 500 人约 10–20 QPS，单实例余量百倍；读写分离的主从延迟是纯负债 |
| ④ | 🟡 细化 | 一阶段：静态资源上 CDN | **有跨地域 / VPN 用户才做** | 纯内网千兆下收益约 20ms，且与「数据不出内网」有冲突 |
| ⑤ | 🟡 细化 | 二阶段：MQ 做 LLM 异步削峰 | **拆成两半**：文档处理先异步化（可用任务表，不必上 MQ）；对话异步化单独评估 | 削峰的前提是可延后；对话是用户在线等待，异步化不缩短总时长 |
| ⑥ | 🟡 细化 | 二阶段：pgvector → Qdrant | **先建 HNSW + 加内存并复测**，仍不达标再迁 | 当前是无索引 + 512Mi，两项都没优化过；pgvector + HNSW 通常撑到百万级 |
| ⑦ | 🟡 细化 | 三阶段：Redis 换集群模式 | **改为主从 + 哨兵** | 需求是可用性；Cluster 解决的是容量分片，几千人下用不上 |

## 八、一句话结论

> **三个阶段，每个阶段有明确的、可观测的触发条件——条件不到就不动，一个阶段内也不打包做。**
> **一期 50 人单副本，二期 500 人多副本 + 主从，三期 2000 人+ 拆微服务；向量库到二期末才可能换 Qdrant，MQ 先只用于文档处理，Redis 到三期才动。**
> **最贵的一步是二阶段的 LLM 异步化（breaking change，约 10–15 人天），所以它最该被「不到触发条件不做」严格约束；而一阶段和三阶段的「最大难点」原本被高估了——SSE 不需要连接粘连，拆服务也不需要 Saga/TCC，因为「不共享事务、跨模块走接口」这两条规矩在一期就已经把代价付掉了。**

## 九、待定项

| # | 待定项 | 说明 | 倾向 |
|---|---|---|---|
| 1 | **一期是否直接把 TXT 存数据库** | 决定一阶段要不要做数据迁移 | **一期就做**（零成本） |
