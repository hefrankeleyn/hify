## 一、决策

> **一期只做两件事。**

| # | 事项 | 内容 | 成本 |
|:--:|---|---|---|
| **1** | **LLM 调用加固** | **超时 + 线程隔离 + 熔断**，三者一体 | 约 2–3 人天 |
| **2** | **Nginx 开启 gzip** | 静态资源压缩，**`/api/` 除外** | 一行配置 |

**其余一律不做**，包括上下文裁剪、批量 embedding、文档解析流式化、pgvector 索引、消息表归档。各自的触发条件与后果见第五节。

## 二、判据：爆炸半径，不是修复成本

一期该加固什么，判据只有一条：

> **这个故障发生时，是影响一个人，还是影响所有人？**

按这条判，50 人规模下的候选项分成两类：

| 故障 | 影响面 | 真实触发概率 |
|---|---|---|
| **LLM 提供商挂掉 / 变慢 / 限流** | 🔴 **所有正在对话的用户，同时** | **高**——外部依赖，不受控，一定会发生 |
| 某个人的对话轮次太多报错 | 🟡 一个会话 | 中 |
| 某次文档导入慢 | 🟡 一次操作 | 中 |
| 向量检索变慢 | 🟡 检索请求变慢，对话仍可用（已定降级为不注入） | 低（需先积累到万级分段） |

**只有第一项会级联。** 上游一挂，业务线程全被占住等超时，**连不涉及 LLM 的管理面请求都会受影响**——这是这套架构里唯一一个单点故障能打到每个人的路径。其余全是局部劣化，用户能感知、能重试、不扩散。

`../01-过程/07_性能瓶颈分析与一期处置.md` 按「事后修复成本」排出了另一组四项。**那个排序对「什么时候该做」有用，对「先加固什么」用错了**——修复成本高的事可以排期，爆炸半径大的事必须开工前就有。两个排序不冲突，本文档取后者。

第 2 件（gzip）不在这个判据内，它是**成本近乎为零因而不需要论证**的一项。

## 三、第一件：LLM 调用的超时 + 线程隔离 + 熔断

### 3.1 为什么这三件必须一起做

这不是三个独立选项，是**一条链**：**超时产生失败信号 → 熔断消费信号快速失败 → 隔离限制影响范围**。缺任何一环，另外两环失效。

| 只做了 | 缺什么 | 实际结果 |
|---|---|---|
| **只有超时** | 无隔离、无熔断 | 上游卡死时每个线程等满 30 秒才释放。并发一上来线程池照样占满，**全站仍然不可用**——只是从「永久挂起」变成「持续拥堵」 |
| **只有隔离** | 无超时 | 隔离舱的许可**永远不释放**（没有超时就没人归还），舱位很快耗尽。该 provider 完全不可用，好处仅剩「不外溢到其它 provider」 |
| **只有熔断** | 无超时 | ⚠️ **熔断器根本不会打开**——它靠统计「失败率」工作，而没有超时就没有失败，请求只是一直挂着。**熔断器看到的失败率是 0** |
| **超时 + 隔离，无熔断** | 无快速失败 | 故障期间每个请求都要等满 30 秒才报错。用户体验是「每次都要卡 30 秒」，持续到上游恢复 |
| **三者齐全** | — | 首次几个请求超时 → 熔断打开 → 后续请求**微秒级明确失败** → 30 秒后半开试探 → 上游恢复即自动闭合。**期间其它 provider 完全不受影响** |

> **第三行是最容易被忽略的**：很多人以为「引了 Resilience4j 就有熔断了」。没有超时，熔断器是个摆设。

### 3.2 超时：四道闸

单一超时值挡不住 LLM 的失败形态。**「连不上」「服务在但不干活」「流开始后卡死」「无限生成」是四件事，要四个值。**

| # | 闸 | 默认值 | Ollama | 挡什么 |
|:--:|---|---:|---:|---|
| 1 | 连接超时 | 3s | 3s | 服务不可达、DNS 失败 |
| 2 | 首字节超时（TTFB） | 30s | 90s | 服务在但不响应、排队 |
| 3 | **流间隔超时** | 30s | 60s | **流开始后卡死** |
| 4 | 整体超时 | 300s | 600s | 无限生成、死循环 |

**第 3 道闸必须自己实现。** 标准 HTTP 客户端的 read timeout 只覆盖第一个字节；流一旦开始，每收到一个 token 就重置计时，**上游卡住十分钟也不会超时**。要在读流循环里自己算「距上一个 chunk 多久了」：

```java
long lastChunkAt = System.currentTimeMillis();
while ((line = reader.readLine()) != null) {
    long now = System.currentTimeMillis();
    if (now - lastChunkAt > cfg.getStreamIdleMillis()) {
        log.error("上游流卡死, provider={}, 已静默={}ms", cfg.getProviderName(), now - lastChunkAt);
        throw new BizException(ProviderErrorCode.STREAM_IDLE_TIMEOUT);
    }
    if (now - start > cfg.getTotalMillis()) { /* 闸 4 */ }
    if (line.isEmpty()) continue;
    lastChunkAt = now;
    parseAndEmit(line, consumer);
}
```

**超时值按 provider 配置**——Ollama 是本地推理，冷启动要把模型加载进显存，首字节可能 60 秒以上；云 API 通常 2–5 秒。一套值套不住。

**不等式必须成立**（任一跳配反，故障现场会干净得什么都查不到）：

```
Nginx proxy_read_timeout (360s)  >  SseEmitter (300s)  ≥  上游整体超时 (300s)
```

### 3.3 线程隔离：两级

**第一级——业务线程池按用途隔离**，至少两个，绝不共用：

| 池 | 用途 | 配置 | 不隔离会怎样 |
|---|---|---|---|
| `llm-chat-` | SSE 对话编排 | **core 32 / max 64 / queue 16** | — |
| `kb-index-` | 文档解析、分块、向量化 | core 2 / max 4 / queue 64 | 一次批量导入**把对话线程全吃光**，所有人卡死 |

> ⚠️ **`queue` 必须小。** JDK 线程池的扩容顺序是「核心满 → 进队列 → 队列满才扩到 max」。`core 16 / queue 128` 意味着第 17～144 个请求全部排队、线程数永远停在 16——对分钟级长任务是致命的：第 17 个用户要等前面一整轮对话结束才轮到他，而池里还有 48 个线程从没被用上。
>
> **这一条修正了 `hify/CLAUDE.md` 里的 `core 16 / max 64 / queue 128`。**

拒绝策略用 `AbortPolicy`，捕获后返回明确错误「当前对话数已达上限，请稍后重试」——**不要用 `CallerRunsPolicy`**，那会让 Tomcat 线程去跑分钟级任务。

**第二级——每个 provider 一个信号量**，防止单一慢上游吃光整个线程池：

| provider | 并发上限 | 理由 |
|---|---:|---|
| **Ollama** | **3** | 本地单机推理，超过显存并发能力后是**所有请求一起变慢**，不是排队而是集体劣化 |
| OpenAI / Claude / Gemini | 20 | 云端弹性，瓶颈在自己这边不在对方 |

Ollama 这个数字最容易配错——「本地不要钱可以随便打」的直觉是错的，它是最脆弱的一环。

**内存核算**：64 线程 × 1MB 栈 = 64MB 堆外；加 Metaspace 约 100MB、堆 512MB，总计约 680MB，1Gi 容器有余量。**不要把 max 调到 128 以上。**

### 3.4 熔断

引入 **`resilience4j-circuitbreaker`**（单个 jar、纯内存、零外部依赖、不增加运维负担）。这是一期唯一新增的依赖。

**为什么值得**：Ollama 停掉以后，每个请求都要等满 3 秒连接超时。50 个人轮流试就是持续的集体卡顿。熔断打开后立即失败，用户马上看到「模型服务不可用」而不是转圈 3 秒。

```java
CircuitBreakerConfig.custom()
    .slidingWindowType(SlidingWindowType.TIME_BASED)   // ★ 时间窗,不是计数窗
    .slidingWindowSize(60)                             // 60 秒窗口
    .minimumNumberOfCalls(5)
    .failureRateThreshold(50)                          // 失败率 > 50% 打开
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .permittedNumberOfCallsInHalfOpenState(2)
    .recordExceptions(IOException.class, TimeoutException.class)
    .ignoreExceptions(BizException.class)              // ★ 业务错误不计入
    .build();
```

**两个必须注意的：**

1. **用时间窗，不用计数窗。** 3–5 QPS 下，计数窗要好几分钟才填满 20 次调用——熔断永远来不及触发。
2. **`ignoreExceptions(BizException.class)`。** 401（Key 配错）、400（上下文超长）是**请求自己的问题，不是上游故障**，计入失败率会让熔断被无辜打开，把一个配置错误放大成服务不可用。

**熔断器按 providerId 分实例**——OpenAI 挂了不能影响 Ollama。

### 3.5 代码落点

全部位于 `hify-provider` 的 `client` 包，用装饰器把「协议」与「容错」分开：

```
com.hify.provider
├── service/ChatModelClient.java          @ModuleApi 对外契约(接口)
└── client/
    ├── OpenAiCompatChatModelClient.java  只管协议
    ├── AnthropicChatModelClient.java     只管协议
    ├── ResilientChatModelClient.java     ★ 装饰器:熔断 → 舱壁 → 超时
    └── StreamReader.java                 四道闸的读流循环
```

装饰顺序即执行顺序：**熔断（最外，失败最快）→ 舱壁 → 实际调用（内含超时）**。

`client` 包只依赖方法入参（`baseUrl` / 解密后的 `apiKey` / `modelName` / 配置对象），**不注入 Mapper、不读 Entity、不读 Spring 配置**——保持它可被原样抽成 jar。

### 3.6 验收：故障注入清单

**做完必须逐条验过，否则等于没做。** 这五条是本决策的验收标准：

| # | 注入方式 | 期望现象 |
|:--:|---|---|
| 1 | 把某 provider 的 `baseUrl` 改成黑洞地址（如 `10.255.255.1`） | 3 秒内失败（非挂起）；5 次调用后熔断打开；**其它 provider 的对话完全正常** |
| 2 | mock 一个接受连接但永不响应的服务 | 30 秒后首字节超时，明确报错 |
| 3 | 流输出到一半 kill 掉 mock 服务 | 30 秒后流间隔超时；**前端已收到的内容保留**，不重试（首字节后不重试） |
| 4 | 停掉 Ollama，同时用 OpenAI 对话 | OpenAI 对话不受任何影响 |
| 5 | 并发打满 64 条对话后再发一条 | 明确返回「对话数已达上限」，**不是无限期排队** |
| 6 | 对话进行中关闭浏览器标签页 | 15 秒内（心跳周期）服务端释放资源并**取消上游请求**，日志可见 |

第 6 条是省钱的关键——不取消上游，用户关了页面 token 还在烧。

## 四、第二件：Nginx 开启 gzip

### 4.1 ⚠️ 唯一红线：`/api/` 必须保持 `gzip off`

**gzip 与 SSE 直接冲突。** nginx 压缩时会缓冲输出直到攒够一个压缩块才下发——**打字机效果会完全消失**，用户看到的是转圈几十秒然后整段文字一次蹦出。

所以**不能全局开 gzip**，必须按 location 分开：

```nginx
# ── 静态资源:开 gzip ──
location / {
    root /usr/share/nginx/html;
    try_files $uri $uri/ /index.html;

    gzip on;
    gzip_vary on;
    gzip_min_length 1024;              # 小文件压了反而更大
    gzip_comp_level 5;                 # 5 是压缩比与 CPU 的平衡点,别用 9
    gzip_types
        text/plain text/css
        application/javascript application/json
        application/xml image/svg+xml font/woff2;
    # ★ 绝不要把 text/event-stream 加进 gzip_types
}

location = /index.html {
    add_header Cache-Control "no-cache";
}

# ── API:显式关闭 ──
location /api/ {
    proxy_pass http://hify-app:8080;
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    gzip off;                          # ★ 红线
    proxy_buffering off;               # ★ 红线
    proxy_cache off;

    proxy_read_timeout 360s;
    proxy_send_timeout 360s;
    client_max_body_size 50m;
}
```

**三条硬规则：**

1. **`/api/` 下 `gzip off` + `proxy_buffering off`，两个都要。** 只关一个不够。
2. **`gzip_types` 里绝不能出现 `text/event-stream`**，也不要用通配写法。
3. **不要在 `http {}` 块里全局 `gzip on` 然后指望 location 覆盖**——写在 location 里更不容易被后来的改动带偏。

> nginx 默认的 `gzip_types` 只有 `text/html`，理论上不会压 `text/event-stream`。但一旦有人为了压 JSON 而扩展 `gzip_types`，很容易顺手加宽——显式 `gzip off` 是唯一可靠的防护。

### 4.2 收益的诚实核算

Vue 3 + Element Plus 的生产包典型体积约 **1.5MB**，gzip 后约 **450KB**，省下约 1MB。

| 访问网络 | 节省时间 | 可感知 |
|---|---:|:---:|
| 千兆内网 | 约 20ms | ❌ 基本无感 |
| 百兆内网 | 约 80ms | 🟡 勉强 |
| **VPN / WiFi / 居家办公（5–10 Mbps）** | **约 1–1.6 秒** | ✅ **明显** |

**结论：在办公室内网收益有限，但远程访问场景收益显著，而成本是一行配置。做。**

不做 brotli——压缩率再高约 15%，但 nginx 官方镜像不带该模块，要换镜像或自编译。**用一行换 15% 不划算，这条不在一期。**

## 五、明确不做的，及其触发条件

**这一节和第一节同等重要。** 列出来是为了：① 后续有人提议时能直接对照；② 触发条件到了能认出来。

| 事项 | 不做的理由 | 触发条件 | 到时候做什么 |
|---|---|---|---|
| **上下文裁剪** | 影响单个会话，不级联 ⚠️ 见下 | 单会话超过约 20 轮 | 保留系统提示 + 最近 10 轮；RAG 结果不进历史 |
| **批量 embedding** | 影响一次导入操作，用户可等 | 单次导入 > 20 篇文档 | `input` 传数组，每批 64 段 |
| **文档解析流式化** | 有 10MB 上传限额兜底 | 出现导入相关 OOM | 流式分块，不整体读入 |
| **pgvector 建索引** | 万级分段前顺序扫描足够快 | 分段数 > 1 万 **或** 表体积 > 64MB | 建 HNSW；注意 `maintenance_work_mem` 在 512Mi 容器可能 OOM，需维护窗口 |
| **消息表归档** | 年增量约 73 万行，远未到 | `chat_message` > 500 万行 | 冷热分离或分区 |
| **应用多副本** | 部署基准已定单副本 | 峰值并发 SSE > 50 | 先解决文件存储，再加副本 |
| **WebFlux** | 真正的上限是业务线程池不是 Web 层 | 峰值并发 SSE 持续 > 500 | 先换非阻塞 HTTP 客户端（只动一个包），大概率轮不到 WebFlux |

### 5.1 ⚠️ 两点必须说明

**第一，上下文裁剪不是性能优化，是功能完整性问题。** 不做的话，单个会话到 20–30 轮时输入 token 会累积到接近上下文窗口，**表现为 400 报错、该会话再也无法继续**。它的爆炸半径确实只有一个会话（所以按本决策的判据排在一期之外，这个判断成立），但它是「功能坏掉」而不是「变慢」。

**处置**：一期不实现裁剪，但**必须把这个失败翻译成用户看得懂的提示**——捕获上下文超长的 400 错误，返回「本次对话已过长，请开启新会话」并在前端给一个「新建会话」按钮。这是几行代码，属于第一件事里「失败降级」的一部分，不构成新增工作项。

**第二，`chat_message` 复合索引不是工作项，是建表脚本的正确写法。**

```sql
KEY idx_conversation_id (conversation_id, id)
```

它不占一期工时——写建表 Flyway 脚本时顺手一行。**但漏了以后代价很高**：百万行表上补索引要长时间锁表，对单副本部署等于服务中断。同类的还有 `kb_segment_vector (kb_id, document_id)`、`chat_conversation (creator_id, update_time)`。

**这两条都不改变「一期只做两件事」的决策**，只是把它们归到正确的位置：一个是错误提示，一个是建表规范。

## 七、一句话结论

> **一期只做两件：LLM 调用的「超时 + 线程隔离 + 熔断」，以及 Nginx 静态资源开 gzip。**
> **判据是爆炸半径——LLM 上游故障是这套架构里唯一一个会同时打到所有用户的路径，其余瓶颈都只造成局部劣化。**
> **超时、隔离、熔断必须一起做：超时产生失败信号，熔断消费信号快速失败，隔离限制影响范围；缺任何一环另外两环失效——尤其是没有超时，熔断器统计到的失败率永远是 0，等于没装。**
> **gzip 的唯一红线是 `/api/` 必须 `gzip off` + `proxy_buffering off`，否则 SSE 的打字机效果直接消失。**
