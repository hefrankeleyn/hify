# Hify 容量规划与运维

> 场景：AI Agent 平台 · Docker Compose 本地部署 · 目标 20–50 人同时在线 · 主要压力在对话接口（流式 SSE）
> 技术栈见 `../02-产品决策/02_Hify技术选型（基准）.md`
> 整理日期：2026-08-10

---

## 一、核心结论

> **QPS 不是瓶颈，并发 SSE 连接才是。**

20–50 人的对话型应用，请求速率低到几乎可以忽略；真正需要设计的是「同时保持打开的长连接」以及它们背后的线程与内存占用。

| 指标 | 估算值 | 说明 |
|------|--------|------|
| 对话接口峰值 QPS | **0.5–2** | 见下节推导 |
| 全站设计余量 | **3–5 QPS** | 含配置读取、日志查询、文件上传等 |
| 并发 SSE 连接（典型） | **约 5 条** | 稳态 |
| 并发 SSE 连接（最坏） | **50 条** | 所有人同时提问 |
| 设计目标 | **稳定支撑 50 条并发 SSE** | Spring Boot 单实例轻松覆盖 |

---

## 二、QPS 估算

### 推导前提

对话型应用的关键特征：**「同时在线」≠「同时在发请求」**。用户的时间绝大部分花在等待输出、阅读回答、思考下一个问题上。

单轮对话的时间构成：

| 阶段 | 耗时 |
|------|------|
| 提问（输入） | 20–60 秒 |
| 等待流式输出 | 5–30 秒（带 RAG / 工具调用可到 60 秒） |
| 阅读回答 | 30–120 秒 |
| **单轮周期合计** | **60–180 秒，中位数约 90 秒** |

另一个变量是**活跃率**：同时在线的人当中，真正处在对话循环里的比例。开着页面去干别的事是常态，典型活跃率 30–50%。

### 三档场景

| 场景 | 假设 | 计算 | QPS |
|------|------|------|-----|
| **典型** | 50 人在线，40% 活跃，90 秒/轮 | 50 × 0.4 ÷ 90 | **0.22** |
| **保守** | 50 人全部活跃，60 秒/轮 | 50 ÷ 60 | **0.83** |
| **突发峰值** | 全员被通知同时使用，30 秒/轮 | 50 ÷ 30 | **1.67** |

**对话接口峰值取 2 QPS。** 加上其它接口（Agent 列表、配置读取、会话日志查询、文件上传、前端轮询），全站按 **3–5 QPS** 做设计余量绰绰有余。

### 这个数字意味着什么

Spring Boot 单实例处理简单请求的能力在数千 QPS 量级。**3–5 QPS 相当于闲置。** 所以：

- 不需要负载均衡
- 不需要读写分离
- 不需要分库分表
- 不需要为「性能」做任何优化

所有工程精力应该投向**长连接管理**和**稳定性**。

## 三、并发 SSE 连接估算

并发连接数 = 同一时刻正处于「生成中」的会话数。

```
并发连接 = 在线人数 × 活跃率 × (单次生成耗时 ÷ 单轮周期)
```

| 场景 | 计算 | 并发连接 |
|------|------|----------|
| 典型 | 50 × 0.4 × (20 ÷ 90) | **≈ 4.4 条** |
| 较忙 | 50 × 0.6 × (30 ÷ 90) | **≈ 10 条** |
| 最坏（同时提问） | 50 × 1.0 | **50 条** |

**设计目标：50 条并发 SSE 连接。**

### 线程模型（最容易踩坑的地方）

**必须用 `SseEmitter`，不能用阻塞式写。** 原因是线程模型：

| 写法 | 线程占用 | 50 并发时 |
|------|----------|-----------|
| 阻塞式（`@ResponseBody` 里循环 write） | 每条连接**独占**一个 Tomcat 工作线程，直到生成结束 | 50 个工作线程被占死数十秒 |
| `SseEmitter`（异步） | 请求线程返回 emitter 后**立即释放**，后续写入走异步线程 | Tomcat 线程池不受影响 |

但异步不等于免费——**执行 LLM 调用的那个线程池需要自己配**：

```yaml
# 关键：不要用默认的 SimpleAsyncTaskExecutor
# 它每次新建线程且无上界，50 并发下会持续创建线程直至 OOM
```

建议配置一个专用 `ThreadPoolTaskExecutor`：

| 参数 | 建议值 | 理由 |
|------|--------|------|
| corePoolSize | 16 | 覆盖典型并发 |
| maxPoolSize | 64 | 覆盖最坏 50 并发 + 余量 |
| queueCapacity | 128 | 突发缓冲 |
| keepAlive | 60s | 回收空闲线程 |
| 拒绝策略 | CallerRuns 或明确报错 | 不要静默丢弃 |

Tomcat 侧保持默认（`threads.max=200`）即可，无需调整。

## 四、内存估算

JVM 堆设为 `-Xmx512m`，核算是否够用：

| 项 | 占用 | 说明 |
|----|------|------|
| Spring Boot 基础 + MyBatis-Plus + 连接池 | 150–200 MB | 常驻 |
| 50 条 SSE 连接的会话上下文 | ≈ 10 MB | 每条对话历史几十 KB~200 KB |
| **知识库向量（内存检索方案）** | **20–40 MB** | 5000 chunk × 1024 维 × 4 字节 ≈ 20 MB |
| 其它（缓冲、临时对象） | 50 MB | |
| **合计** | **约 250–300 MB** | 512m 堆有余量 |

### 两个必须注意的点

**1. 容器内存 ≠ 堆内存。** JVM 除堆外还有 Metaspace、线程栈（64 线程 × 1MB）、Direct Buffer、GC 开销、JVM 自身。

> **建议：容器内存限制设 1GB，堆设 512m。** 只限制容器不设 `-Xmx`，JVM 可能按宿主机内存计算默认堆大小而被 OOM Kill。

**2. 向量数据是唯一会持续增长的内存项。**

| 分段数量 | 内存占用（1024 维 float） | 判断 |
|----------|--------------------------|------|
| 5,000 | ≈ 20 MB | 轻松 |
| 20,000 | ≈ 80 MB | 仍可接受 |
| 50,000 | ≈ 200 MB | 512m 堆开始吃紧 |
| 100,000+ | ≈ 400 MB+ | **必须改用专用向量库** |

> **触发阈值：向量分段数超过 20,000 条时重新评估存储方案。** 一期只支持 TXT、内部文档量有限，短期不会触及。

## 五、缓存策略

### 三条原则

1. **只缓存变更极少的配置。**
2. **绝不缓存 LLM 响应。** 相同问题在不同上下文下答案不同，命中率极低；而一旦命中会产生「明明换了个问法却给一模一样答案」的诡异体验。内部工具也没有成本压力去做这件事。
3. **对话历史直读库。** 20–50 人规模下 MySQL 主键查询是微秒级，加一层缓存只是引入一致性问题。

### 逐项决策

| 数据 | 缓存 | 位置 | TTL | 失效策略 | 理由 |
|------|------|------|-----|----------|------|
| **模型提供商配置**（baseURL / apiKey / model） | ✅ | Redis | 长期 | 配置更新时主动删除 | 每次对话都要读，几乎不变 |
| **Agent 配置**（提示词 / 模型 / 知识库 / 工具绑定） | ✅ | Redis | 10 分钟 | 更新时主动删除 | 每次对话开头读一次 |
| **MCP 工具清单**（`tools/list` 结果） | ✅ | Redis | 5 分钟 | 定时刷新 + 手动刷新 | 既省一次网络往返，**也是 MCP Server 挂掉时的容错兜底** |
| **知识库向量** | ✅ | **进程内存** | 常驻 | 文档增删时重建 | 检索是热路径，绝不能走网络 |
| **登录态 / 会话** | ✅ | Redis | 与登录有效期一致 | — | 标准做法 |
| 对话历史 | ❌ | — | — | — | 直读 MySQL 足够快，缓存徒增一致性问题 |
| **LLM 响应** | ❌ | — | — | — | 命中率极低 + 体验反直觉，见原则 2 |
| 知识库检索结果 | ❌ | — | — | — | 问题措辞千变万化，一期不做 |

### 一个诚实的观察

一期 Redis 实际只承担**配置缓存 + 登录态**两件事，数据量在几 MB 级别——这属于「杀鸡用牛刀」。

由于是**单实例部署，不存在多实例缓存一致性问题**，用 Caffeine 进程内缓存完全能覆盖这两个场景，可以再省一个容器。

> **保留 Redis 的理由**：它已在技术栈里，运维成本接近零；且一旦将来需要多实例、分布式锁、或把 SSE 连接状态外置，Redis 是现成的。**建议保留，但不必强行给它找活干。**

## 六、运维事项清单

### A. 部署与配置

| 事项 | 要点 |
|------|------|
| **Compose 服务清单** | app / mysql / redis /（可选）nginx |
| **容器内存限制** | app 限 1GB，JVM `-Xmx512m`（见第四节） |
| **启动依赖顺序** | MySQL 未就绪时 app 会启动失败。`depends_on` 只保证启动顺序不保证就绪——必须配 `healthcheck` + `condition: service_healthy`，或给 app 加 `restart: unless-stopped` |
| **时区** | 容器默认 UTC。JVM、MySQL、应用三者时区不一致会导致时间字段错乱 → 统一设 `Asia/Shanghai` |
| **字符集** | MySQL 必须 `utf8mb4` / `utf8mb4_unicode_ci`，否则 emoji 和生僻字直接插入失败 |
| **配置外置** | API Key 等敏感配置走环境变量或 `.env`，不进镜像、不进 Git |

### B. SSE 专项（最需要提前想清楚的部分）

| 事项 | 要点 |
|------|------|
| **实现方式** | `SseEmitter`，不用阻塞式 `@ResponseBody`（见第三节） |
| **超时设置** | ⚠️ 需确认，见下方「待确认事项」 |
| **心跳保活** | 每 15–30 秒发一个注释行（`: heartbeat\n\n`）。SSE 的断连往往要等到写入失败才被发现，心跳是主动探测手段 |
| **Nginx `proxy_buffering off`** | **必须关**，否则 Nginx 会攒批下发，完全失去打字机效果 |
| **Nginx `proxy_read_timeout`** | 默认 60 秒会直接切断长连接 → 调到大于 SSE 超时 |
| **Nginx gzip** | 对 SSE 应关闭，压缩会引入缓冲 |
| **`X-Accel-Buffering: no`** | 响应头加上，作为关闭缓冲的双保险 |
| **断连清理** | 在 `onCompletion` / `onTimeout` / `onError` 回调里释放资源，并**取消上游 LLM 请求**——否则用户关页面了 token 还在烧 |
| **重启影响** | 应用重启时所有 SSE 连接断开，前端需要有重连提示，不能白屏 |

### C. 数据与持久化

| 事项 | 要点 |
|------|------|
| **volume 挂载** | MySQL 数据目录、上传文档目录、日志目录。**容器内不存任何数据** |
| **数据库版本管理** | 用 Flyway 或 Liquibase。一个人开发也需要——否则改表全靠手工记忆，重装环境时必然出错 |
| **备份** | `mysqldump` 定时任务 + 上传文档目录打包。内部系统同样会丢数据，且没人替你兜底 |
| **对话历史增长** | 50 人 × 20 轮/天 × 2 条 × 2KB ≈ **4 MB/天 ≈ 1.5 GB/年**。可接受，但要有清理策略（如保留 6 个月） |
| **上传文件限额** | 单文件大小 + 总容量限制，防止磁盘被打满 |

### D. 可观测性

| 事项 | 要点 |
|------|------|
| **健康检查** | Spring Boot Actuator `/actuator/health`，供 Compose healthcheck 和人工排查用 |
| **会话日志落库** | 输入 / 输出 / 耗时 / token 数 / 错误信息。**token 数顺手一起存**，以后做统计不用改表 |
| **应用日志轮转** | logback 配 `maxFileSize` + `maxHistory`，否则磁盘迟早写满 |
| **关键指标** | 并发 SSE 连接数、LLM 调用 P95 耗时、LLM 调用失败率、token 消耗量 |
| **后期演进** | Prometheus + Grafana，一期不做 |

### E. 故障与降级

**核心原则：LLM 和外部依赖一定会失败，每条失败路径都要有明确行为。**

| 故障 | 期望行为 |
|------|----------|
| **LLM 供应商超时/不可用** | 明确的错误提示推给前端，**不要静默失败或无限等待**。连接超时 10 秒；流式场景用「N 秒无数据则超时」而非总时长超时 |
| **MCP Server 不可用** | 工具清单走缓存兜底；工具调用失败不应中断对话主流程，把失败作为工具结果交给模型让它自己处理 |
| **向量检索失败** | 降级为不注入知识库，对话仍然可用 |
| **MySQL 连接池耗尽** | HikariCP `maximum-pool-size` 设 10–20 即可（QPS 低，不需要大池）；关键是设合理的 `connection-timeout` 让失败快速暴露 |
| **磁盘写满** | 日志轮转 + 上传限额 + 定期清理，三道防线 |

### F. 安全

| 事项 | 要点 |
|------|------|
| **API Key 存储** | 模型供应商的 Key **不能明文进库、不能进日志**。至少加密存储，日志输出做脱敏 |
| **内网 ≠ 免防护** | 至少要有登录；会话日志能归因到人 |
| **上传文件校验** | 类型白名单 + 大小限制 |
| **MCP Server 白名单** | MCP 工具可能包含危险操作（文件删除、命令执行）。一期应限制可接入的 Server 范围，不允许任意用户接任意 Server |

## 七、待确认事项

**SSE 超时时长与技术栈基准文档存在出入，需要拍板。**

- `CLAUDE.md` 与技术选型文档记录的是 **60 秒超时，用于防僵尸连接**。
- 但一次带 RAG + 多轮工具调用的生成，**耗时可能超过 60 秒**——按 60 秒硬超时会把正常的长回答截断。

两个目标其实是不同的东西：

| 目标 | 合适手段 |
|------|----------|
| 防止僵尸连接（客户端已断开但服务端不知道） | **心跳**（每 15–30 秒），写入失败即可感知断连 |
| 防止单次生成无限挂起 | **超时**，应设为「最长可能生成时间 + 余量」 |

**建议：`SseEmitter` 超时设 5 分钟，配合 15 秒心跳做断连检测。** 用心跳解决僵尸连接，用超时兜底异常挂起，各司其职。

如果坚持 60 秒，需要接受长回答被截断的风险，或者在应用层做分段续传。**这一条由你确认后我再同步回技术选型文档。**

## 八、上线前检查清单

- [ ] `-Xmx512m` 已设置，容器内存限制 1GB
- [ ] 专用 `ThreadPoolTaskExecutor` 已配置，未使用默认 `SimpleAsyncTaskExecutor`
- [ ] Nginx `proxy_buffering off`、`proxy_read_timeout` 已调大、gzip 已关
- [ ] SSE 心跳已实现，断连回调里会取消上游 LLM 请求
- [ ] MySQL 字符集 `utf8mb4`，三方时区统一
- [ ] MySQL data / 上传文档 / 日志 三个 volume 已挂载
- [ ] Flyway（或 Liquibase）已接入，schema 变更可版本化
- [ ] 备份脚本已就位并验证过**恢复**流程（只备份不验证等于没备份）
- [ ] 日志轮转已配置
- [ ] API Key 加密存储，日志已脱敏
- [ ] 上传文件大小/类型限制已生效
- [ ] LLM 失败、MCP 失败、检索失败三条降级路径已实测
