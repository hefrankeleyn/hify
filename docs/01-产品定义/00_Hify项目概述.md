# Hify 项目概述

## 一、产品定位

**Hify** 是一个**简化版 AI Agent 平台**（参考 Dify 理念裁剪而来），面向**团队内部 20–50 人**使用，**本地部署**、数据不出内网。

> 一句话：让用户不用从零写代码，就能把「模型 + 内部数据 + 工具」组装成能发布给同事用的 AI 应用。

**核心约束（一切取舍的依据）**：

| 约束 | 含义 |
|------|------|
| **一个人开发** | 开发效率第一，凡「大而全」一律降级或不做 |
| **内部 20–50 人** | 不需要规模化 / 计费 / 对外获客，性能不是瓶颈 |
| **本地部署** | 数据不出内网，容器越少越好 |

> 取舍标准是**最匹配当前约束**，不是技术最全。

## 二、做什么（一期）

### ✅ 做

| 功能 | 说明 |
|------|------|
| **多模型提供商管理** | OpenAI、Claude、Gemini、Ollama |
| **Agent 创建与配置** | 平台的中心对象：选模型、绑工具、设系统提示词 |
| **对话引擎** | 流式响应、多轮对话、上下文管理 |
| **MCP 工具接入** | Agent 通过 MCP 协议调用外部工具，区别于普通聊天机器人的关键能力 |
| **管理控制台** | 模型管理、Agent 配置、对话界面 |

### 🟡 降级做

| 功能 | 降级方式 |
|------|----------|
| **知识库 + RAG** | 一期只支持 **TXT**，**固定长度分块**：上传 → 分块 → 向量检索 → 注入 |
| **工作流** | 用 **JSON 配置**，线性 + 条件分支，不做可视化拖拽 |

### 建设顺序

平台地基 → 能对话 → 能干活（MCP）→ 能用数据（RAG）→ 能编排（工作流）

---

## 三、不做什么

| 不做 | 理由 |
|------|------|
| **可视化工作流拖拽编排** | 前端实现极重，一期以 JSON 配置替代 |
| **多租户 / 权限体系** | 内部团队不需要隔离（保留最简登录 + 两档角色） |
| **插件市场、计费系统** | 超出一人开发范围 |
| **文本生成应用、WebApp 发布、嵌入组件** | Agent 一种应用类型即可覆盖，发布形态收敛到管理控制台内 |
| **标注与微调** | 超出一人开发范围 |
| **依赖 LangChain 等 Python 专属框架** | RAG 向量化调 API、工具走 MCP，均在 Java 栈内实现 |

## 四、技术栈

| 层 | 选型 |
|----|------|
| **后端** | Spring Boot 3.x + MyBatis-Plus + MySQL 8.x + Redis 7.x |
| **前端** | Vue 3 + TypeScript + Vite + Element Plus |
| **容器化** | Docker + Docker Compose |

**选型理由**：开发者最熟此栈（单人效率第一）+ 一套技术栈不分裂 + Java 的 AI SDK 够用。

**明确接受的代价**：新模型特性支持滞后、部分 Python 独有库需自行实现、社区答案少。**已否决**「起 Python 边车服务」的逃生口——一个人一套栈，不分裂。

## 五、部署与运维预期

| 维度 | 预期 |
|------|------|
| **部署** | Docker Compose 一键启动，单机部署 |
| **容量** | 20–50 人同时在线；峰值 **3–5 QPS** |
| **真正的瓶颈** | **不是并发，是 LLM 长连接（SSE）管理**。设计目标：50 条并发 SSE |
| **JVM** | `-Xmx512m`，**容器内存限制 1GB**（只限容器不设 `-Xmx` 会被 OOM Kill） |
| **缓存** | Redis **Cache-Aside**：配置信息 + 会话上下文。**不缓存 LLM 响应** |
| **持久化** | MySQL / 向量数据 / 上传文档必须挂 volume，**容器内不存任何数据** |
| **监控** | 起步 Actuator + 日志；后期接 Prometheus + Grafana |
| **扩容** | 一期单机。架构做模块化设计，不堵死后续拆分的路 |

### SSE 三条硬要求

1. 用 `SseEmitter`，**不用**阻塞式 `@ResponseBody`（否则每条连接独占一个 Tomcat 线程）
2. **自配** `ThreadPoolTaskExecutor`，不用默认 `SimpleAsyncTaskExecutor`（无上界建线程会 OOM）
3. Nginx `proxy_buffering off`（否则流式被攒批，失去打字机效果）

### 失败降级（LLM 和外部依赖一定会失败）

| 故障 | 期望行为 |
|------|----------|
| LLM 不可用 | 明确报错推给前端，不静默失败、不无限等待 |
| MCP Server 不可用 | 工具清单走缓存兜底；调用失败作为工具结果交回模型，不中断对话 |
| 向量检索失败 | 降级为不注入知识库，对话仍可用 |
| 用户断连 | 回调里释放资源并**取消上游 LLM 请求**，否则关了页面 token 还在烧 |

## 六、当前待定项

| # | 待定项 | 倾向 |
|---|--------|------|
| 1 | **SSE 超时时长** | 基准记的是 60 秒防僵尸连接，但带 RAG + 工具调用的生成可能超 60 秒被截断。倾向：**超时 5 分钟 + 15 秒心跳**，两个手段各司其职。**未拍板** |
| 2 | **向量存储方案** | 一期不引向量库：向量存 MySQL JSON，检索时内存暴力计算。超过约 20,000 条分段再重评 |
| 3 | **Java 侧 AI 框架** | Spring AI / LangChain4j 二选一，倾向一期先不引，直接用 OpenAI 兼容客户端 |
| 4 | **变更与回滚约定** | 尚未定义：镜像 tag 策略、schema 变更向前兼容、发布时 SSE 断连的前端提示 |
