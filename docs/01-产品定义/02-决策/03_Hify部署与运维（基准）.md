# Hify 部署与运维（基准）

> 📌 **本文档是 Hify 部署形态、容量目标与运维策略的唯一依据（source of truth）**，如与其它任何文档冲突，**以本文档为准**。

## 一、决策前提

沿用同一组约束，运维决策全部由它们推导而来：

| 约束 | 对部署运维的含义 |
|------|------|
| **一个人开发** | 没有专职运维。凡「需要长期照看」的组件一律不引入，能省一个容器就省一个。 |
| **面向团队内部 20–50 人** | 峰值 3–5 QPS，**性能不是问题**。工程精力不投向性能优化。 |
| **本地部署** | 数据不出内网，单机起步，部署过程必须简单到能一条命令重来。 |

## 二、决策总表

| 维度 | 基准决策 |
|------|----------|
| **部署方式** | **Docker Compose 一键启动**，单机部署 |
| **JVM 内存** | **`-Xmx512m`**，显式设上限，防止容器被 OOM Kill |
| **用户量** | **20–50 人同时在线**，单机部署够用 |
| **QPS** | **峰值 3–5 QPS**。瓶颈在 **LLM 长连接（SSE）**，不在并发 |
| **监控** | 起步 **Spring Boot Actuator + 日志**；后期接 **Prometheus + Grafana** |
| **扩容** | **一期单机**。架构上不堵死扩容的路——做模块化设计，为后续拆分留口子 |

## 三、逐项决策理由

### 1. 部署方式：Docker Compose 一键启动

一个人的项目，部署环节的价值不在「优雅」，在**可重复**。Compose 的意义是把 app / MySQL / Redis /（可选）Nginx 的启动顺序、网络、卷、环境变量固化成一个文件——换台机器、重装环境、演示给同事看，都是同一条命令。

**明确不做**：K8s、Helm、CI/CD 流水线编排。20–50 人的内部平台上这些是纯负债。

### 2. JVM：显式设 `-Xmx512m`

这条不是「省内存」，是**防事故**。

> 容器里只限制容器内存、不设 `-Xmx`，JVM 可能按**宿主机**内存计算默认堆上限（默认约为可用内存的 1/4），进而申请远超容器限额的堆，触发 OOM Kill——表现为进程毫无征兆地消失，日志里连异常都没有。

**配套要求：容器内存限制设 1GB，堆设 512m。** 堆外还有 Metaspace、线程栈、Direct Buffer、GC 与 JVM 自身开销，二者之间必须留出这段差额。

内存够不够的核算见 `../01-产品定义/03_Hify容量规划与运维.md` 第四节，结论是常态占用约 250–300 MB，512m 有余量；**唯一会持续增长的是知识库向量**，超过约 20,000 条分段时需重新评估存储方案。

### 3. 用户量与 QPS：性能不是瓶颈，长连接才是

> **同时在线 ≠ 同时在发请求。**

对话型应用中，用户的时间绝大部分花在输入、等待输出、阅读回答上，单轮周期中位数约 90 秒。50 人在线按典型活跃率折算，对话接口峰值不过 **0.2–2 QPS**；全站按 **3–5 QPS** 留余量已绰绰有余。

Spring Boot 单实例处理简单请求的能力在数千 QPS 量级，**3–5 QPS 相当于闲置**。因此明确不做：负载均衡、读写分离、分库分表、以及任何以「性能」为名的优化。

真正需要设计的是**同时保持打开的 SSE 长连接**，设计目标 **50 条并发**（最坏情况：所有人同时提问）。三条硬要求：

| 要求 | 说明 |
|------|------|
| 必须用 `SseEmitter` | 阻塞式 `@ResponseBody` 会让每条连接独占一个 Tomcat 工作线程数十秒 |
| 必须自配线程池 | 默认 `SimpleAsyncTaskExecutor` 无上界地新建线程，50 并发下会一路创建到 OOM |
| Nginx 必须 `proxy_buffering off` | 否则流式被攒批下发，完全失去打字机效果 |

### 4. 监控：先 Actuator + 日志，后 Prometheus + Grafana

分两步是因为**监控的价值取决于有没有人看**。一期一个人开发，指标体系再全也只会在出事时才被打开——那时 Actuator 的 `/actuator/health` 加一份结构化日志已经够定位问题，而 Prometheus + Grafana 意味着再多两个容器、两套配置、一套告警规则要长期维护。

**一期要做的（成本极低、后期无法补录）**：

| 事项 | 说明 |
|------|------|
| Actuator `/actuator/health` | 同时供 Compose healthcheck 和人工排查使用 |
| 会话日志落库 | 输入 / 输出 / 耗时 / **token 数** / 错误信息。token 数顺手一起存，以后做统计不用改表、不用回补数据 |
| 日志轮转 | logback 配 `maxFileSize` + `maxHistory`，否则磁盘迟早写满 |

**后期接入时要盯的四个指标**：并发 SSE 连接数、LLM 调用 P95 耗时、LLM 调用失败率、token 消耗量。

### 5. 扩容：一期单机，但不堵死路

「一期单机」是**部署决策**，不是**架构决策**。二者必须分开：部署可以最简，架构不能因此写死成无法拆分。

## 四、为扩容预留的口子

> 以下是执行层解读，用于落实「不堵死扩容的路」这一条基准决策，**不改变第二节的部署形态**。模块化设计的完整方案另行展开。

### 模块边界

按业务能力划分模块，与产品决策的五块主线对齐：

```
provider   多模型提供商管理
agent      Agent 创建与配置
chat       对话引擎（SSE）
knowledge  知识库 + RAG
tool       MCP 工具接入
workflow   工作流（JSON 配置）
```

### 四条不能破的规矩

| 规矩 | 为什么 |
|------|--------|
| **模块间只通过接口调用，不跨模块直连对方的 DAO / Mapper** | 这是拆分时代价最大的一类耦合。跨模块直连 DAO，等于把「以后能不能拆」这件事交给运气。 |
| **数据库层不跨模块 JOIN** | 一旦跨模块 JOIN 遍布代码，拆库时每一条 SQL 都要重写。宁可多查一次——3–5 QPS 下多一次查询的代价可以忽略。 |
| **状态外置，服务本身无状态** | 会话、登录态放 Redis / MySQL，不放 JVM 内存的静态变量。唯一的例外是知识库向量（进程内缓存，热路径不能走网络），而它本身就是可从库重建的派生数据。 |
| **文件存储走抽象接口** | 一期是本地磁盘 + volume，接口留住之后换对象存储的可能。 |

### 明确不为扩容做的事

不提前引入消息队列、不提前做服务注册发现、不提前抽 RPC、不提前分库。**留口子 ≠ 提前实现。** 这些在单机 3–5 QPS 下没有任何收益，却每一样都要长期维护。

### 单机瓶颈真正出现时的顺序

按「先动便宜的」排：先加 JVM 堆 / 容器内存 → 再把向量检索迁到专用向量库 → 最后才考虑多实例（届时需要外置 SSE 连接状态，Redis 已在栈内）。

## 五、运维硬性要求

> 这些不是可选优化，是**做不到就会出事**的项。完整清单见 `../01-产品定义/03_Hify容量规划与运维.md` 第六节。

| 类别 | 要求 |
|------|------|
| **持久化** | MySQL 数据 / 上传文档 / 日志三个目录必须挂 volume。**容器内不存任何数据。** |
| **启动依赖** | `depends_on` 只保证启动顺序、不保证就绪。必须配 `healthcheck` + `condition: service_healthy`。 |
| **时区与字符集** | 容器默认 UTC，JVM / MySQL / 应用三者时区必须统一为 `Asia/Shanghai`；MySQL 必须 `utf8mb4`。 |
| **schema 版本管理** | 接 Flyway 或 Liquibase。一个人开发也需要——否则改表全靠手工记忆，重装环境必出错。 |
| **备份** | `mysqldump` 定时任务 + 上传文档打包，且**必须验证过恢复流程**（只备份不验证等于没备份）。 |
| **配置外置** | API Key 等敏感配置走环境变量 / `.env`，不进镜像、不进 Git；不明文进库、不进日志。 |
| **缓存边界** | 只缓存变更极少的配置（Redis）；**不缓存 LLM 响应**；对话历史直读库。 |
| **降级路径** | LLM 不可用 → 明确报错不静默；MCP 不可用 → 工具清单走缓存兜底、失败作为工具结果交回模型；向量检索失败 → 降级为不注入知识库，对话仍可用。 |
| **断连清理** | `onCompletion` / `onTimeout` / `onError` 回调里释放资源并**取消上游 LLM 请求**，否则用户关了页面 token 还在烧。 |

## 六、待定项

| # | 待定项 | 说明 | 倾向建议 |
|---|--------|------|----------|
| 1 | **SSE 超时时长** | 基准记录的是 **60 秒超时，用于防僵尸连接**。但一次带 RAG + 多轮工具调用的生成耗时可能超过 60 秒，硬超时会截断正常的长回答。**「防僵尸连接」与「防无限挂起」是两个目标，应由两个手段分别解决。** | `SseEmitter` 超时设 **5 分钟**兜底异常挂起，配合 **15 秒心跳**做断连检测。若坚持 60 秒，需接受长回答被截断，或在应用层做分段续传。**待确认后同步回本文档与技术选型文档。** |
| 2 | **Redis 是否保留** | 一期 Redis 实际只承担配置缓存 + 登录态，数据量几 MB。单实例部署不存在多实例一致性问题，Caffeine 进程内缓存即可覆盖，可再省一个容器。 | **保留**。它已在技术栈内、运维成本接近零，且是将来多实例 / 分布式锁 / SSE 状态外置的现成依赖。但**不必强行给它找活干**。 |

---

## 七、一句话结论

> **Hify 一期 = Docker Compose 单机一键启动，JVM 堆 512m、容器限 1GB，按 20–50 人在线 / 3–5 QPS / 50 条并发 SSE 设计；不做任何性能优化，工程精力全投向长连接管理与失败降级；监控起步只用 Actuator + 日志；不扩容，但用模块化边界把将来能拆的路留着。**
