## 一、项目约束

**Hify**：基于 Dify 理念做的**简化版 AI Agent 平台**。

| 约束 | 含义 |
|------|------|
| **一个人开发** | 人力极其有限，凡「大而全的框架」一律降级或不做。 |
| **面向团队内部 20–50 人** | 不需要规模化 / 计费 / 对外获客。 |
| **本地部署** | 数据不出内网，模型走本地或少量云 API。 |

## 二、决策总表

![Hify 产品决策基准](../assets/hify-产品决策基准.jpg)

决策分三档：**做**（一期完整实现）｜**降级做**（一期交付，但砍到最简）｜**不做**（不在计划内）。

### ✅ 做

| Hify 功能 | 决策 | 理由 |
|------|------|------|
| **多模型提供商管理** | 做 | 平台基础 |
| **Agent 创建与配置** | 做 | 核心载体 |
| **对话引擎（流式、多轮）** | 做 | 交互通道 |
| **MCP 工具接入** | 做 | 区别于聊天机器人的关键能力 |
| **管理控制台** | 做 | 用户操作入口 |

### 🟡 降级做

| Hify 功能 | 决策 | 理由 |
|------|------|------|
| **知识库 + RAG** | 降级做 | 内部部署的核心价值，一期只支持 TXT |
| **工作流** | 降级做 | JSON 配置，不做可视化拖拽 |
| **可视化工作流编排** | 降级做 | 前端拖拽实现极重 |

### ❌ 不做

| Hify 功能 | 决策 | 理由 |
|------|------|------|
| **多租户 / 权限体系** | 不做 | 内部团队不需要隔离 |
| **插件市场 / 计费 / 微调** | 不做 | 超出一人开发范围 |

## 三、一句话结论

> **Hify 一期 = 一个本地部署的 Web 管理控制台。用户在上面创建并配置 Agent（接入统一管理的多模型提供商、通过 MCP 调用工具、挂载仅支持 TXT 的最小 RAG 知识库），通过流式多轮对话引擎使用；需要编排时用 JSON 配置工作流。不做多租户 / 权限体系，不做插件市场 / 计费 / 微调。**

---

## 四、建设顺序

1. **平台地基** —— 管理控制台骨架 + 多模型提供商管理（统一模型接入层）
2. **能对话** —— Agent 创建与配置 + 流式多轮对话引擎，跑通「建一个 Agent 并对话」
3. **能干活** —— MCP 工具接入，让 Agent 能调用工具
4. **能用数据** —— 知识库 + RAG 降级版（仅 TXT）
5. **能编排** —— 工作流 JSON 配置（不做可视化拖拽）

> 完成 1–5，Hify 一期主线即打通。

## 五、落地补充说明

> 以下为对上表各项的执行层解读，**不改变、不扩展**上表的决策范围。

| 决策项 | 落地要点 |
|------|------|
| **多模型提供商管理** | 「统一接入层」不等于要写数十家适配代码。当前 Ollama、vLLM、DeepSeek、通义、Kimi 等普遍提供 OpenAI 兼容端点，实现**一套 OpenAI 兼容客户端 + 配置化 baseURL / apiKey / model** 即可覆盖绝大多数供应商，是单人开发下杠杆最高的做法。 |
| **Agent 创建与配置** | Agent 是平台的中心对象，一期**只做这一种应用类型**。Dify 的 Chatbot / 文本生成 / Chatflow 都可由「Agent + 不同配置」表达（不配工具即 Chatbot，单轮即文本生成），不必拆成多种类型。 |
| **对话引擎** | 用 `SseEmitter` 实现流式（勿用阻塞式 `@ResponseBody`）；设 60 秒超时防僵尸连接；Nginx 需配 `proxy_buffering off`，否则流式被攒批、失去打字机效果。多轮上下文直读库，不缓存。 |
| **MCP 工具接入** | 一期性价比最高的一笔投入：对接一次协议即可复用现成工具生态。一期只做**入向**（把 MCP Server 当工具用）；「把 Agent 反向暴露成 MCP Server」不在一期范围，但 Agent 执行入口建议做成协议无关，便于后续加适配层。 |
| **管理控制台** | 创建 Agent、管理配置、发起对话的统一 Web 入口，同时承载会话日志查看。 |
| **知识库 + RAG** | 一期只支持 **TXT**：上传 → 分段 → 向量检索 → 注入。建议附带一个**检索测试入口**（输入问题看 Top-K 命中），成本极低但对调分段参数是刚需，否则效果好坏只能靠猜。PDF / Word 解析后置。 |
| **工作流** | 用 JSON 配置定义，不做可视化拖拽。最小节点集建议收敛为：LLM、知识检索、工具调用、条件分支。代码执行节点不做（沙箱是安全与运维的双重成本）。 |
| **可视化工作流编排** | 一期以 JSON 配置替代，完整拖拽式画布后置。 |
| **多租户 / 权限体系** | 不做租户隔离与细粒度 RBAC。**待确认**：是否保留最基础的登录与「管理员 / 普通用户」两档角色——见第六节。 |
| **插件市场 / 计费 / 微调** | 完全不做。工具扩展需求统一走 MCP，不另建插件体系。 |

## 六、决策表未覆盖的待定项

> 以下问题属于技术实现层面，决策表未涉及，需另行拍板。**不影响上表的功能范围。**

| # | 待定项 | 说明 | 倾向建议 |
|---|--------|------|----------|
| 1 | **向量存储方案** | 技术栈定的是 MySQL 8.x，而 **MySQL 8.x 无原生向量类型**（VECTOR 为 9.0 引入）。需决定：加一个向量库容器（Chroma / Qdrant / pgvector），还是另寻他法。 | 一期**不引入向量库**：向量存 MySQL JSON 字段，检索时载入内存做暴力余弦相似度。TXT 场景分段量约几百至几千条，毫秒级即可返回，省一个容器和一套运维；数据量涨上来再迁。 |
| 2 | **登录与角色** | 决策表「不做多租户 / 权限体系」通常指租户隔离与 RBAC，是否连基础登录也不做需明确。20–50 人共用时，若无账号则会话日志无法归因、Agent 配置可能互相覆盖。 | 保留**最简登录 + 管理员 / 普通用户两档角色**，不做更细的权限模型。 |
| 3 | **内置工具** | 接入 MCP 后，自建内置工具的边际价值大幅下降。 | 仅保留 1 个 HTTP 请求工具兜底，不预置搜索 / 绘图 / 天气等。 |

## 附：关键名词

- **MCP（Model Context Protocol）**：标准化的工具 / 上下文接入协议。接入后可复用现成的开源工具服务器生态，是 Hify 让 Agent「能干活」的关键选型。
- **RAG（检索增强生成）**：把上传文档向量化、检索后注入提示词，让 Agent 基于内部数据回答。
- **降级做**：一期就交付该功能，但砍到最简版本（如 RAG 只支持 TXT、工作流只用 JSON），以保证产品完整性、避免日后大改。
