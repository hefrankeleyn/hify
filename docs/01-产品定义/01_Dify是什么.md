# Dify 是什么

> 对象：Dify（https://dify.ai）
> 整理日期：2026-08-10
> 说明：本文回答「Dify 到底是什么、解决什么问题」，是理解后续所有文档的入口。
> 内部由哪些模块组成，见同目录 `02_Dify核心功能模块梳理.md`。

---

## 一、一句话

**Dify 是一个「搭建 AI 应用的低代码平台」**——让你不用从零写代码，就能把大模型（GPT、Claude、通义等）+ 你自己的数据 + 各种工具，组装成一个**能上线、能被别人使用**的 AI 应用。

关键词是「**组装**」和「**能被别人用**」。它不是给你一个更好的聊天窗口，而是让你把 AI 能力**变成一个产品交付出去**。

---

## 二、它解决什么问题

### 问题的根源：能调通模型 ≠ 能做出产品

调用大模型 API 本身很简单，十几行代码就能跑通。但从「跑通 demo」到「同事能天天用的东西」，中间隔着一堆**又脏又必须做**的工程活：

| 你想要的 | 实际要做的脏活 |
|---|---|
| 「换个模型试试效果」 | 对接各家 API，处理鉴权、限流、超时、流式协议差异、报错格式不统一 |
| 「让它读我们公司的文档」 | 文档解析 → 切分 → 向量化 → 存向量库 → 检索 → 拼进提示词，还要调效果 |
| 「让它记得上一句说了什么」 | 会话存储、上下文窗口管理、历史裁剪策略 |
| 「让它能查数据库 / 发邮件」 | 工具定义、Function Calling 协议、多轮工具调用循环、失败重试 |
| 「让同事能打开就用」 | 写前端聊天界面、做流式渲染、加访问控制、部署上线 |
| 「上线后出问题能查」 | 会话日志、Token 与费用统计、执行链路追踪 |

这些活跟你的业务创意毫无关系，但**一样都不能少**，而且每做一个 AI 应用就要重来一遍。

### Dify 的做法

**把上面每一行「脏活」都做成现成的可视化模块**，在网页上配置就行。你只需要专注在真正属于你的部分：提示词怎么写、挂哪些知识、给哪些工具、流程怎么串。

---

## 三、核心公式

```
        模型能力              你的数据              工具
      （接哪个大模型）   +   （知识库 / RAG）  +  （让 AI 能干活）
                              ↓
                       Dify 的可视化编排
                              ↓
              一个能发布、能集成的 AI 应用
           （网页 / API / 嵌入组件 / MCP Server）
```

这三样东西是**互补**的，缺一个应用就不完整：

- **只有模型** → 一个通用聊天机器人，不懂你的业务。
- **模型 + 数据** → 能回答公司内部问题了，但只会「说」，不会「做」。
- **模型 + 数据 + 工具** → 能查、能算、能调系统，才叫「智能体」。

---

## 四、能拿它做出什么（具体例子）

| 例子 | 用到什么 |
|---|---|
| **企业内部客服机器人**：上传产品手册当知识库，基于手册回答员工 / 客户提问。 | 模型 + 知识库 |
| **智能体 Agent**：接上搜索、计算器、数据库工具，自己拆解任务多步完成，比如「查一下上季度销售额并生成图表」。 | 模型 + 工具 |
| **自动化工作流**：「收到一封邮件 → 自动分类 → 提取关键信息 → 写好回复草稿」，全程无人值守。 | 工作流编排 |
| **文本处理 API**：把「批量翻译 / 摘要 / 审核」做成接口，供自己的系统调用。 | 模型 + API 发布 |

---

## 五、谁在用它

- **开发者**：快速搭原型验证想法；把 AI 能力以 API 形式接进自家产品，省掉底层搭建。
- **产品 / 运营等非重度编程人员**：靠可视化编排也能独立做出可用的 AI 应用，不必排队等研发。

这两类人共用一个平台，是 Dify 产品设计的核心张力——既要足够可视化让非开发者能上手，又要留足扩展口（代码节点、自定义 API、插件）让开发者不觉得受限。

---

## 六、它和相邻方案的区别

理解一个产品，看它「不是什么」往往比看它「是什么」更快：

| 对比对象 | 区别 |
|---|---|
| **直接调 LLM API** | 灵活但一切自建。Dify 的价值就是把重复的工程脚手架变成开箱即用，代价是要接受它的抽象。 |
| **LangChain / LlamaIndex 等框架** | 它们是**代码库**，你仍要自己写服务、做界面、搞部署运维。Dify 是**带控制台的平台**，自带 UI、日志、发布能力。层次不同，不完全是竞品。 |
| **Coze / 扣子等 SaaS 平台** | 定位最接近。核心差异是 Dify **开源、可自托管**，数据留在自己机房——这是企业内部场景选它的主要理由。 |
| **n8n / Zapier 等自动化工具** | 那些是通用自动化，AI 只是众多节点之一。Dify **以 LLM 为中心**，自带 RAG 和 Agent 运行时，AI 相关的能力深得多。 |

**它明确不做的事**：不自己训练模型，不提供模型（只做接入层），不替代你的业务系统。

## 七、为什么我们要研究它

Hify 是参考 Dify 理念裁剪出的**简化版 AI Agent 平台**，面向团队内部 20–50 人、本地部署。研究 Dify 的意义不在于抄功能清单，而在于两点：

1. **它验证过什么是「必需品」**——模型接入、对话引擎、知识库、工具调用这四样是任何 AI 应用平台的地基，Dify 用大量用户验证了这一点，Hify 不能省。
2. **它也暴露了什么是「过度设计」**——插件市场、多租户、企业级权限、可视化拖拽编排，对一个人开发、内部几十人用的场景是纯负担。

> **Hify 的原则**：拿 Dify 的模块划分当参照系，但每一项都要过一遍「一个人开发 · 本地部署 · 内部 20–50 人」这三个约束。
> 具体取舍见 `03_Hify功能取舍决策.md`。
