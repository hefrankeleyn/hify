# Hify 容量规划：QPS 估算 · 缓存策略 · 运维事项

> ⚠️ **本文档为作者独立分析（过程记录），非最终依据。** 容量/运维基准以 `10_Hify容量规划与运维（基准·课程版）.md` 为准。核心结论二者一致；差异在于本文的缓存策略偏丰富（为规模过度设计），基准版更极简——一期以基准版为准，本文的富缓存方案留作未来备选。
>
> 场景：AI Agent 平台，Docker Compose 本地部署，目标 **20–50 人同时在线**，主要压力在**对话接口（流式 SSE）**。
> 技术栈（依据 `08_Hify技术栈最终决策（基准·课程版）.md`）：Spring Boot 3.x + MyBatis-Plus + MySQL 8.x + Redis 7.x + Docker Compose。
> 整理日期：2026-07-12

## 〇、结论先行（TL;DR）

| 指标 | 数值 | 说明 |
|------|------|------|
| 对话「消息发起」QPS（峰值） | **~1–5 QPS** | 极低。对话是「低请求率 + 长连接」，QPS 不是瓶颈。 |
| **并发 SSE 流（峰值）** | **最多 ~50** | 上限=在线人数（最坏情况人人都在等回复）。**这才是要设计的数。** |
| 其它接口（配置 CRUD/历史/登录） | **几 QPS** | 可忽略。 |
| **真正的瓶颈** | **本地大模型的并发生成能力** | 不是 Spring Boot，也不是 MySQL。见第三节。 |

> 一句话：**这是个「小请求量、长连接、瓶颈在模型」的系统**。Web 层和数据库在这个规模下毫无压力，全部注意力应放在「并发 SSE 连接的承载」和「模型服务的并发/排队」上。

---

## 一、为什么 QPS 是会误导人的指标

传统 Web 用 QPS 衡量，因为请求短平快（几十毫秒）。但**流式对话每个「请求」是一条持续数秒到数十秒的长连接**（一直往外推 token）。所以：
- **QPS 很低**：用户发一条消息 → 等流式回复 → 阅读 → 再发下一条，一个来回 30–90 秒。
- **并发连接数才是关键**：同一时刻有多少条 SSE 流正在推送。

用 QPS 会严重低估系统状态（看起来 <5 QPS 很闲），却忽略了可能有 50 条长连接同时占用线程和模型算力。

## 二、QPS / 并发数估算（含假设与算法）

**假设（保守取值）：**
- 在线用户：50（取上限）。
- 活跃行为：忙时用户平均每 **30–60 秒**发起一次对话（含思考/阅读/输入）。
- 单次流式响应时长 `T_stream`：Agent 走 RAG + 工具调用 + 生成，取平均 **~10 秒**（慢的可达 30s）。

**① 消息发起速率（QPS）**
- 50 人 × (1 次 / 60s) ≈ **0.83 QPS**
- 激进些：50 人 × (1 次 / 30s) ≈ **1.67 QPS**
- 加余量取峰值 **~2–5 QPS**。→ 对 Spring Boot 是「毫无压力」级别。

**② 并发 SSE 流（用 Little's Law：并发数 = 到达率 × 停留时长）**
- 常态：1.67 req/s × 10s ≈ **17 条并发流**
- 最坏：到达率与流时长同时拉高，直到**上限 = 在线人数 = 50 条**（人人同时在等回复）。
- **设计目标：稳定承载 ~20 条、峰值兜底 ~50 条并发 SSE。**

**③ 线程模型的含义（Spring Boot 关键点）**
- 传统 Servlet 阻塞模型下，**一条 SSE 就占一个线程**（等模型返回时线程被 park）。50 并发流 = 占 50 个线程。
- Tomcat 默认 `max-threads=200`，**够用**；但更推荐两条路之一：
  - **虚拟线程（Java 21 + Spring Boot 3.2+，`spring.threads.virtual.enabled=true`）**：长连接等待几乎零成本，最契合本场景。← 首选
  - 或 WebFlux 反应式 SSE（`Flux<ServerSentEvent>`），非阻塞承载大量连接。
- 结论：**Web 层用虚拟线程即可轻松扛住，不是瓶颈。**

## 三、真正的瓶颈：本地模型的并发生成能力（务必先想清楚）

本地部署最容易被忽视、也最致命的一点：**一块 GPU / 一台机器上的本地模型，同一时刻只能高效生成有限几路**。

- 用 **Ollama** 跑本地模型：单卡通常只能并行 **1–4 路**生成，再多就排队 / 变慢。50 人同时提问 → 严重排队。
- 应对方案（按场景选）：
  1. **走云 API（Claude/OpenAI 的 Java SDK）**：并发上限高得多，本地不承担生成算力——最省心，代价是数据出网 & 费用。
  2. **本地用支持批处理的推理引擎（如 vLLM）**替代 Ollama：吞吐显著提升。
  3. **加并发限制器 + 排队**：用信号量把「同时进行的生成数」限制在硬件能力内，超出的请求排队并给用户「正在排队」反馈，避免雪崩。
- **⚠️ 无论选哪种，都要有「模型侧并发上限 + 优雅排队」**，否则 50 并发直接把模型服务拖垮。

> 记住：Spring/MySQL/Redis 在这个规模下都是配角，**模型服务的并发才是主角**。容量规划的重心应放在这里。

## 四、缓存策略（Redis 7.x）

对话系统的缓存要点是「省掉重复的贵操作（模型调用、Embedding、DB 读）」。按收益从高到低：

| # | 缓存对象 | 为什么缓存 | 建议 TTL / 失效 |
|---|----------|-----------|----------------|
| 1 | **Agent 配置 / 提示词模板 / 工具定义** | 每次对话都要读，改动极少（高读低写） | 长 TTL 或常驻；**配置更新时主动失效**（Redis pub/sub 或版本号）。可加本地 Caffeine 二级缓存。 |
| 2 | **会话上下文 / 最近历史** | 每轮对话都要拼历史，避免每次查 MySQL | 会话级 TTL（如 30–60 分钟滑动过期）；落库异步持久化。 |
| 3 | **Embedding 结果** | 向量化调 API 有延迟和费用，同一文本重复算浪费 | 按 `hash(文本+模型)` 长期缓存。 |
| 4 | **RAG 检索结果** | 相同 query 的召回可复用 | 按 `hash(query+知识库版本)` 缓存，中短 TTL；知识库更新时失效。 |
| 5 | **LLM 响应（精确匹配语义缓存）** | 内部 FAQ 类高频重复问题可直接命中，省一次生成 | 按 `hash(最终prompt+上下文+参数)` 缓存完整回答；注意**流式场景是把缓存结果再"伪流式"吐出**。语义相似缓存（向量近似）为进阶可选。 |
| 6 | **限流计数 / 并发计数 / 登录会话** | 天然适合 Redis | 令牌桶按用户限流；用 Redis 计数「当前并发生成数」配合第三节的限制器；登录 session 存 Redis。 |

**注意事项：**
- **不要缓存"正在进行的流"**；只缓存**已完成的最终回答**用于精确重复命中。
- 缓存 key 里务必带**版本维度**（知识库版本、配置版本、模型+参数），否则更新后返回旧结果。
- Redis 用途分两类：**纯缓存**（可丢，走 LRU）与**状态**（会话/限流，建议 AOF 持久化）——可用不同 DB 或 key 前缀区分。

## 五、需要提前考虑的运维事项（Checklist）

### A. SSE / 连接层（最容易踩坑）
- [ ] **反向代理为 SSE 关闭缓冲**：Nginx `proxy_buffering off;`、`proxy_read_timeout` 调长（如 300s+）、SSE 端点**禁用 gzip**、透传 `X-Accel-Buffering: no`。
- [ ] 正确响应头：`Content-Type: text/event-stream`、`Cache-Control: no-cache`、HTTP/1.1 keep-alive。
- [ ] **心跳**：定期发注释帧（`: ping`）保活，检测并清理死连接。
- [ ] **客户端断开即取消上游生成**：SSE 断连时要 cancel 掉正在进行的模型调用，省算力/省钱。
- [ ] 提高进程 **文件描述符上限（ulimit nofile）**，长连接多时别被打满。

### B. 稳定性 / 容错
- [ ] **模型调用超时 + 重试 + 熔断**（Resilience4j）：上游慢/挂时快速失败，不拖垮线程。
- [ ] **并发生成限制器 + 排队**（见第三节），超限优雅提示而非崩溃。
- [ ] **优雅停机**：drain 在途 SSE、JVM graceful shutdown、Compose `stop_grace_period` 调长。
- [ ] 连接池上限设置：HikariCP（DB）、Redis 连接池、调模型的 HTTP client 连接池 + keep-alive。

### C. 资源与部署（Docker Compose）
- [ ] 每个服务设 **资源限制**（`mem_limit`/`cpus`）；**JVM 容器感知**堆设置（`-XX:MaxRAMPercentage` 或 `-Xmx` 不超容器内存）。
- [ ] **健康检查**：每服务 `healthcheck` + `depends_on: condition: service_healthy`，保证启动顺序。
- [ ] **数据卷持久化**：MySQL、上传的知识库文件、向量库、（如需）Redis 都挂 volume。
- [ ] **容器日志轮转**：`logging` 驱动设 `max-size`/`max-file`，否则磁盘被写满。
- [ ] 本地模型的 **GPU/显存 或 CPU/内存** 预留：这是硬约束，先按模型大小定硬件。

### D. 可观测性
- [ ] **Actuator + Prometheus + Grafana**：重点指标——**并发 SSE 数、模型调用延迟 p50/p95/p99、排队深度、token 用量、错误率**。
- [ ] **结构化日志 + 会话级 traceId**：贯穿一次对话（含 RAG 检索、每次工具调用、模型延迟、失败原因）。
- [ ] 简单告警：模型错误率、排队深度、磁盘使用率、内存。

### E. 数据 / 安全 / 成本
- [ ] **密钥管理**：模型 API Key 走 `.env`/Docker secrets，**别打进镜像**，文件权限收紧。
- [ ] **备份与恢复**：MySQL（会话/配置）+ 向量库 + 上传文档定期备份，并**演练恢复**。
- [ ] 内部鉴权（基准 05：简单登录 + 管理员/普通用户）。
- [ ] 若走云 API：**按用户限流 + token 配额 + 费用监控/预算告警**。
- [ ] 磁盘增长监控：向量库、日志、上传文档会持续变大。

## 六、一个可落地的起步配置（建议值，非硬性）

| 组件 | 起步配置 | 说明 |
|------|----------|------|
| Spring Boot 应用 | 2 vCPU / 2–4 GB，开启虚拟线程 | 单实例足够扛 50 并发 SSE。 |
| MySQL 8.x | 1–2 vCPU / 2 GB，HikariCP pool ~10 | 本场景写入以会话日志为主，压力小。 |
| Redis 7.x | 0.5–1 GB，缓存 LRU + 状态 AOF | 缓存 + 限流 + 会话。 |
| 本地模型服务 | **按硬件定，配并发限制器** | **真正的容量瓶颈，优先规划。** |
| Nginx（可选，前置） | 关 SSE 缓冲、超时调长 | 若需统一入口/TLS 再上。 |

> 结论：**20–50 人在线对 Web/DB 层是"小系统"，单机 Docker Compose 单实例即可。把 90% 的容量规划精力放在「本地模型并发 + SSE 长连接承载」这两件事上，其余按上面的 checklist 补齐即可。**
