## 一、工作流程 / 步骤

> 从需求到交付的完整流程：如何拆解、如何与 AI 协作、如何验证。

- **先探地形，再动手**（案例①）：接到「梳理某产品/代码」类任务，先花几十秒确认信息底座——本地有没有源码、有没有 README。避免基于错误假设（如「fork 里一定有代码」）直接产出。
- **多源交叉验证**（案例①）：对「事实性/参考性」内容，不只凭记忆，用官方文档/站点核对一遍，降低过时或臆造风险。即使核对结果信息不全，也能确认「记忆是否与现状冲突」。
- **结构先行**：先定好分类骨架（如按「应用/知识/能力/运营/交付」分层），再往里填内容，产出天然有条理、易检索。
- **⚠️ 先答「是什么」，再列「有什么」**（案例①的返工教训）：整理一个产品/系统时，容易一上来就罗列功能模块，做成一份「零件目录」——读者看完记住了有哪些零件，却依然不知道整体是干什么的。正确顺序是先用大白话讲清楚 **①解决谁的什么问题 ②能拿它做出什么（举具体例子）③一句话定位**，让读者先建立整体图景，再让模块清单退居为「它内部怎么组织」的细节。**判断标准：一个没背景的人读完开头，能不能向别人复述这个东西是干嘛的。**

## 三、工具 / 工程实践

> 工具选型、代码规范、测试、评审、CI 等工程化落地。

- **⚠️ 先确认「用对了指标」，再开始估算**（案例⑨）：容量规划/性能评估类问题，第一步不是算，而是问「这个场景该用什么指标」。流式 SSE 对话系统用 QPS 会严重误导（请求率极低却可能有大量长连接），真正该算的是**并发连接数**（用 Little's Law：并发=到达率×停留时长）。**用错指标，后面算得再精确也是错的。**
- **定位「真正的瓶颈」，别把精力花在配角上**（案例⑨）：评估系统压力时，要显式排出瓶颈优先级，聚焦真正受限的那一环。本案例里 Web 框架/数据库在 20–50 人规模下都是配角，真正的瓶颈是**本地模型的并发生成能力**——容量规划 90% 的精力应放在这里。**别因为「Web/DB 是熟悉的话题」就在配角上过度优化。**
- **把关键决策沉淀进 CLAUDE.md，让 AI 每次都带着正确上下文工作**（案例⑪）：讨论中确定的产品定位、做/不做、技术栈、运维预期等「项目级共识」，要固化进 `CLAUDE.md`（而非散落在聊天里）。这样后续每次让 AI 写代码，它都自动带着这些约束，不会跑偏、不用反复重申。**沉淀时只写「稳定的项目级事实与约束」，从各"基准"文档提炼、保持简洁**；细节留在 docs，CLAUDE.md 只放最需要长期生效的那层。
- **⚠️ 验证要盯真实产物，别被自查脚本的假阳性骗了**（案例⑥的真实翻车）：批量修改（重命名、替换）后，验证必须直接检查**目标文件的真实内容**，而不是轻信一个自己临时写的检查脚本。案例⑥里发生了双重失误：① `perl -CSD` 因中文 pattern 与文件 UTF-8 编码层不匹配（缺 `use utf8`），替换实际没生效；② 自查用的 `grep -v "0[0-6]_"` 把「输出行首带的文件名前缀」误判成「已替换成功」的标志，于是得出「已完成」的假结论。**教训：a) 处理非 ASCII 文本时警惕编码层（字节模式 vs 字符模式）；b) 验证命令本身也可能有 bug，结论存疑时换一种方式（直接看文件内容）交叉验证，尤其当结果「刚好符合预期」时更要警惕。**
- **批量重命名要同步修正交叉引用**（案例⑥）：给文件改名（如加序号前缀）时，文档/代码里对旧名的引用不会自动更新。改名后要立刻全量扫描并修正所有引用，否则会留下断链。

## 四、心智模型 / 原则

> 底层原则与思维方式：何时信任 AI、如何分工、边界在哪。

- **⭐ AI 建议必须你「看得懂、能判断」才能采纳，否则项目会失控**（案例⑩，本方法论的核心原则）：这是整套「AI 辅助开发」的地基。AI 能给出很实在的分析，但你若看不懂就照单全收，就无法判断它在你的场景下是否成立、哪些能砍、哪些是坑——只会被建议牵着走、越加越复杂，直至失控。**看得懂，才能做有意识的取舍**（如案例⑩课程正因判断「QPS 不高」才敢主动放弃复杂缓存换低复杂度）。**AI 是加速器，不是你判断力的替代品；采纳任何建议的前提，是你能读懂它并为它负责。**
- **⚠️ 为「当前规模」做减法，警惕过度设计**（案例⑩的自我修正）：AI（包括我）有「把方案做全」的倾向，容易给出一份「理论完整但对当前规模过度」的方案。案例⑩里作者独立分析时列了丰富缓存层，而课程只缓存配置——因为对「单人 + 50 人 + 低 QPS」，每多一层缓存都是净增的开发/失效/一致性复杂度。**教训：方案的复杂度要匹配真实规模与约束，不是越全越好；对单人项目，「少建一样东西」往往比「多一层优化」更有价值。**
- **对比/选型前，先按项目性质给维度定权重**（案例⑤）：给定一组评估维度不代表它们等权。要先问「这个项目最看重什么」，据此加权——AI 平台就把「AI SDK/生态」权重拉满，单人开发就抬高「开发效率」，小规模部署就调低「运维/性能」。**否则容易被『某方案在某个次要维度领先』误导，得出错误结论。** 打分表要显式标注权重，结论才站得住。
- **选型时优先『顺生态而为』，别与主流生态脱节**（案例⑤）：技术栈的隐性成本是「和主流生态的距离」。做 AI 就跟着 AI 生态（Python 优先）走；跟随某课程/参考项目实践时，语言/框架与其保持一致能省掉大量翻译与踩坑成本。生态的引力，对单人开发尤其重要——一个人没有余力去补齐一门语言在某领域的生态空白。
- **别漏掉「个人熟练度 / 技术栈统一性」这类主观但决定性的约束**（案例⑧的印证）：技术选型时，客观维度（性能、生态）容易被充分讨论，但「开发者最熟什么、能否只用一套栈」这类主观约束，对**单人开发**往往是决定性的、能压过客观维度的。案例⑤/⑦作者已标注它是缺失变量，案例⑧课程补上「最熟 Java」后，结论从 FastAPI 翻转为 Spring Boot——**印证了：评估时必须主动向用户索取这类变量，或至少显式标注「若该变量取某值，结论会翻转」。**
- **「选最匹配约束的技术」而非「最好的技术」**（案例⑧）：技术的绝对先进性（如 AI 生态 Python 更强）只是输入之一。最终该落在哪，由**当前约束的合力**决定。一个在某维度不占优的方案（Java 做 AI），若在「熟练度+统一性+工程化」上占优，且劣势维度（AI 生态）对本项目影响可控，就是更优解。**警惕「技术优越感」凌驾于「场景匹配度」。**
- **先把约束翻译成判断标准，再做决策**（案例②）：面对「砍功能/做取舍」类任务，不要凭感觉逐条判。先把每条约束（如「单人开发」「20–50 人」「本地部署」）翻译成「它具体意味着什么、会淘汰哪类功能」，再提炼一条**不可压缩的主线**，用一句可反复套用的判断标准（「没有它，主线还能跑通吗？」）去过每个功能。决策就从「主观喜好」变成「可解释、可复现」。
- **单人/小团队场景下，优先砍「建设成本」而非「价值」**（案例②）：越是人力受限，越要按「做出来要多少工"来排优先级，而不是只看功能多诱人。可视化编辑器、插件生态、多供应商适配层这类「大而全的框架」正是最该延后的——宁可先硬编码，不做框架。
- **⚠️ 「省成本」≠「自己造轮子」，优先用标准/协议撬动生态**（案例③的关键盲点）：面对约束时，我下意识把「简化」等同于「自己写个最小版」，却漏掉了「**采用一个标准协议、白嫖现成生态**」这个往往成本更低、能力更高的选项。案例③里参考方案用 MCP（Model Context Protocol）接工具，一次对接协议就复用整个开源工具服务器生态，远比我「硬编码 2–3 个内置工具」更划算。**教训：砍功能前，先问一句「这件事有没有现成标准/协议/生态可以借力」，别默认只能自建。**
- **区分「延后」与「降级做」两种简化策略**（案例③）：中间档不是只有「一期不做、V2 再加」一种。还有「**降级做**」——一期就带上，但砍到最简（如知识库一期只支持 TXT、工作流先用 JSON 配置不做可视化）。「延后」让 V1 更小更快；「降级做」让 V1 更完整、减少日后重构。按「这个能力是否影响产品完整性/是否会导致返工」来选用哪种。
- **把「能力」与「UI/交付形式」解耦**（案例③）：同一功能，重的往往是 UI（如可视化拖拽），而非能力本身。可以先用配置/代码/JSON 让「能力」低成本落地，把昂贵的可视化 UI 单独排期。拆分粒度更细，取舍就更精准。
- **⚠️ 不为自己之前的结论护短（抗立场偏差）**（案例⑦）：当用户的新问题实质是在「压力测试」我先前的推荐时，要就事论事、诚实承认对方更强的地方，而不是下意识替旧结论辩护。案例⑦里，前面推荐了 FastAPI，但被问到「工程化能力差距」时，必须先大方承认「Spring 在事务管理上是代差级领先」，再理性分析「本项目的前提是否让这个差距变得不重要」。**先认账，再论证；结论可以不变，但不能靠偏袒来维持。**
- **区分「理论差距」与「对本场景的实际影响」**（案例⑦）：两个方案的能力差距（理论）和「这个差距在你的具体项目里会不会真的疼」（实际影响）是两回事。评估时要把「业务类型/规模/约束」代入，看差距是否落在你真正会用到的战场上。Spring 的事务优势是真的，但 AI 平台事务复杂度低 → 实际影响有限。**不要用抽象的强弱排名替代对具体场景的影响评估。**
- **指出优劣后，给「补齐短板」的可执行清单**（案例⑦）：当推荐了一个有短板的方案，不能止于「它弱在 X」，要顺手给出「如何把 X 补到够用」的具体落地清单（如 FastAPI 自建统一异常体系、事务性 session 依赖、Alembic 迁移等）。让「有短板但仍推荐」变成「知道短板且有办法」，决策才真正可执行。
- **诚实标注不确定性**（案例①）：当依据是「记忆 + 不完整核对」时，在产出中显式声明信息来源与局限（如文档里注明「基于官方产品梳理，本仓库暂无源码」），而非佯装权威。
- **可追溯优先**：每一步操作、每一次决策都留痕（工作记录 + 产出文档分离），方便日后复盘方法本身，而非只留结果。
- **主动对标权威参考，找自己的盲点**（案例③）：完成一个决策后，拿它跟一份成熟/权威的参考方案逐条对齐，是发现盲点最快的方式。对齐时不要急着「维护自己是对的」，而要重点找「它做了而我没想到的选项」（如 MCP、降级做）——分歧处才是收获最大的地方。诚实评判优劣，该采纳就采纳。
- **明确 source of truth，让多份文档各司其职**（案例④）：当同一主题存在多个版本（我的分析、参考方案、课程基准），不要让它们互相打架。应指定一份为「基准/唯一依据」，并在其顶部显式声明「如与其它文档冲突以此为准」，其余文档退为「过程/对比记录」。跟随外部课程/规范实践时，尤其要让**外部权威版**成为基准，避免自己的推演喧宾夺主、误导实操。
- **保留用户原话，还原真实语境**（案例①）：记录时不要只写「我的转述/理解」，还要原样保留用户当次的问话。转述会丢失措辞、语气和隐含需求；原话才能在日后复盘时还原「当时用户到底怎么表达的、我是否理解到位」。
